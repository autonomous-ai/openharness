## What measurably improved

| Workload and comparison | Baseline | After | Result |
|---|---:|---:|---|
| Cmd+O Release p95, #226 alone, 120 samples/action/revision | 20.043 ms | 16.463 ms | **17.9% lower p95**; median 16.332 → 15.675 ms and build median 4.603 → 3.900 ms. |
| Cmd+O debug first frame, 16 / 48 retained terminals, #226 alone | 31.626 / 26.623 ms | 22.872 / 18.525 ms | **28–30% lower median**, 34–36% fewer rebuilt widgets. |
| Search query extension, 2,000 agents, isolated #219 debug run | 18.46 ms | 11.40 ms | **38% lower median**; p95 50.78 → 16.71 ms. Selection tails did not consistently improve. |
| Shortcut-browser fully opened Release frame, #219–221 combined, 80 samples/action/revision | 153.28 ms | 18.99 ms | **87.6% lower median**, primarily from removing the fade. |

These are separate comparisons, not additive gains. There is no single measured percentage for all four implementation PRs combined. Cmd+N and Cmd+T have **no established Release latency improvement**, and no accepted experiment demonstrated a material tab-switch speedup. Debug CPU gains must not be presented as native display latency. Slower controls, tail outliers and unchanged results are preserved in the detailed reports.

Release measurements cover framework keyboard dispatch through the exact requested Flutter raster-completion frame. They exclude OS input delivery, physical display presentation, native titlebar painting completion, real network and agent response time. The host was an Apple M2 Max with 64 GiB RAM, macOS 26.6.2, Flutter 3.47.2 / Dart 3.13.2. Other applications remained running; our timing runs were serial and did not overlap our builds/tests. This is local synthetic evidence, not a claim of zero latency.

## Verification and coverage

The full desktop suite on the earlier combined implementation completed 2,788 passing tests, 10 skips and one daemon-discovery timing failure. That file passed all 31 tests when rerun alone. Later focused suites and changed-file analysis passed on each independent branch: 59 tests for #219, 62 for #220, 149 for #221 and 63 for #226, plus a rerun after finalizing the picker cache API. A 25-test combined primary-workflow check also passed. These counts overlap and should not be added into one total.

The native Release fixture was exercised through application controls for Open/New Harness, query filtering and preview, commands, shortcut browsing/practice, tabs, Store pages, Settings and terminal Find. Repeated dispatch runs independently checked requested states, including new-tab creation and closing/restoration. Nine native-bundle isolation tests passed. The fixture uses disposable state, synthetic transports and blocked networking. Real agent launch, remote transport, reconnect and backend response time were outside this pass.

The final documentation update adds no runtime changes. Implementation PR worktrees were clean and their pushed head revisions verified. The isolated benchmark app was closed when work stopped.

## Experiments deliberately excluded

- [#224 — Welcome-page retention](https://github.com/autonomous-ai/openharness/pull/224): closed. Debug gains did not translate into a justified Release benefit. Initial Cmd+T and tab-switch medians worsened; subsequent baseline drift prevents attributing the entire difference to the change. See the [primary-workflow report](2026-09-22-primary-workflows.md).
- [#232 — Outgoing pane-control retention](https://github.com/autonomous-ai/openharness/pull/232): closed. Tab-switch build work fell about 6%, but both Release input cadences increased elapsed medians. With varied input timing and 360 measured samples/action/revision, median was 19.456 → 20.775 ms and p95 24.828 → 25.477 ms. All 6,600 observations across 14 completed runs are retained in the [pane experiment report](2026-09-22-pane-workflows.md).

Neither rejected production change is present in the combined checkpoint or ready PRs.

## Resume here

1. Start with Cmd+N/T and workspace switching; they still lack a demonstrated Release speedup. Review current main and the status of the ready PRs before starting new branches.
2. Profile native titlebar work during those operations. Source inspection found that `SwarmTitlebar.updateHistory` immediately reconstructs and sizes the History menu whenever its entries change, even when closed. This is a **candidate**, not an established bottleneck or implemented fix. The attempted final system sample caught idle activity and did not produce a fresh completed benchmark result; it is excluded from all performance claims.
3. If deferring hidden-menu work helps, preserve menu shortcut availability, validation, accessibility and current entries on opening. Existing native checks live in `desktop/tool/swarm_titlebar_checks.swift` and `desktop/tool/check_swarm_titlebar.sh`.
4. Keep identical benchmark tooling on both production revisions. Use both post-frame and varied-input modes, alternate complete baseline/modified runs, preserve every completed observation and check build/raster work separately from frame waiting. Retain a change only when the benefit justifies its complexity.
