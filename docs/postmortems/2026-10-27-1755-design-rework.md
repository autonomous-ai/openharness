# Post-mortem: why Swarm's state was redone, and what #1755 redid

Date: 2026-10-27. Author: Theo (Builder), from the PR, commit and review records. Root cause and rules: Ken. Rules:
[Feature design rules](../feature-design-rules.md), short version in [AGENTS.md](../../AGENTS.md#feature-design-rules).

## Root cause

Swarm had to redo its state storage (#1726) because the original design (#1405, merged 2026-10-19) never asked
three questions: how the data grows, who writes concurrently, and how much a client reads per poll. The spec had no
design-check step.

- **Growth, concurrency and read cost were never designed.**
  - Each Swarm was one MongoDB document. Its whole state was one JSON field under one revision.
  - Every command rewrote all of it, and every client poll downloaded all of it.
  - Finished work never left the document.
- **Later features kept adding to it.** In the seven days after #1405, 31 PRs changed the same state model
  (`backend/src/superTabs/model.ts`): routing, team roster, private projects, attachments, decisions, the Reviewer
  role, owner rules, custom roles, the Leads conversation, local models, and more.
- **It failed on 2026-10-26.** One Swarm reached 1.16 MB with 195 work groups and returned 500s on `agent.add`
  from write conflicts (#1726). The first fix, #1722, only added retries and `503 SWARM_BUSY`. It eased the
  symptom, not the cause.

Other problems were found late for the same reason. No design step asked the question that would have caught them:

| Found late | The question nobody asked |
|---|---|
| Private chats reaching the PM's terminal and the previous release (#1751, #1748; D9, D10 below) | audience: the server enforces it, on every copy |
| Every old client getting 426 at release, so all clients had to update together (#1755) | compatibility: old and new clients |
| Teammates' agents running as the machine owner, with the owner's git login: 18 of 113 agent starts in one live Swarm, 21–23 Oct. Fixed by the Team account work (#1688–#1705, `docs/plans/2026-10-24-swarm-team-account.md`). | identity: never use the machine owner's login |

The twelve incidents below are the same failure inside the redo itself. #1726 did have a design and a design
review, and that review caught six problems before any code. But the design lines that later broke were not on its
list, and work added after approval (v1) had no design at all.

## The redo: #1755

#1755 merged "Swarm state by parts" (#1726) and the v1 Swarm work (Chat with PM, lost-work takeover, routing
readiness) into main on 2026-10-27. Its design was
[docs/design/2026-10-26-swarm-state-parts.md](../design/2026-10-26-swarm-state-parts.md), built against the spec
[docs/plans/2026-10-26-swarm-state-parts.md](../plans/2026-10-26-swarm-state-parts.md) and its private
conversations addendum. Groups 2–6 and the v1 groups each merged a PR into `feat/swarm-state-parts` (#1731–#1752).
Then the branch went to main.

This document lists every piece that was built and then redone or patched late because of a gap in the design. For
each one it gives what was redone, the evidence, the gap, when it was found and what it cost. Coding slips that
ordinary review caught are listed separately at the end. No rule cites them.

All times are UTC, taken from the PR commits and the Swarm review conversations. Costs count Builder hours from the
finding to the accepted fix, plus review rounds: verdicts that sent the work back, and the re-check that passed it.

## Incidents

Each incident's **Gap** names the line of the [Design section](../feature-design-rules.md) it broke: growth,
concurrency, read cost, scale, compatibility, migration and rollback, audience, identity, failure or platforms.

### D1. Hosts missed changes that removed something

- **Redone:** the host form's wake-up rule. It now records the machines a group write affected, before and after
  (`SwarmGroup.hostMachineIds`), and a settings marker on machines (`SwarmMachine.hostChangedAt`). An agent that
  leaves a group is written again, so a later rename cannot hide its departure. Design R15 was added afterwards.
- **Evidence:** group 3 review findings at 12:43 and 12:56. Fixes in #1733 `0c154c426` and `d9740911d`.
- **Gap (read cost):** design 4.10 woke a host for a group whose *new* agents included one of its agents. The
  invariant "a host sees every change that concerns its machine" was stated for additions only. Removals, and a
  later write that replaces the marker, were never considered.
- **Found:** group 3 review, after implementation.
- **Cost:** 0.4 h and 3 review rounds. Two new columns and a rewrite of the commit path, all in group 2's files.

### D2. Machine readings woke every host, and every tick resent the roster

- **Redone:** readings no longer wake hosts (design R16). Each Swarm entry in the host form now has an etag, and a
  host sends the etags it holds in a new POST body. Group 5 had to mirror the changed contract.
- **Evidence:** #1733 `200ebec52` and `282ff95eb`, both "Lead's ruling after group 5's end-to-end run". #1737
  `f13ac1673` and `a8f722a7f` mirror them in the CLI.
- **Gap (read cost, scale):** the design said which part writes wake a host, but gave no cost budget for a host tick. Every
  machine reports every 15 s, so every tick resent its Swarm. Nobody saw this until a real host ran end to end.
- **Found:** group 5's end-to-end run, after groups 3 and 5 had built against the contract.
- **Cost:** 0.6 h across two groups and 2 review rounds. One new route and a team-session allowlist entry. The
  wire contract changed after a client had already been built against it.

### D3. Reads loaded the whole Swarm from the database (group 3 to group 3b)

- **Redone:** the change read and the host form. They now load only the parts they need, through a second loader
  (`parts/light.ts`) and a new stored digest (`SwarmGroup.hostDigest`).
- **Evidence:** the group 3b brief at 14:20, and #1745. An idle Desktop change read sent 2.8 KB but loaded 1.17 MB.
  The host form loaded 2.3 MB to answer "unchanged", worse than main, which blocked the merge. After the fix they
  load 45 KB and 16 KB. Group 2's PR (#1735, 12:58) had already noted that host reads "read every part (about
  1,150 KB from MongoDB per tick)".
- **Gap (read cost, scale):** spec goal 3, "a poll costs what changed", was designed and measured only as bytes sent. Design
  section 4 fixed the wire contract, but not what each read loads from the database. Group 0's benchmark measured
  only the wire.
- **Found:** group 6's integration benchmark, after groups 2–5 had merged.
- **Cost:** a new group, 2.2 h (14:20–16:32), 5 commits and 3 review rounds. Group 6 reran its results. The second
  loader then caused D4 and D8c.

### D4. The second read path disagreed with the first

- **Redone:** change reads now apply the known-kind rule that first loads apply. Before, a conversation of a kind
  written by a newer release reached an older reader in changes but not in a first load.
- **Evidence:** group 3b review at 15:42. Fix #1745 `58f5a8b13`.
- **Gap (compatibility, audience):** read filters were written into each read path, not kept as one rule that every path calls.
  The design listed the audience check for every path (4.4), but not the known-kind check.
- **Found:** group 3b review.
- **Cost:** 0.1 h and 1 review round.

### D5. The new dormant flag broke code that assumed every group was loaded

- **Redone:**
  - Losing a project now loads dormant groups too, so their terminals are revoked. A second round extended this to
    old groups with no project id.
  - A group goes dormant only once its reports are read. This corrects design 3.6 a second time; the design review
    had already corrected it once.
  - The migration follows the same dormancy rule.
  - The CLI reads a dormant group's history on demand.
  - Desktop keeps paging older archived groups behind newer dormant ones.
- **Evidence:**
  - Group 2 review round 1, findings 1 and 3, and round 2. Fixes #1735 `99c0060ac` and `ebe62a97f`.
  - #1733 `a9dbb7e86`.
  - Group 5 review finding 2. Fix #1737 `ccdfc6f63`.
  - Group 4 review finding 2. Fix #1734 `01c138eb3`.
- **Gap (growth):** design ruling R3 added `dormant` and said "only the feed and first load read it". It did not
  list the code that relied on all groups being loaded: access revocation, report wake-ups, route-history checks
  and the archived list.
- **Found:** reviews of groups 2, 4 and 5, after implementation.
- **Cost:** 0.9 h and 6 review rounds across four groups. The design was corrected twice.

### D6. Versions reset when a key was recreated after its tombstone was purged

- **Redone:** people, agents and machines now keep their tombstones for good, compacted to the version after 7
  days, so a recreated key continues above its old version. This corrects design ruling 6 and section 2.1.
- **Evidence:** group 2 review round 1, finding 4. Ruling "Versions never reset, even after a purge" in #1735.
- **Gap (growth):** the design had no lifecycle for a part's key (create, delete, purge, recreate under the same
  key), so the purge-then-recreate path was never checked against the rule that versions never reset.
- **Found:** group 2 review.
- **Cost:** part of group 2's two extra rounds (D5). Both the design and the code changed.

### D7. The design's touch table would have brought the conflicts back

- **Redone:**
  - A post no longer touches its recipients.
  - A terminal turn no longer touches the person who opened the terminal.
  - Delivery claims touch only a person sender.
- **Evidence:** #1735 `e5d248293` and `5b130091b`, the ruling "Touching recipients made every worker's post touch
  its Lead, and posts in different groups conflicted again", and the Reviewer's guard audit table in #1735. Group 2
  review finding 1 (D5) was a gap in that narrowed table.
- **Gap (concurrency):** the design's table of parts each command touches was never run against goal 1 (no
  conflicts between groups) before groups split. Only building it showed the conflict.
- **Found:** group 2, while building.
- **Cost:** 0.5 h of rework, a per-change guard audit for the Reviewer, and one Important finding that came out of
  the narrowed table.

### D8. The new `lost` status was not traced through the code that reads work status

The liveness design ("A Swarm that never stops") was a scratchpad doc attached in chat. It joined the branch after
the design was approved, with no design review and a 05:00 Vietnam time deadline ("working product first"). Its brief defined
`lost` as "not active", but did not list the code that reads work status or active work. Six fixes followed:

| | What was patched | Evidence | Gap | Found | Cost |
|---|---|---|---|---|---|
| a | Cancelling lost work brought back a blocking "decide what to do with the worker". | liveness A review 15:29; #1742 `53908fe9e` | compatibility: decision derivation (`awaitingWorkers`) | review | 0.2 h, 1 round |
| b | A loss decided from a machine report did not guard that report, so it could fence a live worker. | liveness A review 15:23; #1742 `05a8328a4` | concurrency: a sweep outside commands ignored the design's touch rule (3.4) | review | in a's round |
| c | The light loader dropped the lost marker, so change reads derived a decision that first loads did not. | group 3b review 15:51; #1745 `bb907dc23` | compatibility: the second read path (D3) | review | 0.6 h, 1 round |
| d | A lost worker became routable again after its task was cancelled or reassigned. The first fix then also refused workers that had recovered. | final review I3, 17:45; #1749 `bbd17458d`, `57410c62e` | failure: lost, then cancel, reassign, recover | final review | 1.7 h, 2 rounds |
| e | Rolling back handed lost tasks to a release that cannot read them. | final review C2; #1748 | migration and rollback (D10) | final review | in D10 |
| f | When liveness lost a task outside a command, the agent's running-work record was never freed. After the release, 16 lost tasks left their agents unassignable for good, even after cancel. | #1781 `54fa314a8`, `df7f62bf5`; its review found stale deliveries too | failure: "an agent has a run record exactly while it owns active work" was kept only by commands and stop receipts, not by the liveness checks | **production, after release** | 0.6 h and 2 rounds to fix; 16 agents blocked in production until it ships |

**Cost:** 3.1 h of fixes and 6 review rounds before release, plus the production incident.

### D9. A private chat reached a terminal that other people could watch (final review C1)

- **Redone:**
  - A native session becomes confidential once it is a Lead or a member of any private conversation, in any Swarm.
  - Only its machine's person may observe, share, read or type into it: through Swarm shares, ordinary shares,
    other Swarms and agent requesters.
  - A confidential session may be registered in one Swarm only, and a new shared record makes concurrent
    registrations conflict (`SuperTabSessionScope.confidential`).
- **Evidence:** final review at 17:45. #1751, 10 commits starting at `b3dce532a`, last fix `d6184d911`, with five review rounds
  at 18:52, 19:10, 19:47, 20:40 and 20:47 before Ready at 21:35. An isolated end-to-end run proved it.
- **Gap (audience):** the addendum listed where a private conversation must not appear: first load, changes, message
  reads, notifications, mentions and `otherProjectsWork`. Those are API routes. It did not list the copies the data
  makes: the PM's terminal screen and scrollback once a message is delivered, shares made outside a Swarm, and the
  same session working in another Swarm. The design review did catch one leak of this kind, dormant stubs, at
  design time.
- **Found:** the whole-branch review, after every group had merged.
- **Cost:** 4.8 h (17:45–22:34) and 6 review rounds. A new schema field and a new product rule.

### D10. Rollback could not represent work added after it was designed (final review C2)

- **Redone:** rollback now refuses any Swarm with a private conversation or a lost task, and the recovery path is
  to roll forward. The refusal's wording was corrected in #1750.
- **Evidence:** #1748 `07626fe86`, #1750 `0dc9e5695`, and final review C2.
- **Gap (migration and rollback):** design 6.4 was written before private conversations and `lost` existed in the
  branch. Nobody asked again what the previous release does with each new field when scope grew. That release
  checks no audience, and does not know the lost status or the lost marker.
- **Found:** the whole-branch review.
- **Cost:** 1 h and 1 round plus a Minor. A lasting product limit: those Swarms can only roll forward.

### D11. The migration refused history from deleted conversations

- **Redone:** messages of conversations deleted before the migration are kept and stay unreadable. Verification
  still rejects anything the migration itself would lose.
- **Evidence:** #1778 `1374a4f2d`. On an isolated restore of the production backup, 24 of 24 Swarms then
  migrated, and 5,380 orphan messages in 7 Swarms stayed unreadable.
- **Gap (migration and rollback):** design 6.3 required "no orphans" in the message fingerprint. That was assumed, not
  checked against production. The dry run used synthetic Swarms made through real commands, which cannot contain
  old anomalies. The spec's plan for a production-copy dry run had been replaced by synthetic data, pending an owner
  ok that never came before the merge.
- **Found:** the gated production migration, after the merge to main.
- **Cost:** a fix during the release window. The production backend stayed on `v1.3.35_backend` until the fixed
  image was built.

### D12. Chat with PM after leaving and rejoining opened a chat the person could no longer read

- **Redone:** the chat's create request is keyed by membership generation as well as account and project.
- **Evidence:** Chat with PM review at 16:15. Fix #1746 `c1752b1dd`.
- **Gap (audience):** the brief required one chat per account and project for life. It did not cover membership
  ending and starting again, which changes who can read the old chat.
- **Found:** review.
- **Cost:** 0.25 h and 1 round.

### Knock-on cost: the main merge was done twice

Main was merged into the branch at 17:41 (`1a3e238bd`, reviewed on its own). D8d, D9 and D10 then landed, so the
merge was redone at 22:35 (`21480ef97`, #1747), with its checks run again.

Rule 2 (review the design again) would have triggered on D1, D5 and D8, each patched twice or more, and on #1722
itself. The v1 work joined the branch with no Design section, which rule 1 requires of any spec that stores data.
That was the source of D8, D9, D10 and D12, and of the 7.5 h after the whole-branch review.

## What worked

- The design review with code citations found 6 issues in 9 minutes, before any code: the migration fence, private
  stubs, finished starts, dormant reports, paging ties and owner visibility. Each would have cost a group a round
  later.
- Rulings recorded with "cost if wrong" made every deviation reviewable. Several incidents above were found because
  a ruling stated its assumption.
- Red-then-green tests in every fix kept fixes from regressing.

## Coding slips (not design; no rule cites them)

Ordinary review caught these, and each took one fix round:
- **Group 2:**
  - the dormancy sweep could revisit the same ineligible groups forever;
  - the benchmark self-test was not adapted.
- **Group 4:**
  - a failed dormant fetch skipped the rest of a change read;
  - the dormant list swallowed the update-required answer.
- **Group 5:**
  - updating a part changed its order;
  - a forced full answer was ignored.
- **Routing readiness:**
  - query credentials were kept in repository observations;
  - a hung git helper outlived its deadline;
  - a failed probe counted as "cannot".
- **C1 fix:** a race test failed when one of its two valid winners won.
- **#1781:** stale-record repair left old deliveries claimable.
