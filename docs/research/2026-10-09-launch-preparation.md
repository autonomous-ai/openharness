The launch-port design's older refusal policy for manual operations is superseded by the current requirement: an unavailable dependency must hold the intent with a visible reason, without failing or half-writing it. Session control and readiness stay independent. Preparation must use confirmed executable facts, preserve operation authority across awaits, and publish only confirmed effects. A durable journal must distinguish safe retries from unconfirmed mutations. These are safety changes following the compatibility extractions, not line-count targets.

Validation will preserve the former golden artifacts, add regressions for the new guarantees, deliberately break wiring, run the affected private-daemon lanes and enforce TypeScript, architecture and per-file core/master coverage. Independent exact-head review and automatic CI precede each merge. No release is authorized.

The first implementation introduces a preparation/commit boundary for relaunch overrides. Models answers before the Store is asked; profile hooks and grid configuration wait until both answers succeed. One deep request snapshot and one machine-fact snapshot supply the attempt. Core instruction-file preparation and saved-API notes wait for an available dependency answer. Ordinary semantic refusals retain the established saved-API notes; the former grid golden caught this distinction. The Store opens SCM instruction files only inside its durable workspace reservation, immediately before the package writes them; an unavailable or uncertain Store causes no earlier core SCM edit. Fresh create and fork likewise defer their own saved-API instruction work.

This step does not yet journal a manual create/fork/restart/retarget intent, make grid writes atomic, or solve retarget authority and native-write uncertainty. Those remain required. In particular, callers still need a durable held outcome instead of converting unavailable-service answers into ordinary failure receipts. Successful former golden observations must remain unchanged through this staging change.

Independent review found that moving instruction writes after a service await could reread a changed registry row. Relaunch now captures immutable requested data separately from core-owned lifecycle authority. Stopped resume and restore’s terminal/fresh projections are legitimate requests that differ from the live row. Their owning current predicate grants the operation; a separate snapshot of the actual live row at dispatch detects later changes. Binding, process, route, launch facts, Stop state and coordinator revision fence local commits and deferred instructions; authority is checked again after SCM preparation. Prepared closures are ephemeral and accept one commit only. This does not claim atomic rollback of an already-dispatched write or fencing of an in-flight Store operation.

Private Store-outage acceptance preserves custom-profile hook bytes and both workspaces’ instruction bytes while launches are held, then verifies required hooks and saved-API notes appear only after recovery. The broader authority and durable-intent work remains separate.

Review also caught that equating a requested projection with the live registry would reject stopped resume and terminal fallback. The first bundled fork lane reproduced that regression for both engines. The corrected composition explicitly passes restart/restore/resume authority, accepts an absent stopped row, and treats preparation revocation as cancellation in restore rather than failing or retiring the newer row. Composed regressions exercise those paths with the real launch helper. A matrix fixture exceeded its existing five-second case budget while broad checks ran; its isolated serial pass is required separately. No failed suite is counted as passing.

Linux CI also caught the older launch-argv golden's precise call trace: OpenCode and Pi on a DSH plus grid formerly wrote configuration before asking the Store. That order is the safety behavior intentionally changed here. The former JSON stays byte-for-byte intact. Only those two named expectations, on both platforms, assert the exact former trace and then require the reversed trace; their complete results and every other case retain exact equality. A mutation restores the old order without adding duplicate writes and must fail this golden assertion. This is an explicit behavior change, not a claim that the entire former call order is unchanged.

[Runtime observations](2026-10-09-launch-preparation-cost.json) compare frozen main and candidate bundles in baseline/candidate/candidate/baseline order, with all thirteen native installers and two fresh OpenCode launches per private daemon. Ready time was 1,582–1,961 ms on main and 1,555–1,632 ms on the candidate; core CPU at ready was 300–310 versus 340–350 ms; RSS rounded to 78.4 MiB in all four runs. Cold launch requests were 187–189 versus 192–195 ms and warm requests 89–92 versus 97–100 ms. These two samples per bundle and the 10 ms CPU observation resolution are reference measurements, not a speed claim or threshold. This workload measures startup and fresh launch, not all retarget or Store-outage latency.
