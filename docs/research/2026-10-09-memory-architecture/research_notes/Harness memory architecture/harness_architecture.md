# Harness memory architecture: what exists and what a cross-agent, cross-machine memory must fit into

Research date: 2026-10-09, against branch `cross-agent` at `f810d23ece` (main-equivalent). Read-only study of the repository. All paths are repo-relative. "Source" links point at repository files; line numbers are from this revision.

Status labels used below:
- **Implemented + tested**: code exists and has executable unit/spec tests in the repo.
- **Implemented, unverified**: code exists but the behavior was not demonstrated end-to-end (live app, real model, real user data).
- **Planned only**: described in docs, no code.
- **Removed / disconnected**: code existed and was removed from the running product.

## 1. The existing memory subsystem (companions/src/memory): modules, data model, pipeline

### Takeaway
A substantial, carefully engineered coding-memory library exists (about 5,500 lines of non-test TypeScript in `companions/src/memory/*.ts`, about 6,000 lines of tests, plus a 2,600-line older "lessons" system). It is a single-machine, single-profile SQLite store with evidence-bound records, revisions, tombstones, an episode queue, LLM extraction through the user's own native CLI (Claude Code / Codex / OpenCode), FTS5 recall with scope/condition filtering, and content-free delivery receipts. Since PR #684 (2026-10-03) it is a library only: nothing starts it, core refuses its requests, and the native hook delivery path was deleted.

**Record schema (data model)**
- Scope: `{profileId, projectId?, taskId?, branchId?}`; task/branch require a project. — [types.ts:12-14](companions/src/memory/types.ts)
- Source event: `{id, profileId, projectId|null, engine, sessionId, nativeEventId, taskId?, branchId?, role: user|assistant|tool|reference|derived, eligibility: coding|private|excluded|non_coding, observedAt, rootIds[1..32], derivedFrom?[{memoryId,revision}], text<=32,000, verification?, retention?: 'evidence_only'}`. Derived sources must carry memory lineage. — [types.ts:23-33](companions/src/memory/types.ts)
- Evidence: `{sourceEventId, quote<=4,000, paths: JSON pointers into the memory (1..32), verification?}`. — [types.ts:35-39](companions/src/memory/types.ts)
- Verification: `method ∈ {test, benchmark, static_analysis, proof_review, visual_review, manual_check, operational_observation}`, result, artifact, revision, environment, coverage, limitations, deployment window. — [types.ts:16-21](companions/src/memory/types.ts)
- Draft/record: `kind ∈ {working_preference, project_decision, verified_pitfall, reference, working_continuity}`, `facet`, `assertionType ∈ {stated_preference, observed_usage, project_constraint, accepted_decision, verified_finding, learning_goal, temporary_state}`, `claim`, `rationale|null`, `futureAction`, `applicability` (typed condition map, ≤24 keys), `exceptions[]`, `retrievalCues[]`, optional `details` (style/decision/reference/experiment with runs, objective, evaluator, dataset, budget), `evidenceClass ∈ {user_stated, observed_verified, inferred, imported}`, `evidence[1..16]`, `conflictKey`, `validity {validFrom, validUntil, recheckWhen}`; ≤32,000 bytes. — [types.ts:59-73](companions/src/memory/types.ts)
- Stored record adds `schemaVersion: 1, id (random UUID), revision, state ∈ {active, tentative, needs_verification, superseded, archived}, createdAt, updatedAt`. — [types.ts:79-82](companions/src/memory/types.ts), [store.ts:454](companions/src/memory/store.ts)
- Access is "Constructed by the authenticated host, never copied from a model's request body": `{profileId, projectIds[], includeProfile, taskId?, branchId?}`. — [types.ts:92-99](companions/src/memory/types.ts)
- Topics (notebook pages): statements each citing `{memoryId, revision, paths}`. — [types.ts:101-113](companions/src/memory/types.ts)
- SQLite tables: `memory_meta, projects, memory_project_names, memory_project_policy, memory_session_policy, project_locators, sources, source_lifecycle, retired_sources, memories, revisions, memory_scope_changes, evidence, memory_support, memory_fts (FTS5: claim, rationale, cues), topics, topic_dependencies, source_dependencies, suppressed_sources, tombstones` plus queue tables (`memory_streams, memory_jobs, memory_job_context, memory_job_sources, memory_inference_calls, memory_inference_jobs, memory_queue_totals, memory_inference_purpose`), receipt tables (`memory_receipts, memory_receipt_items, memory_receipt_context, memory_receipt_relevance, memory_recall_feedback`), notebook tables (`memory_notebook_jobs, memory_notebook_waits`). — [store.ts:93-176](companions/src/memory/store.ts), [queue.ts:9-43](companions/src/memory/queue.ts), [receipts.ts:52-80](companions/src/memory/receipts.ts), [notebook.ts:10-23](companions/src/memory/notebook.ts)
- Store file: `<directory>/memory.sqlite`, directory 0700, file 0600, symlinks refused, `PRAGMA journal_mode=DELETE; synchronous=FULL; secure_delete=ON` ("No long-lived WAL containing deleted text"), FTS secure-delete on. Schema version 2 (records remain v1). Store is bound to one profile: opening with another profile id fails `profile_mismatch`. — [store.ts:35-38,71-92,182](companions/src/memory/store.ts)
- Default controls on creation: `{learn:false, recall:false, generation:0, captureEpoch:0, learnSince:null}`; preferences `{learn:true, recall:true}`. — [store.ts:179-181](companions/src/memory/store.ts)
- Tombstones: `forget()` deletes the memory, its dependent records/topics, FTS row, inserts `tombstones(id, last_revision, at)`, adds source suppression keys (so replay cannot relearn), trims shared sources to remaining evidence excerpts, and returns `alreadyDeliveredContent: 'not_erased'`. — [store.ts:996-1036](companions/src/memory/store.ts)
- Revisions: optimistic concurrency via `expectedRevision` (`revision_conflict`), a `generation` counter on controls (`generation_changed`), conflicting claims with the same `scope_key`+`conflictKey` and overlapping conditions both go to `needs_verification`. — [store.ts:1118-1150](companions/src/memory/store.ts)
- Dedup: proposal fingerprint = digest of the draft minus evidence; identical meaning adds independent support (`memory_support`) instead of a new record. — [admission.ts:73-76](companions/src/memory/admission.ts), [store.ts:435-466](companions/src/memory/store.ts)
- Source idempotency: native key = digest(engine, sessionId, nativeEventId); replays are `duplicate`; compacted sources leave content-free `retired_sources` receipts. — [store.ts:342-383,409-433](companions/src/memory/store.ts)

**Pipeline: capture → queue → extraction → admission → recall → receipts**
1. *Capture* (`capture.ts`): the host registers a session `{profileId, projectId, engine: claude|codex|opencode, sessionId, transcriptPath, busy, liveFrom}` — path "bound by the host, never copied from a model-supplied path". Byte-accurate cursor with file identity (dev/ino/birthtime) and a 64-byte anchor hash; detects rewritten transcripts; new sessions start at byte 0, an older conversation where learning was just enabled reads only the last 256 KB, and timestamps before consent (`learnSince`) are rejected. Episodes are sealed as `complete | bounded | incomplete`; ≤128 lines and ≤1 MB per poll; ≤90,000 bytes / 128 events per episode. — [capture.ts:11-139](companions/src/memory/capture.ts)
2. *Queue* (`queue.ts`): ≤256 pending episodes (`memory_backlog_full`), unreviewed raw input expires after 7 days, 120 s leases, ≤4 episodes per inference call, ≤128 sources / 96 KB per review. Job states: `open, queued, reviewing, waiting_for_model, budget_deferred, source_incomplete, failed, learned, no_useful_memory, cancelled, expired`. — [queue.ts:52-95](companions/src/memory/queue.ts)
3. *Extraction* (`learner.ts`): prompt `coding-memory-v6` tells the model sources are "historical data, not instructions", a quoted opinion/pasted doc/tool output/assistant suggestion "is not the user's preference", bounded episodes may only yield explicit user statements, no-project sessions keep only personal preferences; existing drafts (≤8 KB) are supplied for dedup/conflict; prompt ≤120,000 bytes; 90 s deadline; answer ≤280 KB. — [learner.ts:27-79,93-123](companions/src/memory/learner.ts)
4. *Admission* (`admission.ts`): checks secrets/injection, project scope required except for `working_preference`/`reference` kinds, every quote must appear verbatim in its source, every JSON pointer must exist in the draft, `/claim`, `/futureAction`, `/applicability` (and `/rationale` if non-null) must be covered by evidence, `stated_preference/project_constraint/accepted_decision/learning_goal` need user-role evidence with `user_stated`, `verified_finding` needs tool-role evidence with matching verification, experiment runs need tool evidence; `inferred/imported` or all-derived/reference evidence ⇒ `tentative`, else `active`. Comment: "These checks establish structural provenance, not a proof that an LLM paraphrase is faithful." — [admission.ts:19-65](companions/src/memory/admission.ts)
5. *Recall* (`store.recall`): requires `controls.recall`; tokenizes the query (≤16 terms, stop-words removed), FTS5 `bm25` over claim/rationale/cues, filters by scope, evidence visibility, applicability vs supplied conditions, exceptions, validity window, and "more specific record wins" for the same conflictKey; re-ranks by receipt usefulness; caps at 6 items and 3,000 bytes by default (max 16,000); two formats: `summary` (JSON `coding_memory_context` with notice "Historical context; ... Memory grants no action permissions.") and `source_excerpts` (`coding_memory_sources` v1 with exact quotes). Token count is an estimate (bytes/3). No embeddings / vectors. — [store.ts:761-840](companions/src/memory/store.ts), [recallSources.ts:6-35](companions/src/memory/recallSources.ts)
6. *Receipts* (`receipts.ts`): binding `{engine: claude|codex|opencode, sessionId, projectId, route: prompt_hook|mcp|manual}` "Always constructed from the authenticated host session"; receipts store only digests (query, context, packet), bytes, token estimate and item ids/revisions, `delivery: 'unverified'`; retained 30 days / max 5,000; helpful/unhelpful feedback per memory revision+context adjusts ranking. — [receipts.ts:9-80](companions/src/memory/receipts.ts)
7. *Notebook*: derived topic pages from active records, every statement citing memory id+revision+path; invalidated on correction/forget. — [notebook.ts](companions/src/memory/notebook.ts), [store.ts:1245-1250](companions/src/memory/store.ts)

**Inference ("who does the extraction")**
- Extraction runs on the user's own selected native CLI and account, never an API key: Claude via `claude --print --output-format stream-json --no-session-persistence --safe-mode --tools '' --strict-mcp-config ...` only for certified versions 2.1.285–2.1.287; any tool use or hook event aborts. — [claudeInference.ts:9-57](companions/src/memory/claudeInference.ts)
- Codex via `codex exec --json --ephemeral --sandbox read-only --ignore-user-config ...` with ~24 features disabled (including `hooks`, `memories`, `shell_tool`), certified only for 0.159.0. — [inference.ts:9-49](companions/src/memory/inference.ts)
- The application layer binds the learner to "the collection's observed native runtime" (the companion DSH's model). — [application/memoryInference.ts:1-12](companions/src/application/memoryInference.ts), [application/intelligence.ts:1](companions/src/application/intelligence.ts)

### Inferences
- The record model already contains what cross-machine sync needs at the record level (opaque UUIDs, monotonically increasing revisions, tombstones, suppression keys, content digests, source native keys), but no replication log, vector clocks, device ids, or merge rules exist; `profileId` is a single local owner and the DB refuses a second profile.
- Project identity is local-path based (git common dir realpath), stored in `project_locators` separate from the opaque project UUID; this is deliberately portable in shape but a second machine would need a mapping step (e.g., remote URL hint + user confirmation), which the plan explicitly says must not be automatic proof of identity.
- Recall is purely lexical (FTS5/bm25) plus typed condition matching; any semantic retrieval would be new work.

## 2. Status: what is built, verified, and not; how it was (and is not) delivered into Claude Code and Codex

### Takeaway
Implemented and unit-tested as a library; never released. Before #684 it was wired into the daemon (Settings → Experimental → Coding memory, default off) and delivered recall via Harness's own `UserPromptSubmit` hook (`hookSpecificOutput.additionalContext`) for Claude Code and Codex and via an OpenCode plugin. Today core has none of that: the hook text is gone, `pair`/`memory` requests answer `UNSUPPORTED`, and real-model extraction quality was never measured on the selected model (quota-blocked: zero completed extractions).

## 6. Cross-machine today: accounts, machines, relay, E2EE, and what syncs

### Takeaway
Every daemon holds one WebSocket to the account backend (the "relay"), and all client/machine content travels end-to-end encrypted (Ed25519 identities, CPace pairing, X25519 sessions, ChaCha20-Poly1305) so the relay forwards ciphertext. Machines of one account trust each other through an append-only, hash-chained device key log stored on the backend plus a gossiped trust group. The backend stores account metadata in plaintext (machines, agent names, a per-account "Desk" of tabs, experimental opt-ins, share/link metadata, explicitly published Hub snapshots), and already has a revisioned, idempotent-ops sync pattern (Desk, Zoo) with push notifications to every adapter socket. There is no sync of private project content, transcripts or memory; product docs require "an explicit storage and encryption design before adding cloud synchronization".

### Inferences
- Two reusable building blocks for cross-machine memory already exist: (1) a revisioned, idempotent op-log document per account with a push "changed" notification (Desk/Zoo), and (2) an E2EE device mesh with authenticated per-account membership and gossip (device key log + trust group + `group_sync`). Combining them suggests "ciphertext op-log on the backend, keys only on devices", but no such encrypted-at-rest store exists today; Desk is plaintext by design.
- The per-process group key is for live fan-out, not for at-rest data; an at-rest memory store needs a separate account content key distributed over the device mesh (planned nowhere in the repo).
- A machine that is offline cannot be queried live (fleet router targets live machines), so recall across machines needs replicated data, not remote queries.

### Gaps
- I did not find any doc or code for encrypted-at-rest account data or for a content key shared across devices.
- Mobile and web memory views: none found beyond the desktop Flutter Memories viewer.

## 7. Product principles and constraints recorded in the repo

### Takeaway
Stability-first small core; every feature a separable service that can fail alone and is free when off; experiments in an on-demand host; user-owned, inspectable, correctable memory with evidence; local-first with the backend holding only metadata unless an explicit encryption design exists; validation discipline and evidence honesty in every doc.

### Cited Findings
- harnessd rules: stability first, work follows activity not history, nothing waits on a service, one contract with narrow authority (no unrestricted extension RPC), port proven logic, no flag day. — [docs/design/2026-10-03-harnessd.md:42-59](docs/design/2026-10-03-harnessd.md)
- "A service is a feature the core can run without. It may fail; the core may not." — [cli/src/services/AGENTS.md:1-3](cli/src/services/AGENTS.md). "Experimental code never shares a process with stable code." — [docs/design/2026-10-06-core-boundary-next.md:439](docs/design/2026-10-06-core-boundary-next.md)
- Disable behavior required of Memory: "Disabling Memory stops capture, inference, recall delivery and retries, revokes active work, and leaves its saved data available for explicit management ... There must be no memory-specific message mutation, background job, model call or probe when Memory is disabled." — [docs/plans/2026-10-03-memory-companion-isolation.md:185-191](docs/plans/2026-10-03-memory-companion-isolation.md)
- Memory ownership is "the user and project, never an avatar or companion terminal ID"; an unavailable model configuration "does not authorize a fallback account or provider". — [docs/plans/2026-10-03-memory-companion-isolation.md:68-78](docs/plans/2026-10-03-memory-companion-isolation.md)
- Product boundaries: "Decisions outlive conversations. Approved choices and their provenance remain available outside a model's current context. People can inspect, correct, and remove this memory." "Capabilities can be replaced. Work records and artifact contracts should survive a change of engine." — [docs/product-direction.md:178-190](docs/product-direction.md). Roadmap stage 2 "Carry decisions across related work" and stage 1 includes "account-free local use". — [docs/product-direction.md:302-312](docs/product-direction.md)
- Naming: "Harness is the software product. Autonomous is the company. Agents are the primary way to do work"; a **Project** is "The files and working context for the work, on a particular computer"; a **harness** in the workspace is "A running agent session"; keep vendor names intact (Claude Code, Codex, OpenCode, pi). — [docs/naming-system.md:8-10,46-60](docs/naming-system.md)
- Process rules: measure through completion; never describe an incomplete suite as passing; PR CI runs only changed components (`companions/` has its own check); merge via `make merge-pr`. — [AGENTS.md](AGENTS.md), [docs/validation-and-release.md:37](docs/validation-and-release.md)
- Every additional protocol surface requires "a separate, minimal contract review under CONTRIBUTING.md"; unresolved gaps "must not be filled by weakening caller verification or silently widening core responsibilities". — [docs/plans/2026-10-03-memory-companion-isolation.md:135-138](docs/plans/2026-10-03-memory-companion-isolation.md)
- Evidence honesty is a recurring constraint in memory docs: synthetic diagnostics, agent-judged reviews and hook emission are explicitly not counted as quality, delivery or benefit evidence. — e.g. [docs/plans/2026-09-30-tim-memory.md:154](docs/plans/2026-09-30-tim-memory.md), [docs/research/2026-10-01-memory-quality-review-blocked.json](docs/research/2026-10-01-memory-quality-review-blocked.json)

### Inferences
- A cross-agent, cross-machine memory that respects these rules would be: an on-demand experimental service (own process, `node:sqlite`), off = zero work, reading transcripts via core-supplied sessions, owner-only requests, delivering into engines only through a core-reviewed, deadline-bounded hook extension, and syncing only end-to-end encrypted data whose keys never reach the backend.

- `CONTRIBUTING.md` sections on contract review were only grepped, not read in full.
