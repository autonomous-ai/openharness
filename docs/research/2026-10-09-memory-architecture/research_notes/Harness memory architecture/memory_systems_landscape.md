# Memory systems landscape for LLM agents (as of 2026-10-09)

Research notes compiled 2026-10-09. All GitHub star/licence/release numbers were read from the GitHub REST API on 2026-10-09 unless stated otherwise; stars are a popularity signal, not a quality signal. "Self-reported" means the number comes from the vendor that builds the system; "independent" means a party with no product in the comparison.

## Key question 1: Architectures, data models and write / consolidation / retrieval / forgetting pipelines

### Takeaway
Every leading system now does LLM work on the write path (fact extraction, entity resolution, conflict handling) and hybrid retrieval (vector + BM25 + entity/graph, sometimes temporal) on the read path. They differ mainly in (a) whether stale facts are overwritten, invalidated with time bounds, or simply accumulated and down-ranked, (b) whether provenance back to raw episodes is kept, and (c) whether memory is an external service the agent queries or files the agent edits itself (Letta MemFS, Basic Memory, Anthropic memory tool).

### Cited Findings

**Mem0 (OSS library + self-hosted server + Mem0 Platform)**
- 2025 paper design (arXiv 2504.19413, 2025-04-28): extraction phase takes an asynchronously refreshed conversation summary, the last m=10 messages and the new message pair, and an LLM extracts candidate facts; update phase retrieves the top s=10 similar memories and the LLM picks ADD / UPDATE / DELETE / NOOP via a tool call. Mem0 and Mem0g used GPT-4o-mini for memory operations. — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)
- Mem0g (graph variant) stores entity nodes and relationship triplets in Neo4j; an LLM conflict detector plus update resolver marks outdated relationships invalid instead of deleting them. — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)
- 2025 paper latency (LoCoMo, seconds p50/p95): Mem0 search 0.148/0.200, total 0.708/1.440; Mem0g search 0.476/0.657, total 1.091/2.590; Zep (as run by Mem0) search 0.513/0.778, total 1.292/2.926; full context total 9.870/17.117; LangMem search 17.99/59.82. Memory footprint per conversation: Mem0 ~7k tokens, Mem0g ~14k, Zep >600k (as measured by Mem0), raw conversation ~26k. — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)
- April 2026 "new algorithm": single-pass, ADD-only extraction (one LLM call, no UPDATE/DELETE, memories accumulate), agent-confirmed facts stored as first-class memories, entity linking across memories, and parallel semantic + BM25 + entity-match retrieval fused into one ranking, plus time-aware retrieval. The README says published scores come from the managed Platform "with proprietary optimizations" and OSS users should expect "directionally similar gains but not identical numbers". — [mem0 GitHub README](https://github.com/mem0ai/mem0)
- Mem0 research page: ~6,900-7,000 mean tokens per retrieval call vs "25,000+" for full context; temporal classification at write time and reranking that favours current information; "memory decay" as fire-and-forget recency ranking. — [Mem0 research](https://mem0.ai/research); [Mem0 benchmark guide](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)
- Note the design reversal: the 2025 paper's selling point was LLM-decided UPDATE/DELETE; the 2026 algorithm drops it in favour of append-only plus retrieval-time recency/temporal ranking. — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1); [mem0 GitHub README](https://github.com/mem0ai/mem0)
- Deployment tiers: pip library (no dashboard/auth), self-hosted Docker Compose server (dashboard, auth, "teasers" of advanced features), cloud Platform (all features). — [mem0 GitHub README](https://github.com/mem0ai/mem0)

**Zep / Graphiti (temporal knowledge graph)**
- Zep paper (arXiv 2501.13956, 2025-01-20). Graphiti has three subgraphs: episodes (raw messages/text/JSON stored losslessly, linked to the entities they mention), semantic entities and fact edges, and communities (label propagation clusters with summaries, updated incrementally). — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)
- Write path: an LLM extracts entities from the current message plus the previous 4 messages (speaker always extracted, reflexion-style pass to reduce hallucinations); candidate duplicates are found by 1024-d name embeddings plus full-text search and an LLM decides whether to merge; facts are extracted between entities and deduplicated only against edges between the same entity pair; graph writes use predefined Cypher, not LLM-generated queries. — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)
- Bi-temporal model: event time (t_valid, t_invalid) and transaction time (t'_created, t'_expired). An LLM compares new edges with semantically related existing edges; on a temporally overlapping contradiction the old edge's t_invalid is set to the new edge's t_valid. Graphiti "consistently prioritizes new information" when invalidating. Superseded facts stay as history. — [Zep paper HTML](https://arxiv.org/html/2501.13956v1); [Graphiti README](https://github.com/getzep/graphiti)
- Retrieval: cosine, BM25 and breadth-first graph search (n hops, can be seeded from recent episodes); rerankers RRF, MMR, episode-mentions, node distance, and a cross-encoder (most expensive). — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)
- Provenance: each derived fact links back to its source episode. — [Graphiti README](https://github.com/getzep/graphiti)
- Graphiti backends: Neo4j 5.26, FalkorDB (incl. embedded FalkorDB Lite), Amazon Neptune (+ OpenSearch Serverless), Kuzu (deprecated). Needs an LLM that supports structured output; OpenAI default; Anthropic, Gemini, Groq, Ollama/OpenAI-compatible supported; smaller models may produce invalid schemas. SEMAPHORE_LIMIT defaults to 10 concurrent operations to avoid LLM 429s. Ships an MCP server. Custom entity types via Pydantic. — [Graphiti README](https://github.com/getzep/graphiti)
- Zep Cloud adds users/threads/message storage, a proprietary "Context Graph Engine" (no third-party graph DB), sub-200 ms retrieval claim, dashboard, SDKs (Python/TS/Go), managed or in-your-cloud deployment. — [Graphiti README](https://github.com/getzep/graphiti)
- Zep paper LongMemEval_S latency: 2.58 s (gpt-4o) / 3.20 s (gpt-4o-mini) with ~1.6k context tokens vs 28.9 s / 31.3 s with 115k-token full context. — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)

**Letta (MemGPT lineage): memory blocks, sleep-time agents, MemFS / Context Repositories**
- Memory blocks: labelled sections of the context window with a character limit; blocks can be shared between agents. — [Letta sleep-time docs](https://docs.letta.com/guides/agents/architectures/sleeptime)
- Sleep-time agents (shipped Letta 0.7.0, docs mark experimental): a background agent gets the core-memory editing tools instead of the primary agent, reflects on conversation history/files and writes "learned context" into blocks other agents read. Research basis: "Sleep-time Compute" arXiv 2504.13171. — [Letta sleep-time docs](https://docs.letta.com/guides/agents/architectures/sleeptime); [Letta sleep-time blog](https://letta.com/blog/sleep-time-compute)
- Context Repositories / MemFS (announced 2026-02-12): agent memory is a git repo cloned to the local filesystem; every change is a commit; files under `system/` are always loaded into the prompt, other files are read on demand; the file tree and per-file frontmatter descriptions are always in the prompt (progressive disclosure); agents use bash/Unix tools on memory. Subagents each get an isolated git worktree so several can write memory concurrently and merge back via git conflict resolution; sleep-time reflection runs in its own worktree. A "defragmentation" skill backs up then reorganises memory into 15-25 focused files. No benchmark numbers in the post. — [Letta Context Repositories blog](https://www.letta.com/blog/context-repositories/)
- Current docs: "MemFS, a git-backed memory filesystem"; `/remember` commits a lesson; `/init` bootstraps memory, can mine prior Claude Code / Codex histories via subagents; `/doctor` audits placement, duplication, prompt-token use; "dreaming" background subagents consolidate after N agent steps or on context compaction, with optional second-pass review. — [Letta memory docs](https://docs.letta.com/configuration/memory)
- MemFS has no vector index by default; an optional search mod adds keyword/semantic/hybrid retrieval (third-party summaries; treat as lower-confidence). Cloud agents sync the repo; local-only agents keep it on one machine. — [Letta docs-md mirror](https://github.com/letta-ai/letta-docs-md/blob/main/configuration/memory/index.md); [Meshnote write-up](https://meshnote.io/blog/letta-code-memory)
- The old Letta V1 API server is retired to an `archive` branch; Letta Code (`letta-ai/letta-code`) is the current centre: agent harness, TUI, app server, desktop/web runtime. — [letta GitHub README](https://github.com/letta-ai/letta)

**Hindsight (vectorize-io): retain / recall / reflect**
- Paper: "Hindsight is 20/20" arXiv 2512.12818 (Vectorize.io with The Washington Post and Virginia Tech). Memory bank = four logical networks: world facts, experience (agent's own actions), opinions/beliefs (with confidence in [0,1] and formation timestamp), observations (LLM-synthesised entity profiles). Components: TEMPR (retain+recall) and CARA (reflect). — [Hindsight paper HTML](https://arxiv.org/html/2512.12818v1)
- Memory unit: id, bank id, narrative text, embedding, occurrence interval (start/end), mention timestamp, fact type, optional confidence, metadata. Typed weighted edges: temporal (exponential decay), semantic (cosine threshold), entity, causal (LLM-extracted: causes / caused_by / enables / prevents). — [Hindsight paper HTML](https://arxiv.org/html/2512.12818v1)
- Retain path (several LLM calls): coarse-chunk fact extraction into 2-5 narrative facts with coreference resolution, absolute time normalisation, participant attribution, fact-type classification, entity extraction; entity resolution by string similarity + co-occurrence + temporal proximity; causal link extraction; opinion reinforcement (LLM labels reinforce/weaken/contradict/neutral and adjusts confidence by a fixed step); background merge; asynchronous observation regeneration. The paper does not spell out how world/experience facts are superseded. — [Hindsight paper HTML](https://arxiv.org/html/2512.12818v1)
- Recall: four parallel channels (pgvector HNSW semantic, BM25 via GIN full-text, graph spreading activation, temporal interval filter with rule parser + flan-t5-small fallback) fused by RRF (k~60), reranked by cross-encoder ms-marco-MiniLM-L-6-v2, packed to a token budget. Reflect: recall + a profile with disposition parameters (skepticism, literalism, empathy) and bias strength, can form new opinions. No latency/cost numbers in the paper. — [Hindsight paper HTML](https://arxiv.org/html/2512.12818v1)
- Product (README, 2026-10): observations are consolidated deduplicated beliefs that keep supporting evidence and a proof count; "mental models" are standing answers rewritten in the background, read with no LLM call; "knowledge pages" exportable as markdown; per-bank isolation; MCP endpoint per bank; Postgres+pgvector or Oracle 23ai; embedded mode, Docker, Helm, Hindsight Cloud; 25+ LLM providers incl. local Ollama/LM Studio/llama.cpp. — [Hindsight GitHub README](https://github.com/vectorize-io/hindsight)

**Supermemory**
- Pitched as a universal memory API that extracts structured memories from files, docs, chats and email and builds a knowledge graph. — [TechCrunch-derived coverage via Dealroom](https://nz.dealroom.co/news/feed/supermemory-secures-2-6m-for-ai-memory)
- Docs: a "learning model" decides what to learn / forget / relate, stored in a "fact-based temporal graph that has Vector, FTS, and graph built in". Documents (chats, PDFs, media, code, URLs, Drive/Notion/Gmail connectors) go Queued -> Extracting -> Chunking (contextual chunking) -> Embedding -> Indexing; a second "dreaming" phase extracts/merges memories (`dynamic` mode groups related documents and may continue after status `done`; `instant` mode costs one extra operation per document). Outputs in one namespace: chunks (RAG grounding), memories (facts incl. updates, links, derived facts), and a static + dynamic profile for always-on context. Namespaces are hard isolation boundaries; scoped API keys cannot cross them. — [Supermemory docs: how it works](https://supermemory.ai/docs/concepts/how-it-works)
- Memory relations: `updates` (new fact replaces the old for search; history can remain for audit), `extends` (both valid), `derives` (inferred facts never stated). `isLatest` keeps retrieval on the current fact. Facts persist until updated; preferences strengthen with repetition; episodes decay unless significant; time-bound facts expire; casual chatter is filtered. No documented field linking a memory to its source document. — [Supermemory docs: graph memory](https://supermemory.ai/docs/concepts/graph-memory)
- Research page (May 2026) reports retrieval metrics only (Recall@20 with aggregation) and does not describe the engine's internals. — [Supermemory research](https://supermemory.ai/research)

**Cognee (topoteretes)**
- Turns documents, code and conversations into a self-hosted knowledge graph (entities, relationships, searchable chunks; code becomes a symbol/dependency graph; custom data models and ontologies supported). Current API verbs: `remember` (permanent, or session-scoped with a session id), `recall` (auto-routed graph / vector / code retrieval, hybrid), `improve` (enrich, apply feedback, promote session knowledge into the graph), `forget` (an item or a dataset). — [Cognee README](https://github.com/topoteretes/cognee)
- Write path: with no API key, extraction uses the local GLiNER model and a local embedding model ("Runs locally for free - no API key required"); with a key, OpenAI by default, Ollama supported; LLM-dependent improvement stages are skipped without an LLM. Postgres option combines relational metadata + pgvector + graph state (graph-on-Postgres labelled demo). Multi-tenant by default (every API call needs an authenticated user); MCP server; managed Cognee Cloud. Only benchmark on the README: BEAM 0.79 at 100K tokens (20 questions, 4 rounds) and 0.67 at 10M (exploratory). — [Cognee README](https://github.com/topoteretes/cognee)

**LangMem (LangChain)**
- Each memory operation: LLM takes conversations + current memory state and returns an expanded/consolidated state. Types: semantic (as a searchable *collection* that must be reconciled by delete/invalidate/update, or a schema-bound *profile* updated in place), episodic (past successful interactions with reasoning), procedural (system instructions refined by a prompt optimizer). Formation on the hot path (immediate, adds latency) or in the background (delayed, no latency). Storage via LangGraph BaseStore with hierarchical namespaces templated by `{user_id}`; retrieval by key, semantic search or metadata filter. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Mem0's paper measured LangMem search latency at 17.99 s p50 / 59.82 s p95 on LoCoMo, by far the slowest system tested (Mem0's harness, not independently reproduced). — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)

**MemOS (MemTensor)**
- Paper (arXiv 2507.03724, v1 2025-07-04, v4 2025-12-03, 39 authors): MemCube as the unit that "encapsulates both memory content and metadata such as provenance and versioning"; unifies plaintext, activation-based and parameter-level memory. — [MemOS arXiv](https://arxiv.org/abs/2507.03724)
- 2026 product (v2.x): graph-structured memory behind one add/retrieve/edit/delete API; multimodal; composable "memory cubes" isolated or shared per user/project/agent; async MemScheduler; "Memory Feedback & Correction" via natural language; self-host needs Neo4j + Qdrant; a local plugin uses on-device SQLite with FTS5 + vector hybrid search; cloud plugin claims multi-agent memory sharing. Self-reported scores via its own "OmniMemEval": LoCoMo 88.83, LongMemEval 89.20, PersonaMem v2 40.58, HaluMem 80.91, BEAM-10M 56.75; "35.24% token savings" and "72% lower token usage" without methodology. — [MemOS README](https://github.com/MemTensor/MemOS)

**A-MEM (agentic Zettelkasten memory, research prototype)**
- arXiv 2502.12110 (first 2025-02-17, v11 2025-10-08, NeurIPS 2025): each memory becomes a note with contextual description, keywords and tags; links are generated to similar historical notes; adding a note can rewrite the context/attributes of existing notes ("memory evolution"). — [A-MEM arXiv](https://arxiv.org/abs/2502.12110)
- Mem0's paper scored A-Mem 48.38 overall J on LoCoMo (lowest of the memory systems it ran). — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)

**Memobase (memodb-io)**
- User-profile memory: profile slots by topic/sub-topic plus a per-user event timeline. Chats go into a per-user buffer and are processed in batches when the buffer reaches ~1024 tokens, sits idle ~1 hour, or `flush()` is called; processed blobs are deleted by default. v0.0.40 fixed LLM calls per flush at 3 (from ~3-10), claimed 40-50% token-cost cut; profile/event reads claimed <100 ms via "only few SQL operations"; context search depends on the embedding API (500-1000 ms). FastAPI + Postgres + Redis, MCP server, cloud free tier. — [Memobase README](https://github.com/memodb-io/memobase)
- Hindsight's paper lists Memobase at 75.78% on LoCoMo (copied from reports, not reproduced). — [Hindsight paper HTML](https://arxiv.org/html/2512.12818v1)

**MIRIX**
- arXiv 2507.07957 (2025-07-10, Yu Wang and Xi Chen): six memory types - Core, Episodic, Semantic, Procedural, Resource, Knowledge Vault - managed by a multi-agent framework; packaged app monitors the screen and stores data locally. Claims: ScreenshotVQA +35% accuracy vs RAG with 99.9% less storage; LoCoMo 85.4% (self-reported). — [MIRIX arXiv](https://arxiv.org/abs/2507.07957)
- Independent MemoryAgentBench: MIRIX 26.2 (GPT-4o-mini) / 37.7 (GPT-4.1-mini) overall, below long-context baselines (~47-50) and BM25 (41.5). — [MemoryAgentBench HTML](https://arxiv.org/html/2507.05257v3)

**Basic Memory (basicmachines-co)**
- Markdown files are the source of truth ("Plain text on your disk. Forever."); a local SQLite index (or Postgres, optional Milvus) gives hybrid full-text + vector search with FastEmbed; optional cross-encoder rerank off by default. Each file is an entity with YAML frontmatter (title, type, permalink, tags); observations are bullets `- [category] fact #tag (context)`; relations are wikilinks `- requires [[Target]]`. MCP tools: write/read/edit/move/delete_note, search_notes, recent_activity, build_context over `memory://` URLs, project tools, schema_infer/validate/diff. Humans edit the same files (works in Obsidian). Local installs can run air-gapped; cross-device sync for local is manual (git, Syncthing); paid cloud ($15-19/month) gives bidirectional rclone-based sync with conflict resolution, backups and snapshots. No LLM on the write path: the calling agent writes the notes. — [Basic Memory README](https://github.com/basicmachines-co/basic-memory)

**MCP reference memory server (modelcontextprotocol/servers, src/memory)**
- Knowledge graph of entities (name, entityType, observations[]) and directed relations (from, to, relationType, active voice); stored in one JSONL file (`MEMORY_FILE_PATH`). Nine tools: create_entities, create_relations, add_observations, delete_entities (cascades), delete_observations, delete_relations, read_graph, search_nodes (over names, types, observation text), open_nodes. Self-described "a basic implementation"; no documented concurrency, encryption, size limits, embeddings, or temporal validity. The suggested prompt has the model retrieve at chat start and save identity / behaviours / preferences / goals / relationships. — [MCP memory server README](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)

**Mastra Observational Memory (major 2026 entrant, not on the original list)**
- 2026-02-09: two background agents - an Observer (triggered when unobserved messages pass a token threshold, default 30,000) and a Reflector (triggered by total observation size) that restructures and dedupes without summarising. Observations are plain dated bullet logs with emoji priorities and up to three dates (observed, referenced, relative). No per-turn retrieval: the context is a stable, append-only, prompt-cacheable log (~30k tokens average in the benchmark; ~3-6x text compression, 5-40x claimed for tool-heavy work). — [Mastra research](https://mastra.ai/research/observational-memory)

**Anthropic native memory (baseline)**
- Claude API memory tool `memory_20250818`: client-side; Claude issues view / create / str_replace / insert / delete / rename on paths under `/memories` and the application executes them on storage it controls (files, DB, encrypted files). The API injects "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE ... ASSUME INTERRUPTION" into the system prompt. Available on all Claude 4+ models. Docs make path-traversal checks, size caps, sensitive-data stripping and expiry the developer's responsibility. Pairs with context editing (client-side tool-result clearing) and server-side compaction. — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Launch 2025-09-29 with context editing: internal agentic-search eval +39% (memory tool + context editing) and +29% (context editing alone) over baseline; in a 100-turn web search eval context editing cut token use by 84% (vendor numbers). — [Claude blog: context management](https://claude.com/blog/context-management)

**OpenAI native memory (baseline)**
- Agents SDK: built-in Sessions persist conversation history (SQLite, Redis, Dapr backends) for working context; long-term memory notes are a developer-built cookbook pattern (Jan 2026). An OpenAI cookbook describes a sandbox `Memory()` capability storing reusable workflow lessons under `memories/` and `sessions/` in the workspace. — [Agents SDK sessions](https://openai.github.io/openai-agents-python/sessions/); [OpenAI cookbook: long-term memory notes](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization); [OpenAI cookbook: memory and compaction](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)
- ChatGPT memory (consumer): a December 2025 reverse-engineering by conversational probing (not code inspection) reports no vector DB/RAG over history; instead layers of session metadata, explicit saved user facts, lightweight conversation summaries and a sliding window are injected into the prompt. Another author argues chat-history reference behaves like opaque retrieval. Neither is confirmed by OpenAI. — [Gigazine summary](https://www.gigazine.net/gsc_news/en/20251226-reverse-engineered-chatgpt-memory-system); [Digit](https://www.digit.in/features/general/how-chatgpt-memory-works-without-rag-indian-guy-unravels-the-secret-in-amazing-detail.html); [j0lian Substack](https://j0lian.substack.com/p/field-notes-from-working-with-a-semi)
- OpenAI's built-in memory scored 52.90 on LoCoMo in Mem0's harness (lowest non-research system). — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)

### Inferences
- The field has converged on "LLM on write, hybrid retrieval on read". The real design choices are update semantics (overwrite vs invalidate-with-time vs append-and-rank) and whether provenance to raw episodes survives. Graphiti is the clearest about both (bi-temporal edges + episode links); Mem0's 2026 algorithm gave up explicit update/delete.
- Letta has moved from "memory as a server-side block store" to "memory as a git repo of Markdown files the agent edits", which is architecturally closer to Basic Memory / CLAUDE.md / Anthropic's memory tool than to Mem0/Zep.
- Two families are now clear: (1) *memory services* that run their own LLM extraction on every write and expose search (Mem0, Zep/Graphiti, Hindsight, Supermemory, Cognee, MemOS, Memobase), and (2) *agent-edited files* where the working model itself decides what to write and reads files on demand (Letta MemFS, Anthropic memory tool, Basic Memory, MCP memory server, Claude Code CLAUDE.md, Manus). Mastra's observational memory is a third shape: background LLM summarisation into an append-only log that is always in context, no retrieval.
- Provenance is strongest in Graphiti (fact -> source episode) and Hindsight observations (supporting evidence + proof count); weakest in Mem0 and the MCP server, which store extracted facts without documented source links.

### Gaps
- Per-write cost (LLM tokens per ingested message) is rarely published; only Mem0 (tokens per retrieval), Zep (context tokens) and Memobase (3 LLM calls per flush) give figures, and mostly for reads.
- Supermemory internals beyond its docs (e.g. models used, how `derives` facts are validated) are not public.
- MemOS paper details (MemScheduler, parametric memory in practice) were only read at abstract level.

## Key question 2: Benchmarks (LoCoMo, LongMemEval, BEAM, MemoryAgentBench, DMR), disputes, independent evaluations

### Takeaway
Vendor leaderboards are not comparable: different answer models, judges, category exclusions and retrieval budgets. LoCoMo's answer key is ~6% wrong with a ~93.6% ceiling, and its gpt-4o-mini judge accepts ~63% of deliberately wrong-but-on-topic answers, so 2026 claims above ~93% on LoCoMo are not credible as stated. Independent work (MemoryAgentBench, ICLR 2026) puts Mem0, Zep, Cognee and MemGPT below long-context models and plain BM25 overall, and Letta showed a grep-over-files agent beating Mem0's own LoCoMo numbers.

### Cited Findings

**DMR (Deep Memory Retrieval, from MemGPT)**
- Zep 94.8% vs MemGPT 93.4% (gpt-4-turbo); full conversation 94.4% (gpt-4-turbo); with gpt-4o-mini, full conversation 98.0% vs Zep 98.2%. Zep's own paper says DMR is inadequate: ~60-message conversations fit in context, single-turn fact questions, ambiguous phrasing. — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)

**LoCoMo**
- Mem0 paper (2025-04) LoCoMo J scores: full context 72.90, Mem0g 68.44, Mem0 66.88, Zep 65.99, best RAG 60.97, LangMem 58.10, OpenAI memory 52.90, A-Mem 48.38. The adversarial category was excluded "because it lacks ground-truth answers". Note full context beat every memory system. — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)

Multi-hop selective forgetting: every method at most 7%. — [MemoryAgentBench HTML](https://arxiv.org/html/2507.05257v3)

**Other independent / academic evaluations (2026)**
- "When Does Memory Help?" (MERIT, arXiv 2609.05441, submitted 2026-07-26): on dependent tool-use tasks memory lifts success from 0.00 to 0.55-1.00; embedding retrieval is unreliable on updated facts (0.30-0.95, seed gap up to 0.45; agents act on a correctly retrieved value only 55% of the time); update-on-write fact stores and LLM summarisation hold 0.70-1.00; a hybrid of the two is worse than the fact store alone; swapping implementations moves success by up to 60 points; full replay is never cost-effective. — [arXiv 2609.05441](https://arxiv.org/abs/2609.05441)
- "Ground Truth First" (arXiv 2607.21962, 2026-07-24, single author, promotes own library Veracium): synthetic corpus with planted facts with validity intervals; rankings invert with tenure - a curated budgeted map leads at 3 weeks but falls from 96% to 72% recall of evicted content by 9 weeks while a provenance-typed graph rises to 90%; full history ties the best memory at 3 weeks but has no judge-independent advantage at 9 weeks at ~2x read cost; weakly written facts fail 24% vs 2%. — [arXiv 2607.21962](https://arxiv.org/abs/2607.21962)

**Coding-specific memory benchmarks (yes, several, mostly 2026 and small)**
- VibeMemBench (arXiv 2609.23570, 2026-09-20): 111 SWE-style targets from 90 SWE-rebench V2 repos plus 3,634 historical trajectories; targets kept only if injected history helps a reference solver. Directly injecting verified experience raised resolution by 1.1-4.5 points on 4 of 5 solvers and cut steps on all 5; but 11 of 12 pairings of solvers with four existing memory systems (not named in the abstract) did not beat the memory-off baseline. — [VibeMemBench arXiv](https://arxiv.org/abs/2609.23570)
- DreamBench-SWE (arXiv 2608.20664, 2026-08-21, single author, preregistered): later tasks depend on non-inferable evidence from earlier sessions, scored by hidden executable oracles. Pass counts out of 180: no memory 21, verbatim event memory 82, typed-plus-raw probe 83, one hosted Mem0 configuration with literal storage 97; all three beat no-memory after Holm correction; the probe vs verbatim difference was not significant; the author disclaims claims of superiority among memory conditions. — [DreamBench-SWE arXiv](https://arxiv.org/abs/2608.20664)
- SWE Context Bench (arXiv 2602.08316, v3 2026-05-06): 1,100 base + 376 related tasks over 51 repos / 9 languages; accurately summarised and retrieved prior experience improves resolution and cuts runtime/tokens, mostly on harder tasks; unfiltered or wrongly selected context helps little or hurts. — [SWE Context Bench arXiv](https://arxiv.org/abs/2602.08316)
- SWE-Bench-CL (arXiv 2507.00014, 2025): chronologically ordered issue sequences to measure accumulation and forgetting; early pass rates were very low (generally below 8.5%). — [SWE-Bench-CL arXiv](https://arxiv.org/pdf/2507.00014)
- Letta Context-Bench (filesystem and skills suites; grades correctness and path efficiency): leaderboard last updated 2026-02-17 had GPT-5.2-codex-xhigh 83% ($38.75), GPT-5.2-xhigh 83%, Claude Sonnet 4.6 81%, Gemini 3 Flash 80%, Claude Opus 4.6 77%. It measures a model's skill at agentic context management, not a memory product. The launch blog (late 2025) had Sonnet 4.5 at 74.0%, inconsistent with the later leaderboard's 43% for the same model, so scoring likely changed. — [Letta leaderboard](https://leaderboard.letta.com/); [Letta Context-Bench blog](https://letta.com/blog/context-bench)

### Inferences
- Any LoCoMo number above ~93.6% is above the audited ceiling and should be read as judge leniency or non-standard scoring until a public harness proves otherwise.
- The most consistent independent signals: (1) long context or simple BM25 often match or beat packaged memory services on static QA benchmarks; (2) knowledge updates / selective forgetting are the unsolved part; (3) write-time quality matters more than retrieval cleverness.
- LongMemEval_S is close to saturated (memory systems beat an oracle with only the relevant sessions); LoCoMo is noisy and partly broken. BEAM (1M-10M tokens) and task-based benchmarks (MemoryAgentBench, MERIT, coding benchmarks) are where systems still separate.
- For coding agents specifically, the 2026 evidence is: memory of prior sessions helps a lot when later tasks truly depend on non-inferable earlier facts (DreamBench-SWE: 12% -> 46-54%), but generic memory products extracting "experience" from repo history mostly do not beat no-memory (VibeMemBench). Verbatim event logs did about as well as typed/structured memory in DreamBench-SWE.

### Gaps
- No independent reproduction of Hindsight's LongMemEval numbers found; the README's "independent reproduction" by Virginia Tech and The Washington Post involves co-authors of the paper. — [Hindsight GitHub README](https://github.com/vectorize-io/hindsight); [Hindsight paper HTML](https://arxiv.org/html/2512.12818v1)
- No primary Zep source found for the 94.7% LoCoMo figure that Mem0's blog attributes to Zep.
- VibeMemBench's abstract does not name the four memory systems it tested; the full paper would be needed.
- No benchmark found that compares a plain CLAUDE.md/AGENTS.md file against memory products for coding agents.

## Key question 3: Multi-agent writers, multi-user, multi-device sync, encryption, local-first, deletion / right-to-forget

### Takeaway
Multi-user scoping is universal (user/agent/session ids, banks, namespaces, cubes), but a real concurrency model for several agents writing the same memory is rare: Letta's git worktrees + merge is the only explicit one found. Local-first options exist (Basic Memory, Cognee with local models, Hindsight embedded, MemOS local plugin, Graphiti with embedded FalkorDB, the Anthropic memory tool and MCP memory server), but multi-device sync is either a vendor cloud (Letta Cloud, Basic Memory Cloud, Mem0/Zep/Supermemory/Hindsight clouds) or DIY git/Syncthing. Right-to-forget is in tension with designs that keep history: Graphiti invalidates rather than deletes, Supermemory keeps superseded facts "for audit", Mem0 2026 is append-only, and Letta MemFS keeps every edit in git history.

### Cited Findings
**Multi-agent / shared memory**
- Letta: subagents write memory concurrently in isolated git worktrees and merge back through git conflict resolution; before this, memory formation was single-threaded because concurrent writes could not be coordinated. Sleep-time reflection runs in its own worktree. — [Letta Context Repositories blog](https://www.letta.com/blog/context-repositories/)
- Letta memory blocks can be shared between agents; sleep-time agents write "learned context" that other agents read. — [Letta sleep-time docs](https://docs.letta.com/guides/agents/architectures/sleeptime)
- Letta shared memory repos are hosted by Letta (cloud feature); self-hosted setups can share by pointing agents at their own git remote (third-party write-up). — [Meshnote write-up](https://meshnote.io/blog/letta-code-memory)
- MemOS: memory cubes can be isolated or shared per user/project/agent; cloud plugin advertises "multi-agent memory sharing". — [MemOS README](https://github.com/MemTensor/MemOS)
- MIRIX uses a multi-agent framework internally (one manager per memory type), which is about write parallelism inside one user's memory, not shared memory across user agents. — [MIRIX arXiv](https://arxiv.org/abs/2507.07957)
- Graphiti: concurrency is bounded by SEMAPHORE_LIMIT (default 10) to avoid LLM rate limits; "group management" in its MCP server; I found no documentation of locking or ordering guarantees for concurrent episode ingestion within one group. `reference_time` per episode drives temporal placement; `add_episode_bulk` "resolves invalidated edges and extracts temporal dates before it saves". — [Graphiti README](https://github.com/getzep/graphiti); [Graphiti docs: adding episodes](https://help.getzep.com/graphiti/core-concepts/adding-episodes)
- MCP reference memory server: a single JSONL file with no documented concurrency control. — [MCP memory server README](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)

**Multi-user scoping**
- Mem0: memories scoped and deletable by `user_id`, `agent_id`, `run_id`, `app_id`, metadata. — [Mem0 delete docs](https://docs.mem0.ai/core-concepts/memory-operations/delete)
- Hindsight: isolated banks, per-tenant config, MCP endpoint per bank. — [Hindsight GitHub README](https://github.com/vectorize-io/hindsight)
- Supermemory: `namespace` is a hard boundary in the URL; scoped API keys cannot cross namespaces. — [Supermemory docs: how it works](https://supermemory.ai/docs/concepts/how-it-works)
- Cognee: multi-tenant by default (authenticated user on every call), can be switched to single-user. — [Cognee README](https://github.com/topoteretes/cognee)
- LangMem: LangGraph BaseStore namespaces templated with `{user_id}`. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)

**Local-first and multi-device**
- Basic Memory: Markdown on disk, air-gap capable; local cross-device sync is manual (git/Syncthing); paid cloud does bidirectional rclone sync with conflict resolution. — [Basic Memory README](https://github.com/basicmachines-co/basic-memory)
- Letta: cloud-backed agents sync the memory repo to wherever the client runs; local-only agents keep it on one machine and must be backed up. — [Letta docs-md mirror](https://github.com/letta-ai/letta-docs-md/blob/main/configuration/memory/index.md); [Letta Context Repositories blog](https://www.letta.com/blog/context-repositories/)
- Cognee runs without any API key using local GLiNER extraction and local embeddings. — [Cognee README](https://github.com/topoteretes/cognee)
- Hindsight: embedded Python mode with an embedded Postgres, local LLMs via Ollama / LM Studio / llama.cpp. — [Hindsight GitHub README](https://github.com/vectorize-io/hindsight)
- MemOS local plugin: on-device SQLite with FTS5 + vector hybrid search. — [MemOS README](https://github.com/MemTensor/MemOS)
- Graphiti: embedded "FalkorDB Lite" option on Python 3.12+, local LLMs via OpenAI-compatible endpoints (with a warning that small models produce invalid schemas). — [Graphiti README](https://github.com/getzep/graphiti)
- Anthropic memory tool: storage is entirely the application's (per-user directories, DB keys, encrypted files); memory continues across conversations only if the same handler serves the same store. — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

**Encryption, compliance, deletion**
- Zep: SOC 2 Type II; HIPAA BAA for Enterprise; BYOK (encryption at rest with the customer's AWS KMS key, revocable); BYOC (deploy in customer VPC); RBAC/ABAC/audit logs; HIPAA guide says user/thread/graph ids must not contain PII. Deletion/retention details not on the security page. — [Zep security & compliance](https://help.getzep.com/security-compliance); [Zep HIPAA guide](https://help.getzep.com/hipaa-compliance)
- Zep invalidates superseded facts while preserving history and provenance, so old facts remain stored unless explicitly deleted. — [Graphiti README](https://github.com/getzep/graphiti)
- Mem0: compliance claims are inconsistent across its own pages (SOC 2 Type I and "undergoing Type II" vs "SOC 2 Type II" for Enterprise); claims BYOK and on-prem / air-gapped Kubernetes deployment. Treat Type II as unconfirmed. — [Mem0 infosec guide](https://mem0.ai/guide/ai-memory-regulated-workloads-infosec-review); [Mem0 enterprise security guide](https://mem0.ai/guide/enterprise-ai-memory-security-review-options); [Mem0 trust center](https://trust.mem0.ai/)
- Mem0 deletion API: single, batch (up to 1000 ids), and `delete_all` by user/agent/run/metadata, wildcard `"*"` per entity type; no-filter `delete_all` now errors (previously wiped the project). Docs position this for GDPR/CCPA erasure but do not say whether history/backups retain deleted data. — [Mem0 delete docs](https://docs.mem0.ai/core-concepts/memory-operations/delete)
- Cognee has `forget` for an item or dataset. — [Cognee README](https://github.com/topoteretes/cognee)
- Anthropic memory tool docs put sensitive-data stripping, file size caps, and expiry of stale memory files on the developer; Claude "usually refuses" to write sensitive info. — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Supermemory: "updates" keep history "for audit"; explicit forget/review controls documented separately. — [Supermemory docs: graph memory](https://supermemory.ai/docs/concepts/graph-memory)

**Security of shared / persistent memory**
- MINJA (arXiv 2503.03704): an attacker who only sends queries can plant malicious records into an agent's memory bank; reported >95% injection success and >70% attack success across GPT-4o-mini, Gemini 2.0 Flash and Llama 3.1 8B. A January 2026 paper argues these numbers were under idealised conditions. — [MINJA arXiv](https://arxiv.org/abs/2503.03704); [arXiv 2601.05504](https://arxiv.org/abs/2601.05504v1)
- OWASP Top 10 for Agentic Applications 2026 lists ASI06 "Memory & Context Poisoning" (secondary source). — [WorkOS blog](https://workos.com/blog/ai-agent-memory-poisoning)
- "Ground Truth First" tracks whether provenance boundaries survive representation as an injection-resistance measure. — [arXiv 2607.21962](https://arxiv.org/abs/2607.21962)
- A 2026 survey of 435 works finds research concentrates on accumulating and retrieving state rather than governing, recovering or relinquishing it (deletion, rollback, audit). — [Always-On Agents survey, arXiv 2606.30306](https://arxiv.org/abs/2606.30306)

### Inferences
- For a product where several agents (e.g. Claude Code and Codex sessions on several machines) write one memory, the only off-the-shelf pattern with explicit merge semantics is git over Markdown (Letta MemFS / Context Repositories, or Basic Memory files synced by git). Service-based memories serialise through a database and an LLM extraction queue but document no conflict semantics between concurrent writers.
- "Keep history" designs (bi-temporal invalidation, append-only, git) are good for provenance and audit but make right-to-forget a separate, deliberate purge path (including git history rewriting or graph hard-delete); none of the reviewed docs describes purging derived facts when a source episode is deleted.
- Provenance on each memory (source episode, writer, confirmation status) is the main defence recommended against poisoning, and matters more once several agents share a store.

### Gaps
- No system documented end-to-end encryption of memory content where the vendor cannot read it; BYOK at rest (Zep, Mem0 claim) is the strongest found.
- No documentation found on whether deleting a source episode in Graphiti/Zep, Mem0, Supermemory or Hindsight cascades to facts derived from it.
- Hindsight and Supermemory deletion and compliance pages were not reviewed.
- Graphiti's ordering/locking guarantees for concurrent ingestion into one group were not found in docs.

## Key question 5: Expert consensus (late 2025-2026) on what works

### Takeaway
There is no settled winner, but the 2025-2026 evidence and practitioner writing converge on: (1) context engineering first - keep the window small, stable and cacheable, compact and clear tool results, recite goals; (2) agent-driven, just-in-time retrieval with simple tools (files, grep, BM25) is competitive with specialised memory on QA benchmarks; (3) quality on the write path (curated, updated, dated facts with provenance) matters more than retrieval cleverness, and pure embedding similarity is the weakest option for facts that change; (4) background / sleep-time consolidation is now standard across vendors (Letta dreaming, Mastra Reflector, Hindsight observations and mental models, Supermemory dreaming, LangMem background manager) but lacks independent evidence on its own; (5) graphs and temporal validity pay off mainly over long horizons and for knowledge updates, and selective forgetting is still unsolved.

### Cited Findings
**Context engineering (vendor guidance)**
- Anthropic (2025-09-29): context is "a finite resource with diminishing marginal returns" ("context rot"); agents are moving from up-front embedding retrieval to "just in time" loading via lightweight references and tools, with a hybrid (Claude Code drops CLAUDE.md in up front and uses glob/grep just in time); compaction, tool-result clearing as "one of the safest lightest touch forms of compaction"; structured note-taking (NOTES.md, to-do lists, the Pokemon agent keeping notes across context resets); sub-agents returning 1,000-2,000-token distilled summaries. — [Anthropic: effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Anthropic memory tool docs recommend a multi-session software pattern: an initializer session writes a progress log, feature checklist and startup script reference; each later session reads them first and updates the log at the end; mark features done only after end-to-end verification. — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Manus (2025-07-18, Yichao "Peak" Ji): treat "the file system as the ultimate context" with restorable compression (drop page content but keep the URL / path); recite objectives by rewriting todo.md; KV-cache hit rate is the most important production metric (cached Sonnet input $0.30 vs $3/MTok), so keep prefixes stable and context append-only; keep errors in context. — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Mastra's observational memory applies the same cache logic to memory: append-only observation log, no per-turn retrieval, prefix invalidated only on reflection. — [Mastra research](https://mastra.ai/research/observational-memory)
- OpenAI's Agents SDK direction is also file-based: a sandbox `Memory()` capability storing reusable workflow lessons in `memories/` in the workspace, plus sessions and compaction. — [OpenAI cookbook: memory and compaction](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)

**Files / grep vs specialised memory**
- Letta's filesystem agent (GPT-4o-mini + grep/search over a file) scored 74.0% on LoCoMo vs Mem0's reported 68.5%; Letta concludes retrieval success depends on the agent knowing when and how to search, and that comparing memory tools in isolation is hard. — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- MemoryAgentBench: BM25 (41.5 overall) beat Mem0 (21.1), Zep (24.0), Cognee (20.6), MemGPT (28.3); long-context models led (46.9-49.6). — [MemoryAgentBench HTML](https://arxiv.org/html/2507.05257v3)
- Mem0's own 2025 paper had full context (72.90) above every memory system on LoCoMo; the argument for memory there was latency (p95 17.1 s vs 1.4 s) and tokens (~26k vs ~7k), not accuracy. — [Mem0 paper HTML](https://arxiv.org/html/2504.19413v1)
- Major vendors' own native memories are file/document based: Anthropic's memory tool is a `/memories` directory; Letta moved to a git-backed Markdown filesystem; ChatGPT's consumer memory (per outside probing) injects saved facts and summaries rather than doing RAG. — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); [Letta Context Repositories blog](https://www.letta.com/blog/context-repositories/); [Gigazine summary](https://www.gigazine.net/gsc_news/en/20251226-reverse-engineered-chatgpt-memory-system)

**Write-time curation vs raw retrieval**
- MERIT (2026): update-on-write fact stores and LLM summarisation hold 0.70-1.00 on updated facts; embedding retrieval 0.30-0.95 and agents use a correctly retrieved value only 55% of the time; hybrid worse than the fact store alone. — [arXiv 2609.05441](https://arxiv.org/abs/2609.05441)
- "Ground Truth First" (2026): write-stage quality strongly predicts downstream quality (weakly written facts fail 24% vs 2%); curated maps win short horizons, provenance-typed graphs win long horizons (90% vs 72% at 9 weeks). — [arXiv 2607.21962](https://arxiv.org/abs/2607.21962)
- Counterpoint: Mem0 itself moved in April 2026 from LLM-decided UPDATE/DELETE to ADD-only extraction plus retrieval-time recency/temporal ranking and reports large gains (LoCoMo 71.4 -> 92.5, LongMemEval 67.8 -> 94.4, vendor numbers). — [mem0 README](https://github.com/mem0ai/mem0)
- DreamBench-SWE (2026): verbatim event memory (82/180) did about as well as a typed-plus-raw structured probe (83/180) for multi-session software tasks; both far above no memory (21/180). — [DreamBench-SWE arXiv](https://arxiv.org/abs/2608.20664)
- SWE Context Bench: accurately summarised and selected prior experience helps; unfiltered or wrongly selected context helps little or hurts. — [SWE Context Bench arXiv](https://arxiv.org/abs/2602.08316)

**Graphs and temporal validity**
- Zep's paper shows gains concentrated in temporal and multi-session categories on LongMemEval and a drop on single-session-assistant questions. — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)
- Hindsight's largest gains were multi-session (21.1% -> 79.7%) and temporal reasoning (31.6% -> 79.7%) over the same-backbone full-context baseline (paper's own numbers). — [Hindsight paper HTML](https://arxiv.org/html/2512.12818v1)
- MemoryAgentBench: multi-hop selective forgetting at most 7% for every system tested, i.e. conflict resolution over changing facts is unsolved. — [MemoryAgentBench HTML](https://arxiv.org/html/2507.05257v3)

**Sleep-time consolidation**
- Letta: sleep-time agents / "dreaming" consolidate after N steps or at compaction, in a separate git worktree; "defragmentation" reorganises memory into 15-25 focused files. No benchmark numbers in the Context Repositories post. — [Letta memory docs](https://docs.letta.com/configuration/memory); [Letta Context Repositories blog](https://www.letta.com/blog/context-repositories/)
- Research basis: "Sleep-time Compute" (arXiv 2504.13171), referenced by Letta's docs. — [Letta sleep-time docs](https://docs.letta.com/guides/agents/architectures/sleeptime)
- Mastra Reflector, Hindsight background observation regeneration and mental models, Supermemory "dreaming" phase and LangMem background formation are all variants of the same idea. — [Mastra research](https://mastra.ai/research/observational-memory); [Hindsight GitHub README](https://github.com/vectorize-io/hindsight); [Supermemory docs: how it works](https://supermemory.ai/docs/concepts/how-it-works); [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)

**Surveys / taxonomy**
- "Memory in the Age of AI Agents" (arXiv 2512.13564, Dec 2025): forms = token-level, parametric, latent; functions = factual, experiential, working memory; dynamics = formation, evolution, retrieval; separates agent memory from LLM memory, RAG and context engineering. — [arXiv 2512.13564](https://arxiv.org/abs/2512.13564v1)
- "Always-On Agents" (arXiv 2606.30306, 2026-06-29): treats memory as one kind of persistent state alongside task ledgers, permissions, provenance and audit records; field under-studies governance, recovery and relinquishing state. — [arXiv 2606.30306](https://arxiv.org/abs/2606.30306)

### Inferences
- The practical consensus for coding agents in late 2026 is "files the agent can read and edit, loaded progressively (index always in context, details on demand), with dated entries and provenance, plus background consolidation" - this is what Anthropic's memory tool, Claude Code's CLAUDE.md, Letta MemFS, Manus and OpenAI's sandbox memory all converge on. Vector/graph services add the most value for (a) very long horizons with many changing facts, (b) multi-user personalisation at scale, and (c) temporal queries.
- Benchmarks rewarding QA retrieval (LoCoMo, LongMemEval) do not measure what coding agents need; task-success benchmarks (DreamBench-SWE, VibeMemBench, MERIT) show memory helps only when later work truly depends on non-inferable earlier facts, and that generic "experience extraction" often fails to help.
- Append-only, cache-stable memory (Mastra, Manus) and bi-temporal invalidation (Graphiti) are two answers to the same problem - never silently overwrite - one optimised for cost and one for queryable history.

### Gaps
- No independent head-to-head of Letta MemFS / git-based memory vs Mem0 / Zep / Hindsight on the same task benchmark.
- No independent evidence isolating the benefit of sleep-time consolidation itself.
- No primary commentary from well-known independent practitioners (e.g. Simon Willison, Andrej Karpathy, Harrison Chase) was collected in this pass.
- The Claude Code auto-memory feature and ChatGPT memory internals were not verified against first-party documentation in this pass.
