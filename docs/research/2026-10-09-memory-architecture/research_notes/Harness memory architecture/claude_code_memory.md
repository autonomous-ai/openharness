## CLAUDE.md hierarchy, imports, rules and AGENTS.md

### Takeaway
CLAUDE.md is user-authored, plain-markdown, concatenated (not overriding) instruction memory loaded at launch from managed → user → project → local, ancestor directories at launch and subdirectories lazily; since v2.1.277 (2026-09-18) Claude Code reads AGENTS.md natively when no CLAUDE.md exists, which makes AGENTS.md the most portable "deliver-into" file for a cross-agent layer.

### Cited Findings
- Two memory systems: CLAUDE.md (you write; instructions/rules; project/user/org scope; every session) and auto memory (Claude writes; learnings; per repository, shared across worktrees; first 200 lines or 25KB per session). "Claude treats them as context, not enforced configuration." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- Locations in load order (broad → specific): Managed policy (macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`; Linux/WSL `/etc/claude-code/CLAUDE.md`; Windows `C:\Program Files\ClaudeCode\CLAUDE.md`), User `~/.claude/CLAUDE.md`, Project `./CLAUDE.md` or `./.claude/CLAUDE.md`, Local `./CLAUDE.local.md` (gitignored). — [memory docs](https://code.claude.com/docs/en/memory)
- Managed content can also be inlined via a `claudeMd` key in `managed-settings.json` (honored only in managed/policy settings). Managed CLAUDE.md cannot be excluded. — [memory docs](https://code.claude.com/docs/en/memory)
- Load mechanics: CLAUDE.md and CLAUDE.local.md in the cwd and every ancestor directory load at launch; "All discovered files are concatenated into context rather than overriding each other," ordered root → cwd; within a directory, CLAUDE.local.md is appended after CLAUDE.md. Subdirectory CLAUDE.md files load on demand when Claude reads/writes/edits a file in that subdirectory (including `cat`/`head` of a single file via Bash). — [memory docs](https://code.claude.com/docs/en/memory)
- CLAUDE.md content "is delivered as a user message after the system prompt, not as part of the system prompt itself." For system-prompt-level instructions use `--append-system-prompt`. — [memory docs](https://code.claude.com/docs/en/memory)
- Block-level HTML comments (`<!-- ... -->`) are stripped before injection (not inside code blocks). — [memory docs](https://code.claude.com/docs/en/memory)
- Imports: `@path/to/file` syntax, relative paths resolve from the importing file, absolute and `~/` paths allowed, recursive max depth four hops; spaces need backslash escapes; imports inside code spans/fences are ignored. Imported files load at launch (no context saving). External imports (outside working dir) in project files trigger a one-time approval dialog per project; user-scope files import without the dialog (except in Cowork). — [memory docs](https://code.claude.com/docs/en/memory)
- `/memory` has allowed direct editing of all imported memory files since v1.0.94 (2025-08-27). — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Size: docs recommend under 200 lines per CLAUDE.md; Claude Code loads a CLAUDE.md up to 4 MiB in full and skips a larger file; startup and `/status` warn when a file exceeds the recommended length or when files together exceed a combined limit. `/doctor prompt-audit` (v2.1.283+) audits instruction files for staleness/conflicts. — [memory docs](https://code.claude.com/docs/en/memory)
- `.claude/rules/*.md` (added v2.0.64, 2025-12-10 per changelog "Added support for .claude/rules/"): recursive discovery; rules without `paths` frontmatter load at launch with the same priority as `.claude/CLAUDE.md`; rules with `paths:` globs load when Claude Read/Write/Edits (or single-file `cat`s) a matching file. `paths` is the only frontmatter field read. User-level rules in `~/.claude/rules/` load before project rules. Symlinked rules outside the working directory are treated like external imports. Brace-expansion budget: 1,000 expanded patterns / 4 MiB per rule. — [memory docs](https://code.claude.com/docs/en/memory); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- `claudeMdExcludes` (glob on absolute paths, any settings layer, arrays merge) skips specific CLAUDE.md/rules files. `--add-dir` directories do not load CLAUDE.md unless `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. — [memory docs](https://code.claude.com/docs/en/memory)
- AGENTS.md: native reading requires v2.1.277+. Default "Project instructions" mode `claude-md-or-agents-md`: Claude reads AGENTS.md (and `.claude/AGENTS.md`) in cwd and ancestors only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists there; `~/.claude/CLAUDE.md`, managed CLAUDE.md and `.claude/rules/` do not block it. Other modes: `claude-md-and-agents-md` (both; dedupes an AGENTS.md already imported/symlinked), `claude-md`, `managed-only`. Set via `/config` or `pluginConfigs["cc-plugin-agents-md@builtin"].options.instructionFiles` in user/`--settings`/managed settings (ID was `agents-md@builtin` before v2.1.285). Not read: `AGENTS.local.md`, `AGENTS.override.md`, `.agents/`. AGENTS.md read this way does not fire `InstructionsLoaded`, is not loaded from `--add-dir` dirs, and silently loads external imports only if previously approved. — [memory docs](https://code.claude.com/docs/en/memory)
- Docs recommend removing a `SessionStart` hook that prints AGENTS.md once native reading works, because it "adds a second copy to the context." — [memory docs](https://code.claude.com/docs/en/memory)
- `/init` and `/import` (v2.1.213+) migrate other tools' instruction files (Cursor, Copilot; with `CLAUDE_CODE_NEW_INIT=1` also AGENTS.md, Devin, Windsurf, Cline) into CLAUDE.md as a one-time copy. — [memory docs](https://code.claude.com/docs/en/memory)
- Recent loading fixes: path-scoped rules and nested CLAUDE.md not loading on Write/Edit fixed in 2.1.288; on single-file `cat` fixed in 2.1.293; subdirectory AGENTS.md not attached on @-mention fixed in 2.1.290. — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- For a cross-agent layer, AGENTS.md is now the lowest-friction shared instruction file: Codex and others read it natively, and Claude Code reads it natively unless a CLAUDE.md exists. A `CLAUDE.md` containing `@AGENTS.md` is the robust form across all Claude Code versions and modes.
- Because all levels concatenate and conflicts are resolved "arbitrarily," a memory layer that writes into instruction files should own one clearly delimited file (e.g., an imported `@~/.harness/memory.md`) rather than editing user-authored CLAUDE.md content.
- User-scope imports (`~/.claude/CLAUDE.md` → `@~/...`) load without approval dialogs, making them the quietest machine-wide delivery path.

### Gaps
- The exact "combined limit" across all instruction files that triggers the startup warning is not stated in the docs I read.

## Auto memory (MEMORY.md + topic files)

### Takeaway
Auto memory (shipped 2026-02-05, v2.1.32; on by default) is a per-git-repository, machine-local directory of plain markdown files: a `MEMORY.md` index (first 200 lines / 25KB injected every session) plus one topic file per memory with YAML frontmatter (`type` ∈ user/feedback/project/reference, plus a `modified` ISO timestamp since v2.1.214). Claude writes it with ordinary file tools during the turn, and a background "memory extraction" pass also writes it; topic files are recalled on demand. It does not sync across machines, and there is no documented "dream"/scheduled consolidation in Claude Code.

### Cited Findings
- Timeline: "Claude now automatically records and recalls memories as it works" — v2.1.32 (2026-02-05); "Claude automatically saves useful context to auto-memory. Manage with /memory" — v2.1.59 (2026-02-25); "Project configs & auto memory now shared across git worktrees of the same repository" — v2.1.63 (2026-02-28); `autoMemoryDirectory` setting — v2.1.74 (2026-03-11); "last-modified timestamps to memory files, helping Claude reason about which memories are fresh vs. stale" — v2.1.75 (2026-03-13); `MEMORY.md` "now truncates at 25KB as well as 200 lines" — v2.1.83 (2026-03-24); agent "reminded to compact its MEMORY.md index when nearing the size limit" — v2.1.186 (2026-06-22); over-limit writes "now produce an explicit error instead of silent truncation" — v2.1.210 (2026-07-14); ISO `modified` frontmatter timestamp — v2.1.214 (2026-07-18). — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); dates from [npm registry](https://registry.npmjs.org/@anthropic-ai/claude-code)
- Four memory types recorded as a `type` frontmatter field: `user` (role, expertise, preferences), `feedback` (corrections and confirmed approaches), `project` (ongoing work, deadlines, decisions not derivable from code/git), `reference` (where to find external info such as trackers/dashboards). "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." "Claude doesn't save something every session." — [memory docs](https://code.claude.com/docs/en/memory)
- Storage: `~/.claude/projects/<project>/memory/`; `<project>` "is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory. Outside a git repo, the project root is used instead." Layout: `MEMORY.md` ("Index, one line per memory, loaded into every session") plus topic files like `user_role.md`, `feedback_testing.md`. — [memory docs](https://code.claude.com/docs/en/memory)
- "Auto memory is machine-local. ... Files are not shared across machines or cloud environments." — [memory docs](https://code.claude.com/docs/en/memory)
- Load: "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation." Topic files are not loaded at startup; "Claude reads them on demand using its standard file tools." UI shows "Saved N memories" / "Recalled N memories". — [memory docs](https://code.claude.com/docs/en/memory)
- Index bound enforcement: after a write to MEMORY.md, Claude Code measures it; near a limit it reminds Claude to "keep one line per entry, move detail into topic files, and merge or drop stale entries"; over a limit the write succeeds but returns an error telling Claude to rewrite the index "because everything past the limit is dropped on the next load." v2.1.268 (2026-09-10) made the truncation warning state how many lines were cut. — [memory docs](https://code.claude.com/docs/en/memory); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- `modified` timestamp: "When Claude writes a memory file that begins with YAML frontmatter, Claude Code records the write time in a `modified` frontmatter field as an ISO 8601 timestamp ... Claude Code never adds frontmatter to a file that has none" (v2.1.214+). — [memory docs](https://code.claude.com/docs/en/memory)
- Explicit "remember X" requests go to auto memory; "add this to CLAUDE.md" goes to CLAUDE.md. — [memory docs](https://code.claude.com/docs/en/memory)
- Background extraction exists: v2.1.77 (2026-03-16) fixed "`--resume` silently truncating recent conversation history due to a race between memory-extraction writes and the main transcript"; v2.1.273 (2026-09-15) says a repo-chosen memory directory under `blockReadsOutsideWorkingDirectories` "is no longer loaded into the prompt, recalled, indexed, or used by memory extraction." — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Recall is a distinct model-driven step: v2.1.286 (2026-09-30) "[Claude Tag] Fixed memory recall finding nothing in organizations that cannot use the default Sonnet model"; v2.1.288 (2026-10-02) "Fixed session titles, memory recall and prompt hooks failing on Mantle or behind gateways that reject structured outputs." — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- "Improved N memories" alongside "Saved"/"Recalled" suggests the extraction pass can also rewrite existing memories (an in-line consolidation), but no doc describes its policy.
- Recall appears to be a side query to a Sonnet-class model using structured outputs that selects topic files to inject (the "age note" on "restored memory file[s]" implies injected content carries staleness metadata). This is inferred from changelog wording, not documented.
- For a cross-agent layer, the auto memory directory is an easy read target (plain markdown, stable-ish frontmatter, keyed by git repo), and also a write target: files the layer writes there with valid frontmatter and an index line will be loaded/recalled by Claude Code. Repointing `autoMemoryDirectory` at a layer-managed (synced) directory is the cleanest documented integration, at the cost of Claude Code's own writes landing in that directory too.
- Worktree sharing is keyed on the git repo; it is not keyed on the remote, so two clones of the same repo on one machine in different paths likely get different directories, and different machines never share.

- The binary evidence implies Anthropic has built (but not publicly documented or broadly enabled) three things a cross-agent layer would also need: background consolidation over transcripts (Auto Dream), relevance-ranked recall with a cheap-model selector/synthesizer, and personal/team/org memory sync to hosted stores. Their absence from docs suggests staged rollout; a layer should expect Claude Code to eventually ship its own cloud sync and design to coexist (e.g., treat the local memory dir as a projection, not the source of truth).

### Gaps
- No official description of when extraction runs (end of turn? idle? session end?), which model it uses, or how many files recall selects.
- `CLAUDE_MEMORY_STORES`, team/personal/org memory sync are not documented on the public memory page; only the changelog and binary strings name them. Whether any of it is enabled for ordinary Pro/Max/Team users is unknown.
- Auto Dream's current status (flag-gated off? limited cohort?) is unknown; it is not in docs or changelog as of 2026-10-09, and default `minHours`/`minSessions` values were not recoverable.

## Session continuity: compaction, resume, transcripts

### Takeaway
Within a session, continuity comes from auto-compaction (a structured summary replaces history; CLAUDE.md, auto memory, plan, up to five recent files and invoked skills are re-injected). Across sessions, `--continue`/`--resume` replay a local JSONL transcript at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`, whose format Anthropic explicitly calls internal and unstable; retention defaults to 30 days.

### Cited Findings
- What survives compaction: system prompt and output style still apply; project-root CLAUDE.md and unscoped rules "Re-injected from disk"; auto memory "Re-injected from disk"; fresh git status; plan-mode plan re-injected; path-scoped rules and nested CLAUDE.md reload only on demand; up to five most recently modified read/edited files re-read (files over 5,000 tokens come back as a path reference); invoked skill bodies re-injected "capped at 5,000 tokens per skill and 25,000 tokens total; oldest dropped first"; the skill listing does not reload; "Context that hooks added earlier" is summarized; SessionStart hooks matching `compact` re-run. — [Context window docs](https://code.claude.com/docs/en/context-window)
- The compaction summary "keeps: your requests and intent, key technical concepts, files examined or modified with important code snippets, errors and how they were fixed, pending tasks, and current work"; full tool outputs and intermediate reasoning are gone. Since v2.1.198 the summarization inherits the session's extended-thinking setting. — [Context window docs](https://code.claude.com/docs/en/context-window)
- Controls: `/compact [instructions]`; `/rewind` → "Summarize from here" / "Summarize up to here" (latter added v2.1.141, 2026-05-13); `/autocompact <tokens>` sets the auto-compact window (saved per model since v2.1.288); subagent `autoCompactWindow` frontmatter (v2.1.296). — [Context window docs](https://code.claude.com/docs/en/context-window); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Transcripts: JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`, `<project>` = working directory path with non-alphanumerics replaced by `-` (truncated to 200 chars plus a hash if longer). "The entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release. To build on session data, use `/export` or the script interfaces instead." — [Sessions docs](https://code.claude.com/docs/en/sessions)
- Note the asymmetry: transcripts are keyed by working-directory path, auto memory by git repository. — [Sessions docs](https://code.claude.com/docs/en/sessions); [memory docs](https://code.claude.com/docs/en/memory)

## Skills, rules, output styles and plugins as procedural memory

### Takeaway
Skills are Claude Code's on-demand procedural memory: only name+description (≤1,536 chars each) sit in context; the SKILL.md body loads on invocation and is re-injected after compaction (5k tokens per skill, 25k total). They follow the open Agent Skills standard, so a cross-agent layer can author one SKILL.md and project it into several agents; claude.ai-synced skills are the one account-level, cross-machine artifact Claude Code consumes today.

### Cited Findings
- Locations/precedence: Enterprise (managed dir) > Personal `~/.claude/skills/<name>/SKILL.md` > Project `.claude/skills/<name>/SKILL.md`; also nested `<subdir>/.claude/skills/` (load when Claude touches the subdir), `--add-dir` dirs, plugins (`<plugin>/skills/`, invoked as `/plugin:skill`), and claude.ai-synced skills under `~/.claude/skills/synced/` (terminal sync since v2.1.273, 2026-09-15). Legacy `.claude/commands/*.md` still works. — [Skills docs](https://code.claude.com/docs/en/skills)
- Progressive disclosure: at session start only descriptions load; `description` + `when_to_use` truncated at 1,536 characters in the listing; full body loads on invocation and then "stays in context across later turns; Claude Code doesn't re-read the file"; keep SKILL.md under 500 lines with supporting files loaded on demand. `disable-model-invocation: true` keeps a skill entirely out of context until `/name`. `paths` globs limit automatic activation. `/skill-doctor` (v2.1.252+) finds unused skills. — [Skills docs](https://code.claude.com/docs/en/skills)
- After compaction: most recent invocation of each skill re-attached, first 5,000 tokens each, 25,000-token combined budget, most recent first; the skill listing itself "is not re-injected after /compact." — [Skills docs](https://code.claude.com/docs/en/skills); [Context window docs](https://code.claude.com/docs/en/context-window)
- Portability: "Claude Code follows the open Agent Skills standard, with extensions"; outside Claude Code only `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` frontmatter is allowed (other keys hard-error on claude.ai/Skills API). — [Skills docs](https://code.claude.com/docs/en/skills); [agentskills.io](https://agentskills.io)
- Docs position the mechanisms: CLAUDE.md for facts needed every session; multi-step procedures or area-specific guidance belong in a skill or a path-scoped rule. "Rules load into context every session or when matching files are opened ... use skills instead, which only load when you invoke them or when Claude determines they're relevant." — [memory docs](https://code.claude.com/docs/en/memory)
- Output style is part of the system prompt and "still appl[ies]" after compaction; subagents do not inherit it. — [Context window docs](https://code.claude.com/docs/en/context-window); [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- Plugins can ship skills, hooks (`hooks/hooks.json`), agents and MCP servers; the native AGENTS.md reader is itself a built-in plugin (`cc-plugin-agents-md@builtin`). — [Hooks reference](https://code.claude.com/docs/en/hooks); [memory docs](https://code.claude.com/docs/en/memory)
- Subagents can preload up to 32 skills via the `skills` field (v2.1.295). — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- A cross-agent memory layer can distribute "procedural" memories (how-tos, runbooks) as Agent Skills: cheap at rest (description only), portable across Claude Code and other Agent-Skills-compatible agents, and robust to compaction. Declarative facts are better delivered via the index/hook path.
- A plugin is the cleanest single install unit for a layer inside Claude Code: it can bundle SessionStart/UserPromptSubmit/Stop hooks, an MCP server for search, and skills.

### Gaps
- Exact token budget for the whole skill listing (truncated part of the skills page) not captured.

## Hooks relevant to memory delivery

### Takeaway
SessionStart (sources startup/resume/clear/compact/fork) and UserPromptSubmit are the two supported injection points; both accept plain stdout or `hookSpecificOutput.additionalContext`, capped at 10,000 characters each (overflow saved to a file with a 2,000-char preview). Stop can force continuation; PreCompact can block; SessionEnd and PostCompact cannot inject; InstructionsLoaded is observe-only.

### Cited Findings
- Common hook input: `session_id`, `transcript_path` ("written asynchronously and may lag the current turn"), `cwd`, `hook_event_name`; plus `prompt_id`, `permission_mode`, `scratchpad_dir`, `effort`, `agent_id`/`agent_type` when relevant. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- SessionStart: matchers `startup`, `resume`, `clear`, `compact`, `fork` (fork reported as `resume` before v2.1.214); only `command` and `mcp_tool` hook types; plain stdout on exit 0 becomes context; `hookSpecificOutput.additionalContext` "placed at the start of the conversation before the first prompt"; other fields `initialUserMessage`, `watchPaths`, `sessionTitle`, `reloadSkills`; `CLAUDE_ENV_FILE` for persisting env vars. On resume/fork also gets `seconds_since_last_response`, `context_tokens`, `prompt_cache_likely_expired`, `estimated_cache_write_usd` (v2.1.251+). — [Hooks reference](https://code.claude.com/docs/en/hooks)
- UserPromptSubmit: input `prompt` (pasted text expanded) and `session_title`; output `decision: "block"` + `reason`, `additionalContext` ("added to Claude's context alongside the prompt"), `sessionTitle`, `suppressOriginalPrompt`; plain stdout also added; cannot replace prompt text; default timeout 30 s; fires on turns Claude Code starts on its own too. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- PreCompact/PostCompact: matchers `manual`, `auto`; PreCompact can block compaction (exit 2 / top-level `decision`); PostCompact has no decision control. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Stop: input `stop_hook_active`, `last_assistant_message`, `background_tasks`, `session_crons`; `decision: "block"` + `reason` keeps Claude working; `additionalContext` gives non-blocking feedback at end of turn; loop cap of eight consecutive continuations with no tool call (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`). — [Hooks reference](https://code.claude.com/docs/en/hooks)
- SessionEnd: matchers `clear`, `resume`, `logout`, `prompt_input_exit`, `other`; cannot block or inject; hooks share a 1.5-second budget, raisable by per-hook `timeout` up to 60 s. Docs suggest a SessionEnd hook "can archive the transcript when a session ends." — [Hooks reference](https://code.claude.com/docs/en/hooks); [Sessions docs](https://code.claude.com/docs/en/sessions)
- InstructionsLoaded: fires when CLAUDE.md or `.claude/rules/*.md` loads (start and lazy); input `file_path`, `memory_type` (`User`/`Project`/`Local`/`Managed`), `load_reason` (`session_start`, `nested_traversal`, `path_glob_match`, `include`, `compact`), `globs`, `trigger_file_path`, `parent_file_path`; observe-only. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Output size cap: `additionalContext`, `systemMessage`, `initialUserMessage`, and plain stdout each capped at 10,000 characters; over the cap the full output is saved to a file in the session directory and Claude gets the path plus a 2,000-character preview; "Claude Code doesn't ask Claude to read the file"; no setting raises it. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Hook types: `command`, `http`, `mcp_tool`, `prompt` (single-turn LLM eval), `agent` (experimental subagent with Read/Grep/Glob). Config sources: `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed policy, plugin `hooks/hooks.json`, skill frontmatter, subagent frontmatter; `allowManagedHooksOnly` and `disableAllHooks` exist. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- After compaction, "Context that hooks added earlier" is summarized with the rest, while SessionStart hooks matching `compact` are re-run and their output added to the compacted context. — [Context window docs](https://code.claude.com/docs/en/context-window)
- Hook-related fixes 2026-10: async SessionStart hook context re-added on every resume (fixed 2.1.295); late-loading plugin SessionStart hooks skipped in headless sessions (fixed 2.1.296). — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- A cross-agent layer can deliver (a) a compact always-on digest via SessionStart (matchers startup|resume|clear|compact so it survives compaction), (b) per-prompt retrieved memories via UserPromptSubmit `additionalContext` (≤10k chars), and (c) capture via Stop (`last_assistant_message`) / SessionEnd + `transcript_path`.
- Budget 10,000 characters per injection; anything larger silently degrades to a file pointer that Claude is not told to open.
- Integration-surface map for a layer above Claude Code (each item sourced in the sections of this note):
  - **Read from:** auto memory dir `~/.claude/projects/<repo-derived>/memory/` (MEMORY.md + typed topic files with `modified`); subagent memory dirs (`~/.claude/agent-memory/`, `.claude/agent-memory[-local]/`); CLAUDE.md/AGENTS.md/rules files; transcripts `~/.claude/projects/<cwd-encoded>/<session-id>.jsonl` (unstable format); hook payloads (`prompt`, `last_assistant_message`, `transcript_path`); `InstructionsLoaded` for what loaded; `claude -p --resume <id> --output-format json` for structured summaries.
  - **Deliver into:** AGENTS.md / CLAUDE.md `@import` of a layer-owned file (always-on, ≤ ~200 lines recommended); `~/.claude/rules/` or `.claude/rules/` with `paths:` for scoped facts; SessionStart `additionalContext` (startup|resume|clear|compact) and UserPromptSubmit `additionalContext` (≤10,000 chars each); writing typed files + index lines into the auto memory dir, or pointing `autoMemoryDirectory` / `CLAUDE_CONFIG_DIR`+`CLAUDE_CODE_PROJECT_DIR_NAME` at a layer-managed directory; Agent Skills for procedures; a plugin to bundle hooks+skills+MCP.
  - **Avoid relying on:** model-chosen MCP memory tools (lose to the system-prompt auto-memory instructions per #48465); parsing JSONL fields without version gates; mid-turn edits being visible after auto-compaction (#92949).

### Gaps
- PreCompact input fields (e.g., `custom_instructions`) and whether PreCompact can add instructions to the summary were not in the excerpts I fetched.

## Claude API side: Memory tool, context editing, compaction, Managed Agents memory stores

### Takeaway
The API offers two distinct memory primitives: (1) the client-side Memory tool (`memory_20250818`, no beta header now, all Claude 4+ models) where your app stores `/memories` files however it likes; and (2) server-side Managed Agents **memory stores** (beta `agent-memory-2026-07-22`), workspace-scoped versioned document collections mounted at `/mnt/memory/<slug>/` in agent sandboxes, with an API for CRUD, optimistic concurrency, audit versions, redaction, and a "dreaming" consolidation job. Neither is wired into a local Claude Code CLI session by default.

### Cited Findings
- Memory tool: "operates client-side: Claude requests file operations, and your application executes them." Tool entry `{"type": "memory_20250818", "name": "memory"}` is the whole config; "available on all Claude 4 and later models"; SDK helpers `BetaAbstractMemoryTool` (Python/C#), `betaMemoryTool` (TS), `BetaMemoryToolHandler` (Java), ready-made `BetaLocalFilesystemMemoryTool` (Python/TS); "the memory tool itself doesn't require a beta header." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Commands: `view` (dir listing 2 levels deep, excludes hidden and node_modules; file view with 6-wide line numbers; `view_range`; text view truncated past 16,000 characters; images viewable), `create`, `str_replace` (unique match required), `insert` (`insert_line`, 0 = top), `delete` (recursive; not the root), `rename` (no overwrite; not the root). — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The API auto-injects a system prompt when the tool is present: "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE. MEMORY PROTOCOL: 1. Use the `view` command of your `memory` tool to check for earlier progress. ... ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Security responsibilities on the implementer: path-traversal validation (`/memories/../../secrets.env`, URL-encoded `%2e%2e%2f`), size caps, "Periodically delete memory files that haven't been accessed in a long time," and sensitive-data stripping ("Claude usually refuses to write sensitive information to memory files"). — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Pairing guidance: memory tool + context editing (client clears old tool results) and/or server-side compaction ("summarizes older conversation context server-side ... when the conversation approaches the context window limit"); "memory preserves the information that must survive summarization." Recommended multi-session pattern: initializer session creates progress log + feature checklist + startup script reference; later sessions read them first; update progress log before ending; "Mark a feature complete only after end-to-end verification." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Managed Agents memory stores (status: beta, header `agent-memory-2026-07-22` for store calls; session calls still use `managed-agents-2026-04-01`; sending both on a store request returns 400): "A memory store is a workspace-scoped collection of text documents optimized for Claude"; attached in a session's `resources[]` only at creation (`type: "memory_store"`, `memory_store_id`, `access` `read_write` default or `read_only`, optional `instructions` ≤ 4,096 chars); max 8 stores per session; mounted at `/mnt/memory/<slugified-name>/` (exact path in `mount_path`); a note with name, mount path, access, description and instructions is auto-added to the system prompt; access enforced at filesystem level. — [Managed Agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- Limits: individual memory capped at 100 kB (~25k tokens); max 10,000 memories per store; at the limit, new writes fail but existing memories stay readable/editable. — [Managed Agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- API: `POST/GET /v1/memory_stores`, `/v1/memory_stores/{id}/memories` (create does not overwrite; list with `path_prefix` ending in `/` and `depth` 0|1), `POST .../memories/{memory_id}` update content and/or path with `precondition: {type: "content_sha256", content_sha256}` for optimistic concurrency; `DELETE`. Every mutation creates an immutable `memver_...` version (store-scoped, survives memory deletion) retained 30 days (recent versions of a live memory kept regardless); `POST .../memory_versions/{id}/redact` scrubs content but keeps the audit trail; stores can be archived (one-way, read-only) or deleted. — [Managed Agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- Self-hosted sandboxes: the store is a local copy the environment worker downloads and reconciles after tool calls "at most once per sync interval (15 seconds by default), and once more when the session ends"; other sessions see changes only after both workers sync. — [Managed Agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- Prompt-injection warning: "a successful prompt injection could write malicious content into the store. Later sessions then read that content as trusted memory. Use `read_only` for reference material." — [Managed Agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- Consolidation: "You can also run a dreaming session, which consolidates fragmented content into a separate new output store rather than modifying the original. Switch your sessions over to that output store, then archive or delete the original." — [Managed Agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory) (links to [dreams](https://platform.claude.com/docs/en/managed-agents/dreams))
- Claude Code linkage: the bundled `claude-api` skill was updated "for the Managed Agents Aug 19 release: web search/fetch domain settings and memory stores on self-hosted sandboxes" (v2.1.238, 2026-08-20), and v2.1.172 (2026-06-10) references "mounted team memory stores (`CLAUDE_MEMORY_STORES`) in remote sessions." — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- The Managed Agents memory store is the only Anthropic-hosted, API-addressable, versioned, multi-session memory substrate found; its design (path-addressed small markdown files, sha256 preconditions, version audit, redaction, read-only shared stores, offline "dream" consolidation into a new store) is a close template for a cross-agent memory layer, and a layer could even use it as a backend.
- `CLAUDE_MEMORY_STORES` suggests Claude Code remote/cloud sessions can mount the same kind of stores as "team memory" and include them in recall; this is the closest thing to cloud-synced memory in Claude Code, but it is undocumented for local CLI use.
- The memory tool's auto-injected protocol and the Claude Code auto-memory prompt are different contracts: the API tool expects one `/memories` tree, Claude Code expects `MEMORY.md` + typed topic files. A cross-agent layer should normalize to one canonical format and project into each.

- Dreams (research preview, request access; beta header `dreaming-2026-04-21` in addition to `managed-agents-2026-04-01`): "A dream reads an existing memory store alongside past session transcripts, then produces a new, reorganized memory store: duplicates merged, stale or contradicted entries replaced with the latest value, and new insights surfaced. The input store is never modified." Inputs: one `memory_store` + 1 to 100 `sessions`; optional `instructions` ≤ 4,096 chars ("a synthesis pass over the inputs, not an editor"); selectable model (e.g., `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-sonnet-4-6`). `POST /v1/dreams` → `drm_...` with status `pending`→`running`→`completed|failed|canceled`; runs as an observable session; "typically take minutes to a few hours"; billed at standard token rates; errors include `input_memory_store_too_large`. Example resource timestamp 2026-04-29. Rationale stated: "over many sessions a memory store accumulates duplicates, contradictions, and stale entries." — [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams)

- Context editing (beta header `context-management-2025-06-27`): `clear_tool_uses_20250919` (defaults: `trigger` 100,000 input tokens, `keep` 3 tool uses; options `clear_at_least`, `exclude_tools`, `clear_tool_inputs`) and `clear_thinking_20251015`; applied server-side, client keeps full history; results reported in `context_management.applied_edits`. With the memory tool, "As context approaches the clearing threshold, Claude gets an automatic warning to preserve important information" so it can write to memory before results are cleared. Docs recommend server-side compaction (edit type `compact_20260112`) as the primary long-conversation strategy; SDK client-side compaction (`compaction_control`) is deprecated (default threshold 100,000; summary sections Task Overview, Current State, Important Discoveries, Next Steps, Context to Preserve). — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Anthropic's framing (2025-09-29): "structured note-taking" where the agent "regularly writes notes persisted to memory outside of the context window"; compaction; just-in-time retrieval via "lightweight identifiers (file paths, stored queries, web links, etc.)"; sub-agents returning 1,000–2,000-token summaries; "CLAUDE.md files are naively dropped into context up front" while glob/grep retrieve just in time; memory tool released in public beta alongside Sonnet 4.5. — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Gaps
- Whether Claude Code (local CLI) can trigger or consume dreams is not documented; no Claude Code changelog entry mentions dreams.
- Server-side compaction API (`compact_20260112`) parameters were not captured in detail (separate compaction page not fetched).

## Known issues and changelog timeline

### Takeaway
User-reported problems cluster around: the hard 200-line/25KB index cap (silent loss of newest entries, constant curation at scale), staleness with no expiry, cross-project leakage when sessions start outside a repo, no cross-machine sync, low-value or wrong saves, competition with MCP memory servers for priority, compaction re-injecting stale snapshots, and prompt-injection/poisoning risk. Most are open as of 2026-10-09; many earlier duplicates were auto-closed by a stale bot without Anthropic responses.

### Inferences
- The recurring failure modes (cap-driven loss, staleness, wrong scope, no sync, priority fights with external memory) are exactly what a cross-agent layer above Claude Code must solve; the strongest integration posture today is to feed Claude Code through its own channels (AGENTS.md/CLAUDE.md import, SessionStart/UserPromptSubmit hooks, optionally `autoMemoryDirectory` or a plugin) rather than through an MCP tool the model may ignore.
- Because Anthropic stale-bot-closes many memory issues without response, community workarounds are the de facto state of the art; expect undocumented behavior changes between releases.

### Gaps
- No official Anthropic statement on roadmap for cross-machine auto-memory sync, Auto Dream, or an MCP memory-provider hook as of 2026-10-09.
