How: The starter is a tiny Store-style harness: the finished Space Dodge project, a manifest that runs on OpenCode, and viewer.use: autonomous/web-viewer pointing at its index.html. It is the same shape the community "fork a project" flow already creates (fork_project.dart), which waits for the viewer and shows it. The conversation is a bundled OpenCode session, imported on first run with its folder paths rewritten (checked: an exported session resumes on another computer). The preview is served by the daemon, which starts the viewer on a free local port when the harness attaches. The app opens it at 70/30 without taking focus from the composer. Hide and show use what exists today: Close viewer on the preview, and View ▸ Toggle Viewer to reopen it. What's new is a default key for Toggle Viewer (⇧⌘V; nothing uses it now) and the small header hint. Who gets it: only someone with no Claude Code, Codex or OpenCode and no sessions, the same people OpenCode is downloaded for. To decide: the web viewer is a Store package fetched at install, so the app should bundle it (or fetch it during setup) to make the first screen appear without waiting.

Every web project gets the same preview, not only the starter

So the starter doesn't promise something the rest of Harness doesn't do: in any harness, with any agent, the first time the agent writes an HTML page or starts a local web server, the preview opens beside it by itself, exactly like the starter's. Nobody has to know a viewer exists.

Someone's own next project, after the starter: a plain ⌘N harness on Claude Code, no Store harness, no setting. The page appears as soon as the agent writes it.

How Harness knows it's a web project: it doesn't guess from the project; it watches what the agent does. Either the agent writes an .html file in the project (a static page or game), or it starts a local web server and prints its address (Local: http://localhost:5173 from Vite, Next, etc.). The daemon already reads every turn's tool calls and the pane's output, so both are visible to it.
When it opens: automatically, the first time either happens in that harness, without the person running anything. After that it shows the newest page, or the server's address, and reloads as files change.
Not instead of Chrome: it is a preview inside Harness, beside the agent, so the person sees the result without leaving. The preview's header has "Open in browser" (↗), and ⌘-click on any address or file the agent prints still opens the default browser as today.
Turning it off: × hides it for that harness; ⇧⌘V (or View ▸ Toggle Viewer) brings it back; the agent's header shows "◧ Preview ⇧⌘V" while it is hidden.
What's new: today the daemon starts a viewer only for Store harnesses that declare one (services/viewers.ts returns early for every other session). This would start the bundled web viewer for any session that writes a page or prints a local address. The pane, its layout and its toggle are the ones Store harnesses use now.

After picking one that isn't installed: its pane opens at once with one progress line, and the message is sent when it starts. For one that needs a sign-in, the pane shows that agent's own sign-in screen.
What exists today: Store harnesses already get a progress panel like this while they install (Fetch, Set up, Check; dsh_install_panel.dart). An agent install (Cursor, Copilot, Grok…) does not: its pane prints "harness: installing the engine — this pane becomes the agent when it finishes", the install command and the installer's raw output. This brings the Store panel's treatment to agents. You said to build it, so it's in the build.

Checked: can it be built (2026-10-08)

Bundled OpenCode session (screen 2): yes. In a fresh macOS VM, opencode export produced a 33 KB JSON of a real game session. opencode import in a brand-new home under a different folder made it the only session there, and opencode --session <id> opened with the whole conversation on screen. Two things for the build: rewrite the folder paths in the JSON to the person's own folder before importing, and hand-curate the transcript. The one OpenCode made ran python3, which on a fresh Mac raises Apple's developer-tools dialog.
Game preview pane: yes, with modest work. The app already has web panes (WKWebView, web_pane_panel.dart) for harness viewers; a local index.html needs a URL the pane can load.
Recent sessions and counts (screen 3): yes. The daemon's session_search, asked with a time and no words, returns recent Claude Code and Codex sessions with engine, folder, title and last activity. The app's welcome page already reads it (welcome_sessions.dart). The limits come from the usage controller behind the Models menu.
Opening panes without starting 9 agents: needs a "show the conversation, start the agent on first keystroke" pane, which does not exist yet. It is the largest piece of new work here. Until it exists, the cap could be 2 live panes per tab.

Decided

Tour: 5 slides: machines, agents, ⌘P, ⌘N, then sessions + the Harness phone app + the Harness device. Tagline "All your machines. All your agents. One command center." Harness opens by itself when setup finishes; no button.
New users: the Space Dodge game, preview beside it, a first change pre-filled and selected. OpenCode is downloaded only when there is no agent engine.
Every web project: the preview opens by itself when an agent writes a page or starts a local server; × hides it, ⇧⌘V shows it.
Existing users: only sessions not running anywhere. Tab 1 = newest Claude Code + newest Codex; tab 2 = next 3, both agents where possible; one agent = its own recent sessions. A pane's agent starts on the first keystroke. No welcome strip.
Pickers: no status badges; agent installs get a friendly progress pane instead of installer text.
Not changed: the footer and everything outside onboarding. (Footers in these renders now match the app: usage on the left after Models.)
