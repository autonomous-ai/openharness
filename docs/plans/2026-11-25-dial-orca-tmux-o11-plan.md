> **For agentic workers:** REQUIRED: run this plan with **devcrew phase 3** (a queue: each task starts once the tasks it
> depends on have landed and no running task shares one of its files). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Eval scenario O11 grades what the dial does today for Claude Code under tmux in an Orca pane: `c` is an Orca
row at its tab's place (`[a, b, c]`), a tap on it switches Orca to its tab, shows its tmux pane and brings Orca forward,
and voice to it goes through its mod, typed into no Orca pane and no tmux (the hard gate). Tier A runs the real tmux
lookup for it on macOS and Linux.

**Architecture:** Eval only, under `cli/src/testing/dialAppEval/`. No product file changes. Tier A's Orca world gets the
tmux model (`tierA/steps/tmux.ts`, which already models a tmux session in an Orca pane) when a scenario has a `tmux`
session; Linux's model of Orca puts its terminal host under Orca's main process, as the recording has it, so tmux's
client lookup finds Orca there as it does on a real Linux. The `open` check grades an Orca row under tmux by its tmux
pane too, the gate counts words put into tmux, and O11 itself is rewritten. The eval's design doc follows; the baseline
is regenerated by a run.

**Tech Stack:** TypeScript (Node 24), Vitest (tier A spec, in process on fakes and virtual time), the dial app eval's
runner, grader and baseline.

**Spec:** `docs/plans/2026-11-25-dial-orca-tmux-o11-design.md` (approved, option A; read it with this plan). Base:
`chore/dial-orca-tmux-o11-proposal` at `0cf4605050`. The eval's own design: `docs/plans/2026-11-22-dial-eval-orca-design.md`.

## What this plan decides from the code (read for this plan, not run)

- **Linux: Orca is found from Orca's main process, not its host.** tmux's lookup names the app holding the client by
  walking the client's parents (`cable/hosts/tmux.ts clientOf` → `scannedApp.ts scannedApps`), which on Linux maps each
  name through `frontAppId`: `orca-ide` is Orca, `orca-agents` (the host) is not. `scannedApp.ts`'s `PTY_HOSTS` (the
  spec's "scannedApp.ts:226") names the *maker* of a terminal, not its app. On a real Linux the host is a child of Orca's
  main process (`RECORDED_ORCA.linux.deb.how`: "a child of the main process (comm `orca-ide`)", recorded ppid 3816), so
  the walk finds Orca. Tier A's model starts the host under init (ppid 1), so without Task 1 `c` would land on tmux's
  page on Linux. Task 1 adds Orca's main process above the host, on Linux only (macOS records the host under launchd).
- **macOS: the tap's tmux move is `switch-client`, as far as tier A can tell.** The client's walk finds no app on macOS:
  the host's recorded path is under `/Users/u/…/Orca Agents.app`, outside the world's app roots, and the helper's bundle
  id is not recorded. `c`'s app is Orca by its bundle id hint (`hostDetect.ts detectApp`). With no app for the client
  the tmux pane carries none, so a tap runs `switch-client -c <the client used last> -t <c's pane>` (`tmux.ts` focus),
  not `select-window ; select-pane` (that path is the Linux one, where the client's app is Orca). On a real Mac it
  depends on the helper's bundle id (Open question 2). The `open` check's new `pane` part takes either command: both
  make `c`'s pane the one tmux shows in that tab.
- **Windows: O11 does not run.** tmux runs only inside WSL there (`cli/AGENTS.md`, the devices row); an agent in WSL
  hooks to WSL's own Harness, never to the Windows devices, and the Windows devices find no tmux. A modelled tmux on
  win32 would be invented behavior, so O11's `platforms` are `['darwin', 'linux']`, the world never installs tmux on
  win32, and `a/win32/O11/*` leave the baseline at the regeneration.
- **Tier B: O11 runs in tier A alone (Open question 1).** Tier B's `c` is not in a tmux pane: `appEvalOrca.ts
  personsTmux` makes a detached session (no client) on the daemon's private server, and `c`'s hooks run in the Orca host
  stand-in's runner (`orcaHost.ts`). So the devices' lookup finds tmux did not make its terminal: no nest, Orca by the
  bundle id, a ring that passes by another path, and a tap whose tmux pane is refused (`checkedPane`) with no Orca
  switch, a failure of the model, not the product. Nor does Orca's rig record tmux runs (only an iTerm2 rig's daemon
  runs the recording tmux, `appEvalDriver.ts ownRig`). Precedent: the chats' scenarios are tier A alone
  (`orcaScenarios.ts CHATS_TIERS`). `b/darwin/O11/*` leave the baseline at the regeneration.
- **The tap's order is the spec's:** Orca switches to `c`'s placed terminal, tmux shows `c`'s pane, Orca comes forward.
  The check grades each part, not their order between Orca and tmux (as iTerm2's `open` does). Whether the placed
  switch runs before tmux's move is the run's to show (Task 5's run): a part at 0 stops the task, it is not "fixed" by
  weakening the check.
- **The voice step needs the face on `c`:** a tap does not move the face (`loopbackDial.ts tap`), so after the tap the
  person turns the dial to `c` (a swipe, labelled `face`, which also ends the tap's window), then speaks, as O10 does.
