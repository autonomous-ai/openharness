## Current priority (15 November, continuation)

anh Dee clarified: the core is the heart of the product and must be small, tight and stable. Features belong in
subcomponents and subprocesses, can be switched on or off, and can develop independently. Core completion is the
priority; Browser feature work and polish are secondary. He also requested parallel agents, with in-session
subagents by default. Each agent keeps its original task; finish and close it before assigning a new task to a new
agent. The coordinator owns integration, reviews, CI and merges.

Core completion means:

- Feature implementations and heavy engine work are outside the default core's eager import closure. Core keeps
  agent/session authority and durable state, terminal I/O, input ordering, and generic bounded IPC/routing. Declared
  contracts do not justify loading their implementations. Report the actual files/lines and remaining imports.
- A component switched off, killed, hung, restarted or sending a malformed/oversized reply leaves core and unrelated
  agents working. Queues, waits, replay and restart recovery are bounded; unavailable evidence stays unknown.
- Core performs no synchronous whole-history reads, shell/version probes or lock waits. Keep crash safety and
  cross-process exclusion while moving their blocking work; measure the affected workload before and after.
- Changes preserve the last 30 days of contracts and stored data. Retained inline compatibility is explicit, kept
  outside the default load, and dated from supported builds. The earlier Harness OS/inline exception is a residual
  to review against this target, not evidence that feature isolation is finished.
- Architecture/lean-entry checks, behavior goldens, failure-injection tests, required coverage, relevant platform
  checks and independent review pass before merge. A feature's own completion is not required to make its boundary safe.

Current execution order: security and secret reads (6), live engine processing (5), blocking core work (9), engine
setup/file writes (8), then the remaining core dependencies and routes. Browser extraction continues only where it
removes a core dependency or fixes a regression already introduced by that extraction; no Browser feature expansion.
The numeric package labels below are stable references, not a requirement to finish feature work first.

   separate worktrees; keep heavy tests and measurements within machine capacity, and integrate one reviewed PR at a time.
2. Read, in this order: the rules below, the package's section here, its rows in the audit, and its notes file in
   [2026-11-15-core-plan/](2026-11-15-core-plan/). If it has a branch, fetch it (`git fetch origin <branch>`). Helpers
   are in its `tools/`: `coreCount.mjs` (the core's files and lines, as the architecture test counts them),
   `closure.mjs` (the core's closure with a door shut or open) and `workspacesGitFacts.e2e.ts` (package 4's rig).
3. Work in a worktree of your own from current `origin/main`. Start from the package's branch if it has one: merge
   `origin/main` into it first, and let `src/architecture.spec.ts` judge the core's file list.
4. One pull request per step. The pull request also marks its step done here: the status, its number, and the core's
   files and lines after it.
5. Merge as the root `AGENTS.md` says (`make merge-pr ARGS="N --reviewed-head SHA --reviewed-base SHA --merge"`, from a
   clean checkout at the reviewed head), once `ci/required` passes and an independent review found nothing left.
6. Out of tokens in the middle of a step: commit what you have with a "WIP" subject, push the branch (no pull request),
   write what is done and what is left in the package's notes file, and set its status here in your next change.

## Rules for every package

The rule that decides most questions (`cli/AGENTS.md`, "Protect the core", rule 7): **the core grows nothing for a
component.** A component works through what the core offers every client and service: the local API the apps use
(which a component's process may open as this computer's owner's tool, `agentClient/daemon.ts`) and `CoreApi`. Where
that is not enough, it does the work in its own process, or does without. No rule, list, record or mechanism goes into
the core for one component, not even a generic one only it would use. A generic piece that replaces several
per-service ports with one shape is fine, and is the usual way out. It lands with at least two of its users and
deletes their old ports in the same pull request.

Also read: the root `AGENTS.md`, `cli/AGENTS.md`, `cli/src/core/AGENTS.md`, `cli/src/services/AGENTS.md`.

- **Tests.** A test written first fails without the change: show it red, then green, in the pull request. Test where
  the behaviour lives. No fixed sleeps. What moves to a service fails without the core going down: copy the patterns
  of `e2e/serviceProcesses.e2e.ts`.
- **Compatibility.** Public clients and stored data from the last 30 days keep working. Private worker composition
  is positively admitted: a new core under a retained master without that guarantee refuses before runtime effects,
  and the existing pending-update probation restores the previous complete runtime. A retained new master runs a
  positively supported old bundle only in that bundle's own inline composition, from its verified execution payload.
  This replaces the unrestricted private new-core/old-master promise; it does not retire public client contracts.
  A shim for an old public build carries its removal date. Data on disk that moves states its migration and rollback.
- **The core's process.** `architecture.coreFiles.txt` lists every file it loads. A file that leaves deletes its line,
  and `architecture.spec.ts` and `leanEntry.spec.ts` must pass. Say the core's files and lines before and after.
- **Hot paths** (terminal I/O, frames, idle daemon work, attach, every registry save) show numbers before and after on
  the same workload.
- **Gates.** `npx tsc --noEmit -p .` in `cli/`; `npm run test:core` (`src/core` and `src/services` at 100% per file);
  the gates `python3 scripts/local-checks.py --list <paths>` names; the e2e files that cover what moved
  (`npx vitest run --config vitest.e2e.config.ts e2e/<file>`). Never against the person's own daemon (port 18473),
  `~/.claude`, `~/.codex` or their tmux server.
- **Before the pull request:** commit; run `python3 scripts/local-checks.py --run --base origin/main` from the clean
  committed head; put its receipt fence in the body; run `/code-review high` on your own diff and fix what it finds.
  Reviews found real bugs in every core pull request so far.
- **The body:** what changed and why, in plain short words; the red-then-green output; the core's files and lines
  before and after; the receipts; the platforms.

## Lessons from the earlier moves

Each line is a real bug that a review or an e2e run found.

- A move adds a hop. Measure the core's CPU per byte or per frame before and after on the same workload: the first
  browser-stream move decoded and re-made every frame and cost the core 80% more; framing once in the service and
  passing the bytes through unread brought it back to parity.
- The core keeps its own bounds on what a service sends it: an open timeout, an unread-bytes cap, a failed input ends
  the stream. Never lean on the service's bounds.
- Moving a request to a service makes "not answered" reachable for every caller: grep every asker and make each read
  no answer as unknown, never as "none" or "false".
- When the core comes to depend on a service inside a multi-step operation, ask the service before the first
  irreversible step.
- A wait that moves from the core into the edge host still blocks every service there: keep it short.
- A compatibility fallback keyed on "the field is null" also fires for a new peer that says null on purpose: key it on
  the field being absent.
- A port member that throws for an expected refusal counts against the service and can switch it off: answer true or
  false instead.
- A loose read of a file another reader checks strictly is a behaviour change: keep the checked read and load it on
  demand (`await import`), which `leanEntry.spec.ts` allows.
- Use the existing connection-closed signal (`onConnectionClosed` in `services/process.ts`), not a second one.
- Name a core-to-service request after its port member, as `services/AGENTS.md` says.
- An e2e run without `E2E_BUNDLE=1` runs the sources live: never edit the CLI's sources while one runs, and never run
  `tsc`, vitest or a second e2e beside it. Timing cases fail under your own load.
- CI reads the pull request's body from the event: put the receipts in the body before the push it judges. Push the
  final head, wait until its CI run exists, then `gh pr ready`.
- Real Podman runs only in CI (`gh workflow run cli-e2e.yml --ref <branch> -f agent_browser_podman=true`): one run, only
  when needed.
- Already failing on main's local e2e, not yours: `sandbox.e2e.ts`, `agentClient.e2e.ts` folder trust,
  `agentBrowser.e2e.ts` window size, `hermesAdmission.e2e.ts` (2). Compare a failure against main before blaming a
  change.

### 2026-11-18 Design: private worker admission and immutable execution

The master owns a cohort of session core and optional workers. Its selected bundle is separate from the code
of the master itself. Changing that selection reaps the old workers even when this Node cannot replace the
master, its unproven replacement limit has been reached, or rollback selects the master's own original bundle.
A normal core restart on the same admitted selection keeps surviving workers. Failure of a worker still costs
only that worker; admission never waits for every optional feature to become healthy.

The probe reports an executed private contract and a literal host/capability plan stamp. A test computes the
stamp from the complete canonical host definitions and capability versions, so changes cannot quietly leave
it stale. The entry guard loads only these literals and generic process/file checks, before configuration,
core composition or any service runner. No feature catalogue, feature policy or new feature state enters core.
A breaking private worker protocol change bumps this contract. A compatible artifact is allowed; this stamp
is not a claim that the executed bytes equal the bytes currently named by mutable `cli.js`.

A pathname hash alone is insufficient: publication can change B to an unguarded old C before Node opens it,
then restore B before the new guard reads it. Packaged children and their probe therefore execute one claimed,
immutable payload through the existing lean store. The payload combines verified embedded lean files and a
full CLI snapshot. The probe uses that full snapshot. Modern lean failure falls back to the same frozen full
CLI, never to mutable canonical CLI bytes. A retained legacy core requires its verified lean core entry,
which preserves original-CLI identity; if that proof is absent the master must replace itself successfully
or refuse the combination. This is the narrow admission exception to lean being only an optimization.
The retained historical runtime has zero feature workers. Its existing master-owned updater remains a
supervision process on the same frozen **full** payload, with `HARNESSD_UPDATES=master`; it never falls back
to the old core's updater-beside launch on canonical mutable CLI. The supported protocol 5–7 updater targets
`env.ADAPTER_CLI_DIR` (and Windows `cliDir/currentCli`), not its execution pathname. The historical baseline
`acbfb09ede` and subsequent updater changes preserve that identity and the staged IPC contract.

The original CLI pathname remains the identity used by helpers, hooks, commands, installed-copy checks and
update configuration. It is supplied explicitly to both lean and modern full-snapshot entries before those
modules load. Execution identity is separate: the entry checks its actual artifact path and expected private
contract/plan. Source and unbundled developer entries keep the same before-effects contract guard and do not
participate in installed bundle publication.

The artifact owner holds at most one unreleased candidate plus the master's existing lean claim. Preparation
never drops an active claim. Full-file reads, decompression and the file list have explicit caps before
allocation: 128 MiB for full CLI bytes and inflated lean JSON, 8,192 lean files. The measured frozen maxima
are 12,467,909 CLI bytes, 12,609,846 inflated bytes and 471 files. The reserved full-snapshot filename cannot
collide with a lean entry. Failed release keeps ownership and prevents a new candidate; unresolved failed
publication cleanup similarly refuses subsequent preparation. Canonical and entry fingerprinting retain
the shared 64 KiB buffer but enforce the same 128 MiB descriptor cap before reading, hash exactly the
declared size and check one byte for growth. Nonregular leaves are refused before opening; supported POSIX
opens also use nonblocking mode before descriptor validation. Windows admits regular disk-file publication,
with a regular-leaf preflight and descriptor check, not arbitrary device/pipe paths. An uncertain close
latches refusal until process restart and never retries that fd. These are byte/memory bounds, not wall-time
guarantees for filesystem I/O, with no idle/reconnect hashing. Existing cached members are compared by the
same bounded streaming hash against verified bytes, avoiding whole reads of an oversized corrupt cache.
Files publish atomically through the existing store; no new index, datastore, polling loop or
process framework is introduced. The existing cleaner protects other live masters and observes its recent
artifact grace; a bounded keep entry protects this master's still-used image. The live-claim bound is distinct
from shared store retention. Stopping, refusal and rollback release claims only after actual child and probe
reaping. A crash leaves the existing dead-PID claims for cleanup. A probe deadline requests termination but
never treats an unreaped process as gone.

| Supervisor and selection | Admitted behavior |
| --- | --- |
| Old master and old runtime | Existing complete old runtime. |
| Old master successfully replaces itself on new bundle | New master admits its own worker cohort. |
| Old master kept while new core is selected | New entry refuses before effects; pending update restores old runtime. |
| New retained master, matching modern contract and plan | Reap prior cohort, probe frozen payload and start the admitted cohort. |
| New retained master, different modern contract or plan | Refuse; pending update restores the previous selection. |
| New retained master, supported old bundle | Exact successful historical protocol 5–7 probe plus verified legacy lean core; own inline composition, no feature workers, and the master-owned updater on the same frozen full payload. |
| Return to the master's original bundle | Still reap any different child cohort first. |
| Failed, missing, malformed, oversized or unknown proof | Never infer compatibility or legacy mode. Pending update restores; an unsupported manual replacement stays stopped with a named bounded retry state. |

The historical inline contract is a positive supported protocol record, not an absent modern marker or a
version-string/date guess. Probe output is bounded. A fresh deliberate Windows `none` choice is marked and
preserved through modern handover. An old Windows master wrote unmarked `none` automatically, so a legacy
handover recomputes the new platform default instead of treating that inherited value as deliberate consent.
A supervisor-selected legacy layout is never a new-core fallback.

Replacement-master execution is a separate boundary: POSIX exec and Windows launch still select the canonical
CLI so historical master/helper identity remains correct. The probe does **not** claim those master bytes
are pinned across publication. A modern replacement validates and freezes its own selected child cohort;
compatible executed semantics may admit it, while a different plan refuses. If B/C/B publication loads an
older unguarded master, a modern child refuses its missing cohort envelope before effects and pending
probation restores the complete old runtime. The strict extraction invariant is therefore no admitted modern
core with unproven historical workers, not byte identity of the replacement master. Final startup acceptance
must include the composite folder's full CLI snapshot (about 12 MB) in each pre-spawn folder scan; no speed
improvement is claimed without that measurement.
The original `startMasterFromBundle` optimization still reads the selected CLI whole before entering this
new child-artifact owner. Its allocation is an explicit pre-existing residual; this design does not claim
all startup allocations are bounded. The source/decode, canonical fingerprint, claimed child fingerprint
and cached-member comparison bounds above apply to the new admission path.

Only private code metadata and existing cache/claim files are stored. No user data format, client protocol,
service token authority, migration or release rollback data changes. Public clients remain supported for the
existing window. The master and entry logs use fixed actionable admission reasons, with no request content.
Validation must include old/new/kept/rollback combinations, actual reap ordering, cancelled/expired probes,
nonpending no-spawn refusal, B/C/B publication, helper identity, all entry paths, per-file coverage, native
Windows/macOS/Linux and final startup cost. Design approval is not a claim that those gates have passed.

### 2026-11-18 Design: keep preparation allocations out of the master

Evidence
The exact helper-only diagnostic reproduced the failing master's resident growth without loading a daemon:
plain39.70 ->143.18MiB at return (143.48next turn); instrumented source52.90, inflated90.05,
parsed126.72, buffers138.73, published143.48MiB. Preparation~287-291ms;486files; both actual0 and clean.
The native master155.46MiB failure is real. The per-file map/handle return does not retain payloads,
but temporary JSON/Brotli/string/Buffer allocation commits pages to the long-lived master's allocator.
No GC, delay or relaxed100MiB limit is proposed.

One recommended path
Move ONLY existing createExecutionArtifacts.prepare work to one short-lived child; keep the existing
store, claim format, hashes, limits, parser and publication logic. The master retains only returned path/hash
metadata and its release handle. This works on cold startup AND retained-master upgrade/rollback/Windows.
It does not add a service, service catalogue entry, network, persistent index, public protocol or feature code.

Executed preparer code
- Bundle the existing three-module helper closure plus a small strict request/result wrapper at build time.
  Use the build's existing esbuild/define mechanism (already embeds scripts), shared by build.mjs/build-bundle.mjs.
- Embed that bounded plain source literal in the master's own code (build gate <=128KiB; exact closure gate).
- Run named managed Node with fixed --input-type=module, deliver literal code through owned stdin, then EOF.
  Prepend a bounded JSON data constant holding source/directory/expected/parentPID/keepMasterEntry. No outside
  string becomes executable source: JSON.stringify encodes the fixed-shape data object. No shell, -e/Windows
  command-line-size dependency, mutable script execution, install-side helper or broad artifact store.
- Code is the executed master's literal, so no circular need to trust/decode the selected CLI before preparing it.
  Source-dev execution still has no packaged owner. The helper is generic supervision, not an experiment.

Ownership and success sequence
1. Existing reexec transition stops/reaps prior core/services, then releases the prior candidate claim.
2. Start exactly one preparer using the SAME bounded capture/kill/actual-close primitive as runProbe. Extend that
   existing primitive minimally for stdin and typed stdout; do not introduce a second process-owner framework.
3. Child validates fixed request shape/bounds and parentPID===process.ppid. It calls existing helper with pid=parent
   and original-master keep claim. Full source hashing/regular descriptor/128MiB limits, bounded Brotli/JSON/file
   count, reserved name, atomic publication and claim safeguards stay in that helper unchanged.
4. Child emits one bounded metadata record (<=4KiB), never code/content. It intentionally leaves the parent's
   successful candidate claim held. Parent waits for actual child close/EOF before accepting it; all child
   allocator pages/descriptors then belong to a process that has ended.
5. Parent validates exact shape, selected identity, folder hash, fixed entry names, hashes and optional lean-field
   relationships, derives all paths from its own directory/canonical request, and creates a release-only handle using existing claim release, and independently
   validates immutable full/lean bytes as today. The actual selected-bundle probe then runs on that full snapshot.
6. Existing positive worker admission, staged-path drift checks, service/core startup and actual-reap release follow.
   The candidate is held between preparation, probe, admission, child use and real reaping exactly as now.

Async integration / lifetime
- Master prepareExecution becomes an owned async preparation; candidate remains distinct from admitted Cohort.
- Reexec's preparation stage accepts an owned task {result,cancel}, matching its existing probe structure. Track it
  through cancel/settled so master shutdown cannot release/start/exit past an un-reaped preparer.
- Failed POSIX exec reacquisition also awaits the same preparation before late path drift/admission checks.
- No-PID synchronous/asynchronous failure produces no fake handle; existing unsupported/pending restore/backoff applies.
- Deadline/cancel sends a termination request only. PID-bearing errors and deadlines retain ownership until actual close.

Failure and bounded leftovers
- Named ordinary helper failures carry only an allowlisted code. Existing helper rollback and claim cleanup logic remain.
- Success transfers one complete claimed image; adoption failure, malformed/oversized/no reply or abrupt preparer death
  cannot prove what was published. Latch parent preparation as unsettled, retain any parent claim/scratch, refuse any
  further candidate, log fixed restart guidance. At most one unknown attempt per supervisor; no retry accumulation.
- Existing cleanup_unsettled/source-close uncertainty remain strict restart outcomes. The child ending closes its OS
  descriptors, but this patch does not broaden recovery policy or silently delete uncertain publication claims.
- Existing cleaner reclaims a dead parent's claims on subsequent start. Never delete a live foreign claim or original
  master's claim. Normal shutdown stops/reaps preparer before exiting; timeout is never a claim-release proof.
- This costs one temporary generic child per actual candidate preparation, not on idle/reconnect/same-cohort crash.
  No descendant probe: preparer exits before the separately owned actual bundle probe starts.

Minimal file/API boundary
- executionArtifacts.ts: retain synchronous writer for child/tests; expose a strict release-only metadata adoption helper
  sharing the existing claim-release semantics (no decode/buffer retention in parent).
- small harnessd preparation wrapper/parent adapter; reuse extracted raw capture part of reexec.runProbe rather than
  duplicate lifecycle. Keep child-only decode module out of the parent's normal execution/import closure where possible.
- master.ts/reexec.ts/masterProcess.ts: inject owned async preparation, cancellation/settled and failed-exec reacquisition.
- shared build helper + both existing builders: embed bounded preparer literal and gate exact generic source closure.
- tests/Design amend the allocation/lifetime contract. No feature-worker files or public wire changes.

Rejected smaller alternatives
- Only move first preparation before initial exec: retained no-exec/limit/Windows selections still inflate the master;
  it solves one test while preserving the actual lifetime cause.
- Reassign/null buffers or wait for idle/GC: already separate activation, no retained payload handle; allocator pages
  remain as measured, and explicit GC/sleeps are disallowed.
- Streaming decoder rewrite: would replace the bounded existing native JSON/Brotli parser with a new parser/format and
  legacy compatibility burden. It is substantially broader than isolating this already-owned bounded operation.
- Reuse only the original lean folder: does not cover a newly selected/legacy payload and cannot substitute mutable
  CLI execution. The verified immutable full snapshot and exact selected probe must remain.

Selected proof before claiming fix
RED: owner does not admit/release while preparer still alive; cancellation/error/oversized/invalid stdout holds/latches;
no-PID no spawn; parent PID/shape/path/manifest refusal; legacy/modern helper parity and actual child closure;
