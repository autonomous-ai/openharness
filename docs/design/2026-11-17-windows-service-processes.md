Observed boundary
The existing core already listens on a random per-start authenticated named pipe; localWsServer verifies that request and proves the 101 response before it admits the unchanged service role/master token. No new listener, core API, service list, credential, or core state is needed. masterEnv forces HARNESSD_SERVICES=none on Windows; startServiceProcess refuses normal services without unixSocketPath; runServiceProcess dials only ws+unix. Those three assumptions are the transport gap.

Implementation
1. Preserve explicit HARNESSD_SERVICES=none and the existing Unix no-socket fallback. Default Windows masterEnv leaves the environment unchanged, permitting the existing ServiceSupervisor plan. No new switch. No spawn or shutdown mechanism changes: existing hidden Windows master, ordinary inherited-console children, hostServices shutdown-by-message, existing supervised stop/reap/backoff remain owners.
2. startServiceProcess allows Windows normal services even before the core has published its daemon record. Its existing socketPath field remains '' on Windows; no per-runner mechanical plumbing or stored pipe path. The updater continues to need no core endpoint. Unix no-socket refusal stays unchanged.
3. The default service-side connector uses the already-loaded config/env ADAPTER_DATA_DIR and configured PORT on Windows, then existing daemonPipe -> pipeWebSocket. Each actual reconnect reads the record/token again; nothing pins a pipe name or token across core restarts. Unix still opens the identical ws+unix URL. The injected connect callback becomes sync-or-async with an AbortSignal, preserving existing synchronous fixtures. The connector lives in a small services module and is not imported by core.
4. One endpoint discovery Promise per host process is shared only while it is actually in flight, then cleared. This avoids twenty edge services simultaneously launching the same 3-second bounded Windows process-table proof. It is not a TTL cache: every next connection wave rereads record/token/liveness, and each socket gets its own nonce. No map, idle poll, credential in env, or persistent state. Stop/timeout never clears a still-running shared lookup and starts another. A caller checks its abort after discovery before constructing the WebSocket.
5. runServiceProcess keeps one connection attempt at a time. Its connection deadline covers lookup, WebSocket opening, and service 'connected'. A 10-second deadline logs SERVICE_CONNECT_TIMEOUT, aborts discovery for that caller and terminates an obtained socket; a late socket is terminated and never receives machine_select. Reconnect is scheduled only after actual lookup settlement/socket close, through existing 250ms->5s backoff (REFUSED remains >=60s). Stop clears the timer, aborts the attempt, and prevents late attachment/reconnect. All sync/async connector failures use a fixed SERVICE_CONNECT_UNAVAILABLE log, never the error's path, token or personal contents. Emit once per unsuccessful period, reset after connected. Existing lifetime retries continue while supervised; no per-request retry is added.
6. Current-connection fencing applies to all socket listeners. Late open/message/close of an invalidated socket cannot send the service token, answer a request through a replacement connection, or clear it. Outstanding queries reject and routed requests abort when that connection actually ends, as before. The connected deadline adds no timer after successful registration and no steady-state work.
7. Documentation updates explain default Windows process isolation and the explicit inline/no-master exceptions. No claim of actual Windows acceptance from platform-injected tests.

Authentication and privacy
Use daemonPipe's existing bounded record/token validation and recorded-process proof. Pipe paths remain restricted to local \\.\pipe\harness-<id>, never SMB/TCP. A server with no proof is terminated before WebSocket open, so it gets no master token or application frame. Service-role admission still requires the boot's separate master token. Both checks are required. daemon-token remains the same owner-protected existing file; no new secret export. HMAC nonce binds to the per-core pipe id, so old proof/replay cannot authenticate the next core. Tests record only counts/booleans, no token/path/personal frame logs.

Compatibility / unresolved release-admission prerequisite
New master/new core/new workers: pipe transport. New worker/old core that already serves authenticated pipe: unchanged local WS and service-role wire work when the old core's master service list names the worker. Old Windows master/new core: old master explicitly says none, so current servicesTheMasterRuns keeps the existing inline compatibility path until a successful full master replacement; the new core must not silently override its parent. Explicit inline and HARNESS_NO_MASTER stay unchanged.
A new Windows master retained while rollback selects an OLD worker bundle is unsafe if that worker still rejects no Unix socket. Existing reexec returns kept before stopChildren for unproven-limit/no-handover; several failed handover cases also restart children using the selected script. Therefore removing default inline is NOT accepted for release solely by this transport patch. Root's separate generic positive bundle/worker freshness task must prevent an incompatible new-master/old-worker launch or keep the previous compatible bundle until a safe supervised handover. Do not add a Windows-only core fallback, duplicate service host, version-string guess, or reinterpret timeout as unsupported. Transport implementation/tests can proceed independently; enabling default Windows in the final release remains held on the explicit old/new/kept/rollback matrix. The coordinating reviewer approved including the default-enable diff on the held integration branch; it must not ship before that freshness and rollback acceptance.

Design checklist
Growth: no durable data; one discovery Promise per process and one attempt/timer/socket per known service. All released at actual settlement/close; retained unresolved attempt cannot admit another. Existing service request limits unchanged.
Concurrency: original attempt identity + AbortSignal and original socket; no shared connection authority. Token and endpoint rediscovered; each connection authenticates separately.
Read cost: startup/reconnect only, fixed existing record/token/liveness reads; concurrent services in one host share actual in-flight discovery. Nothing while connected/idle. Unix path unchanged. Compare connection setup CPU/RSS/latency and process count on Windows; whole-daemon acceptance is root-owned.
Scale: existing finite SERVICE_HOSTS/services bounds; at 10x reconnect activity there remains one discovery in flight per host and one attempt per service. Metrics first: connect failures/timeouts and connect latency; no identifiers/content. Existing service status is unavailable until its connection is accepted.
Compatibility: unchanged published WS/service schemas and existing private files. Current, prior-30-day, rollback and retained-master cases described above; no fallback after ambiguous failure.
Migration/rollback: no stored-user-data migration. Endpoint record remains existing per-start record, owned by core. Rollback must satisfy generic freshness prerequisite before default-enable ships. Old/new readers unchanged.
Audience: existing pipe HMAC + master token. No broader local/TCP trust.
Identity: same OS owner, same machine service role; no guest/login fallback.
Failure: endpoint missing/stale/proof failure/timeouts => named unavailable and bounded reconnect, no inline/TCP fallback. Core and ordinary terminal input survive service loss; host stops children by existing mechanism.
Platforms: affects Windows default runtime; Unix path and no-socket/debugging compatibility tested. Actual signed Windows user-session window census and separate PID/failure-isolation proof required before release. macOS authenticated socket tests cover protocol behavior only.

Implementation notes and validation (2026-11-17)

The implementation changes masterEnv and the service bootstrap only to allow the Windows process plan; it adds services/localConnection.ts and bounded asynchronous connection ownership to services/process.ts. No runtime file under core/ changed. The service-side response path also checks its original socket before delivering a completed asynchronous answer, and ignores late events from retired sockets. One redundant dial guard was removed: dial is called only initially or by the single reconnect timer, which stop cancels; ended alone schedules that timer after actual ownership settlement.

Nine caller regressions failed first on the unchanged base (six connection ownership/deadline tests and three Windows startup assertions). Final focused validation passed 257 tests in 12 files, including the real local WebSocket service door and existing pipe auth tests. The two affected services runtime files each reached 100% statements, branches, functions and lines (combined 276/183/53/199); typecheck and architecture/environment/startEnvironment checks passed. Protocol fixtures ran over private authenticated Unix sockets on macOS x64 with Node 24.22.2, not over Windows named pipes. No existing threshold or timing limit was loosened, and no coverage exclusion or retry-to-green was used.

Actual signed Windows separate-process, hidden-window, lifecycle and cost evidence remains required. So does generic kept-master/old-worker/rollback release admission, including a new Windows master selecting an older worker bundle whose bootstrap refuses a missing Unix socket. This branch is held for those gates; the default-enable change is not a claim that the whole Windows boundary is accepted. Final integrated full-core/harnessd/native gates and release are owned by the coordinator.

A final platform audit pinned the Unix no-socket fixtures to Linux so they do not accidentally start Windows services on a Windows test host. The two affected startup spec files passed again (40/40); runtime source and the service coverage set were unchanged.
