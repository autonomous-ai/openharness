# harnessd

harnessd is the Harness daemon rebuilt around one rule: **the process that keeps your agents
reachable never fails because of a feature.** It is a small supervisor, a lean core that owns
sessions, terminals and turns, and separate service processes for everything else. The `harness`
command and every app stay clients, the way `docker` is a client of `dockerd`.

This document records the design requested on October 3, 2026, and what has been built against it.
It is the one document the rebuild is reviewed against. It changes as decisions land, and says which
ones are still open.

## Why

The daemon today is one Node process that does everything. Its startup is a single 5,200-line
function in [`cli.ts`](../../cli/src/cli.ts); [`backendSocket.ts`](../../cli/src/backendSocket.ts)
routes 54 request types for local and remote clients alike through about 30 callbacks that
`cli.ts` assigns after construction. Nearly every subsystem is constructed on every start. The
only gates are environment flags, sign-in, a connected device, or a state directory existing.

That shape turns any feature's bug into everybody's outage:

- **2026-10-03.** Opening a pane read the agent's whole transcript into memory. An 803 MB Codex
  rollout took 1.9 GB of heap on its own; the daemon died at its 4 GB limit seconds after every
  start, and every pane on the machine dropped about every ten seconds
  ([PR #705](https://github.com/autonomous-ai/openharness/pull/705)). Nothing restarted it but the
  desktop app running `harness start` again, up to a minute later.
- Optional features run inside the process that holds the sessions: the USB dial's `ioreg` probe
  every 2 s whether or not a dial was ever plugged in, warm `claude`/`codex` recap workers that the
  default recap mode never uses, the search indexer over every transcript, one viewer process per
  harness, headless Chrome for shared viewers, a 15 s backend poll for tab channels, and a
  10-minute check that keeps the managed `grid` on its pin.
- Work grows with history, not activity. Besides attach, whole histories are read by a client's
  `session_get` (before it windows) and `sessions_list` (to count lines), every engine's recap but
  Claude Code's and Codex's, the Cursor watcher, the first search pass, Change agent's handoff, the
  Codex resume repair, and the database engines' first load: OpenCode, Kilo, Hermes and Devin read
  every message of a session in one synchronous query on the core's event loop.

[PR #684](https://github.com/autonomous-ai/openharness/pull/684) moved Companions and Memory out
as a library. harnessd finishes that direction for the whole daemon and gives the extracted parts
somewhere to run.

## Rules

1. **Stability first.** No feature runs in the process that owns sessions. A service can crash,
   hang or leak without dropping a pane, losing a question or blocking input.
2. **Work follows activity, never history.** No hot path (attach, a request, a turn ending) may
   read in proportion to a conversation's length. Reads are bounded and streamed; caches have
   budgets; queues have limits.
3. **Nothing waits on a service.** The core starts, serves and stops without any service. An
   unavailable service fails only its own capability, with a retryable error.
4. **One contract, narrow authority.** Services use the same authorized local API clients use,
   with a scoped role. No unrestricted extension RPC; every addition to the contract is reviewed
   on its own ([CONTRIBUTING.md](../../CONTRIBUTING.md)).
5. **Port proven logic.** The normalizers, tmux handling and transport carry hundreds of measured
   fixes. The architecture is rebuilt; that logic moves with its tests.
6. **No flag day.** The desktop app, web, phone, `hn`, engine hooks, the device and the backend
   keep working throughout. Protocol changes are additive.
7. **Learn from the daemons that work.** Where a well-run daemon has solved a problem we have, we
   take its answer unless we can say why ours differs ([What other daemons do](#appendix-what-other-daemons-do)).

**The master** ([`harnessd/supervisor.ts`](../../cli/src/harnessd/supervisor.ts)) is the process
`harness start` launches (`harness __harnessd`). It claims the pid file, keeps its children running
and stops them. It contains no feature code, opens no network connection and holds no sockets, so
there is almost nothing in it that can fail. It is generic: it knows a service by its manifest
entry, not by what it does.

**The core** owns everything a session needs and nothing else, and it binds the listening sockets
itself. Passing them through the master would buy a refused connection's worth of time during a
core restart, which every client already retries, at the price of complexity in the one process that
must stay simple; on Linux, systemd socket activation can hold them later without the master doing
anything (see [Supervision](#supervision)). If the core crashes, hangs or outgrows its memory budget,
the master starts a new one. Clients reconnect as they do today; agents keep running throughout,
because they live in tmux, not in the daemon. A core whose master is gone stops, so nothing is left
holding the port.

**Services** are separate processes, each started from the same bundle as `harnessd <service>`
with its own process title. Each connects to the core's local socket like any other client, under
the service role, and reconnects with backoff when the core restarts. A service never writes to
tmux, never reads the registry file, and never holds a credential the core can hold for it.
Isolating a feature costs a process: an idle Node process is about 40 MiB, and one that loads
today's 4.4 MB bundle peaks near 125 MiB. So the risky services — relay, devices, viewers, search,
models — get their own processes, and the light ones share one host.

## Services

### Relay — anyone can host one

The relay service connects this machine to its phone, the web and other machines through a relay
server. Harness runs one (`harness-api.autonomous.ai`), and the server's code is in this repository
(`backend/`), so anyone can run their own and point their machines and apps at it.

- **End-to-end encryption makes the server untrusted by design.** Sessions travel sealed between
  paired devices (CPace pairing, the trust group); the relay forwards frames it cannot read. Trust
  comes from pairing, not from whoever runs the server.
- **The address is a setting everywhere.** The daemon reads it from `BACKEND_WS_URL` and `WEB_URL`
  today; it becomes a `harness` setting and a field in the desktop app, and the phone's QR
  onboarding carries it, so a phone paired to a self-hosted relay never asks Harness for anything.
- **Sign-in is pluggable.** A Harness account is the default. A self-hosted relay can use its own
  accounts (OIDC) or none: paired device keys are already an identity the trust group verifies.
- **Features are capabilities the relay advertises.** Forwarding, presence and pairing rendezvous
  are the minimum. Desk sync, the Store, tab channels, shares and the device key log are optional,
  and the apps hide what a relay does not offer instead of failing.
- **The protocol is documented** — `adapter-ws` for machines, `web-ws`, `device-ws` and
  `observer-ws` for clients — with versioned frames, and TURN for peer-to-peer terminals is
  configurable.

### Devices — a host for drivers

The round unit is the first device type, not the only one. The devices service hosts one driver
per device type: `usb-dial` (the round unit over USB serial), `autonomous-device` (Wi-Fi and LAN),
and whatever comes next. A driver finds its devices, owns their transport — one owner per physical
port — and speaks to the core only through the local API: agent, turn and question events in;
input, answers and agent actions out. Firmware push, the dial↔window bridge and the voice router are
shared utilities drivers use. Adding a device type adds a driver and its manifest capabilities;
the core does not change.

**From today's code to there** (mapped on 2026-10-04). The device code is about 7,200 lines:
`cable/` 5,800, `device/` 1,200 and `devices/` 100, beside about 6,000 lines of tests. Another 400
lines wire it inside `runForeground`. Every call the core makes into it is guarded already
(`outsideConsumers('devices')`), so an exception there costs one call. A native crash in the serial
port code, or a leak, would still cost the whole core. Three couplings decide the order:

1. **The dial's host also routed turns between machines** (until D0). ⌘K and the window's voice
   route sent a turn through `DaemonCableHost.sendTurn`. It knew a local agent from a remote one by
   the agent lists it learned from the fleet (`DeviceFleet` over `DeviceLink`, the lane to the
   owner's other machines). With the dial off, ⌘K would have answered "no agent list yet". So the
   router, and the fleet and machine list it reads, left the dial's host first, as a fleet service of
   their own that ⌘K and the dial both use.
2. **The Wi-Fi device rides the relay's encrypted sessions.** `AutonomousDeviceService` and
   `AutonomousDeviceDirect` pair, attach and receive through `BackendSocket`, so they move with the
   relay, after it has a boundary of its own.
3. **The window bridges are the desk's, not a driver's.** Selection, visit, form and the voice route
   are shared by the dial, the Wi-Fi device and ⌘K. They stay in the core, and drivers reach them
   through `CoreApi`.

### Models

Grid is how Harness runs local AI models with Codex, Claude Code and the other engines, from the
app. It is essential, so it starts by default, but it runs as its own service: a failed model
download or a crashed local model server must never take sessions down with it.

### Workspaces

Everything about the folder an agent works in: worktrees (created with their branch, the ignored files
`.worktreeinclude` names copied in), project folders and their pre-trust, git and PR status, file and
media previews. It runs on the machine that holds the folders, because a phone or another computer
can start an agent there, but not in the core: preparing a folder fetches, checks out and copies, and
is slow and can fail. A client asks workspaces for a folder, then creates the agent in it; the core
only ever receives a path. Cleaning up is the person's decision, made in the app with a preview —
workspaces lists what is left and removes what it is asked to, to the Trash
([#711](https://github.com/autonomous-ai/openharness/issues/711)).

### Companion and Memory

Both are a package since #684, and nothing starts them today. In harnessd they are two services
that are off until used, and Memory never depends on Companion.

## The local API

The core serves the contract documented in [cli.md](../cli.md#automation): a `machine_select`
frame, then request frames with a `requestId` answered by `<type>_result`, events for agents,
turns and activity, and the binary terminal channel. Nothing about it changes for existing
clients.

Services use the same socket and frames with three narrow additions, each reviewed on its own:

- **A service role in `machine_select`** (`role: "service"`, its name and a per-boot token the
  master passes it). The token proves the process is the one the master started; it grants only
  the capabilities its manifest entry lists.
- **Request ownership.** A service declares the request types it answers (`search` answers
  `session_search` and `session_tail`). The core routes those requests to it and returns its
  answer. If the service is down, the client gets `SERVICE_UNAVAILABLE` with `retryable: true`
  instead of a hang. Security checks (owner-only, sealed-only, local-only) run in the core before
  any routing, so moving a handler can never widen who may call it.
- **Scoped reads.** Services that need more than events get bounded reads, never a file path:
  `transcript_read` returns at most a window of one agent's transcript from an offset, and only
  to a service whose manifest grants it.

Events reach services through the same subscription clients use, with bounded queues. A slow
subscriber's queue is cut at its limit and it is sent `resync`; the core never blocks on it.

Clients and the daemon agree on a version range: an app newer or older than the daemon is told
so, the way the Docker CLI negotiates its API version and `tailscale` warns when the daemon differs.

## Supervision

Built for the core ([`harnessd/`](../../cli/src/harnessd/), spawn protocol 2): readiness apart from
binding, with a start-up deadline; the heartbeat watch; the exit-code contract; exit reasons;
crash-loop safe mode; the heap and resident budgets; the status file; log trimming in the master; and
updates with probation from ready and rollback — a broken update that falls into safe mode rolls back
too. `HARNESS_NO_MASTER=1` runs the core on its own; `harness start -f` runs the master in the foreground,
as launchd and systemd do. A core on its own (that switch, or a core an older release's own handoff
started) hands an update to a master on the new build, which judges it (`core/updateHandoff.ts`); it no
longer spawns and judges a core like itself. What follows is the design the master is held to;
the parts still to build say so.

- **Ready is not bound.** The core says `bound` when its port is listening and `ready` when start-up
  is done and the request gate opens. Start-up has a deadline: a core that binds but is not ready in
  time is killed and counted as a crash, because a start-up that hangs after binding otherwise looks
  healthy for ever while every request waits at the gate. Probation for an update counts from
  `ready`. A core from before `ready` (protocol 1, after a rollback) is held to `bound` alone.
- **Alive is more than a timer.** The heartbeat proves the event loop turns; it also carries the
  longest event-loop delay since the last one, and next the age of the oldest waiting request, so a
  core that is slow to the point of useless is seen before it is hung. Every child's last exit is
  recorded with its reason: crashed, hung, did not bind, not ready, memory, update, stopped.
- **Exit codes are a contract.** 75 restarts at once onto the bundle on disk (an update). 78 means
  stop for good — this computer was removed from the account, or it is connected from another one —
  and the master stops with it. Any other exit, 0 included, is a crash and is restarted: Node also
  exits 0 when its event loop runs out of work, and an outside SIGTERM to the core must not take the
  daemon down.
- **Backoff that forgives, and a way out of a loop.** Restarts back off from 0.5 s to 30 s and the
  delay resets after a minute up, timed on a monotonic clock so sleep and clock changes do not skew
  it. Three crashes inside five minutes start the core in safe mode — the updater alone, so a
  published fix can still arrive — instead of the same crash again. When safe mode's own time runs
  out (15 minutes, counted while the machine is awake) the master tries a normal core again, and an
  update leaves safe mode at once. A core that falls into safe mode by itself, because its start-up
  threw, tells the master so; the master reports it, and rolls back an update whose first core does
  this. Chrome and VS Code break their loops the same way.
- **Memory: a clean restart before a fatal one.** The core runs with an explicit V8 heap limit, and
  the master restarts it cleanly when its heap passes 75% of that limit, or its resident memory
  passes a larger ceiling that also covers buffers V8 does not count. With the two limits equal, V8's
  own out-of-memory abort — which skips every cleanup — would come first, as it did on October 3.
- **Status without the core.** The master writes a status file (each child's state, restarts, last
  exit and its reason, safe mode) atomically on every change, so `harness status` can say what
  happened when nobody can ask a core that is crash-looping.
- **Logs have caps.** The master trims the daemon's log, which a supervised core no longer does
  itself; per-process files come next with their own caps, written by the master as each child's
  stdio so no line is lost in a pipe.
- **Ordered stop, deadlines owned by the master.** Services, then the core, then the master, each
  with a deadline the master enforces; `harness stop` waits for the master instead of killing it
  after a fixed three seconds. A fast stop leaves agents running in tmux; that is the only kind.
- **Updates.** The core's updater stages a bundle and exits 75; the master restarts the core on it,
  on probation from `ready`, and rolls back if it fails. When the master's own code changed, it
  re-executes itself in the gap between the old core's exit and the new core's start, as Syncthing's
  monitor does — re-executing with a core running would cost that core its channel. Built
  (`harnessd/reexec.ts`): in place, keeping its pid, so launchd, systemd, the pid file and the app's
  owner check never see the master change; a probe of the bundle's own master first; a marker that
  rolls back a master that died after re-executing. A newer build staged while the last is still on
  probation is judged on its own, and a master that starts on an update no master finished judging
  (it died mid-update) judges it. Next: bundles move to versioned directories behind one pointer, so a
  swap is one rename. A version that was rolled back is not offered again.
- **Something supervises the supervisor.** On macOS a launchd user agent (registered through
  `SMAppService`, which asks the user once) and on Linux a systemd user unit run the master in the
  foreground and restart it; the desktop app then watches instead of respawning, so there is one
  supervisor per machine. tmux must stay out of the daemon's process group and cgroup — a systemd
  stop kills everything in the unit's cgroup by default, and launchd kills a dead job's process
  group — so agents keep running when the daemon stops, the way containerd shims keep containers.
  Built as an opt-in, `harness service install` (see Rollout); not installed by default, and the
  desktop app still runs `harness start`, which then goes through the platform.
- **Versioned spawn protocol.** Master and core may differ during an update. Messages are only ever
  added, unknown ones are ignored, and each side states its protocol in its first message.

For services the master reads a manifest bundled with the release:

```json
{ "name": "devices", "args": ["service", "devices"], "enabled": "auto",
  "memoryMiB": 256, "capabilities": ["events:agents", "events:turns", "requests:dial_*"] }
```

- **Start.** The core first, then enabled services, without waiting on any of them. `enabled` is
  on, off, or auto (a probe the service runs itself and exits cleanly from when it has nothing to
  do, such as no device ever paired).
- **Restart.** Exponential backoff from 1 s to 60 s. After five crashes in ten minutes a service
  is parked as failed and reported, never respawned in a tight loop, and retried slowly and after
  every update. The core is always restarted.
- **Budgets.** Every child runs with an explicit heap limit from its manifest and the memory rules
  above.
- **Lifetime.** Children watch their spawn channel and exit when the master goes, so a crash
  never leaves orphans holding the socket, the serial port or a pid file.

## Bounded work

Every read on a hot path is bounded by what it serves, never by a conversation's length. Built:

- **Attach** walks back from the end of a transcript to the last turn opener and streams forward
  from there ([`attachTranscript.ts`](../../cli/src/lib/attachTranscript.ts), merged in #705). It
  reaches past the opener only for the few older records the chips, a continuing `/goal` and calls
  still answering need, at most 64 MiB. A session attached again while it is tailed hands its tail
  over byte-exact.
- **History pages** (`session_get`) are read by walking back from their cursor to the turn they
  start in, holding only the page, at most 32 MiB; a line index kept as the file grows counts lines
  (`sessions_list`) and finds Codex's line cursors ([`transcriptPages.ts`](../../cli/src/lib/transcriptPages.ts)).
- **The live tail** reads what it fell behind on a chunk at a time, and a file rewritten in place
  with more history than one batch should hold is attached again from its end instead of replayed.

Claude Code and Codex are done. The order for the rest is OpenCode, Grok, pi, then every other
engine; database engines follow the same rule with a query for the last turn instead of the whole
message list, and their reads move off the event loop. A test fails the build if core code makes a
whole-file read (`tailFile(…, Infinity)`, `readFile` on a transcript, an unbounded
`createReadStream`) of an agent's history.

## Rollout

Each step ships on its own, keeps every client working, and can be turned back by configuration
while it beds in.

Done so far:

  a private tmux server, fake Claude Code and Codex engines that bind through the real hooks, and a
  client that speaks the desktop's protocol. It reproduced the October 3 crash on `main` and found
  three more defects, now fixed and kept as tests.
- **The master** at 100% coverage, tested end to end: crash, hang, a start-up that hangs after
  binding, a SIGTERM from outside, a crash loop into safe mode and out again, killed master, clean
  stop inside `harness stop`'s grace, memory budget with backoff, and the status file throughout.

- **Bounded reads for Claude Code and Codex:** attach (#705, merged), history pages and line counts,

- **The recap model mode is gone,** with its warm worker pool: a recap is the answer's own excerpt.

  again; a newer build moves past it, and `harness update` installs it on purpose. Before, a release

  guarded and answered with a fallback declared beside the port's contract, so the funnel, restore

  process started on the whole 4.4 MB cli.js: at idle, from the bundle, the master took 164 MiB resident

  Each master claims the folder it runs from, and a folder is removed only once no live master claims

  service starts from cli.js whenever its master's lean files are gone or changed, cli.js is no longer

  (`cli/src/config/envFields.ts`), which every process loads and which cost each 15 to 19 MiB. The CLI

    agents outliving stop and uninstall, and a killed master restarted. A tmux server in a scope of its
    own (`systemd-run --user --scope`) would make stop jobs safe as well: a core change, still open.
  - Tested against a temporary home and fake `launchctl` and `systemctl` alone on PATH, never the real
    ones; `plutil -lint` checks the plist, and `systemd-analyze verify` the unit where it exists.
    `e2e/cli.e2e.ts` runs `harness start`, `stop` and `status` from the installed bundle on the managed
    Node: without the service no platform tool is asked and an agent outlives a stop in tmux; with it,
    fakes that run the master from the definition (both platforms, on any computer, through
    `HARNESSD_TEST_PLATFORM`) see start and stop go through them; another data folder's definition is
    ignored.

- **The master re-executes itself on the bundle on disk** (`cli/src/harnessd/reexec.ts`, at 100%).
  Before, an update replaced the core and left the master on its old code until something restarted
  it. Now, in the gap before any core starts (an update's exit 75, a rollback, a bundle replaced by
  hand), a master whose code is not the bundle on disk replaces itself with it (`process.execve`).
  - In place, not by handing over to a fresh master: launchd and systemd follow the pid they started,
    and to them a master that exits is a job that ended; the pid file, `harness stop` and the desktop
    app's owner check follow it too. Only in the gap, with the services stopped and reaped first: no
    core loses its channel and nothing is orphaned. The agents live in tmux, out of reach of it all.
  - The state handed on (`HARNESSD_RESUME`, kept from every child): restarts, the last exit, the update
    on probation, the pid file's claim, and re-executions since a core last came up (after three, the
    master keeps its code). The status and `/api/status` gain the master's version and that count.
  - Exec gives up the old master as a fallback, so: a probe (`harness __harnessd-probe`) asks the
    bundle's own master first, and one that fails it fails the update, rolled back and remembered in
    `update-rejected.json` like a failing core; a bundle from before this answers "Unknown command"
    and is never started as a probe. And a marker (`harnessd-reexec.json`), removed once the new
    master's first core is up: a master that starts and finds one left by a process that is gone rolls
    back and moves onto the bundle before. Without `process.execve` (before Node 22.15 and 23.11) the
    master keeps its code, as before.
  - `e2e/reexec.e2e.ts`, on real bundles: the pid stays through every swap while the master's version
    follows the bundle; the core and an agent at work carry on; a build whose master fails its probe is
    rolled back and not staged again; one whose master dies after re-executing is rolled back at the
    next start; every core is the master's child throughout. With a released bundle
    (`MIGRATION_FROM`): an older master supervises the newer core an update brings until it restarts,
    and this master runs an older bundle's core without re-executing on it.
  - Round 40 (`e2e/updateHostile.e2e.ts`, on real bundles): the update path under hostile conditions,
    since it is how every fix reaches every machine. A link that drops mid-download, a download cut
    short, a release published broken, a manifest whose hash or version lies, a newer build published
    while the last is on probation, an update with both agents mid-turn, a build whose master answers
    its probe but whose core crashes at start, and a master killed mid-update. After each, the daemon
    runs a working build under its master, both agents are back and take a turn, nothing is left in the
    install or the data folder, and a build that failed here is remembered. Defects found and fixed:
    - A newer build staged while the last was still on probation, or still starting, was taken for that
      update failing: rolled back, and remembered as bad. A fix published soon after a release was
      refused that way by every machine still judging the release. The master now judges the newer
      build on its own when the bundle on disk changed since the core started (`SupervisorDeps.bundle`).
    - A manifest naming an older build's bytes under a newer version installed it; it came up, still
      reported the older version, and installed itself again, a restart a minute. The canary now
      requires the version the manifest names (`scripts/upload-cli.sh` already checks the same).
    - A build that failed its canary, or whose bytes did not match the manifest, was downloaded again
      at every check: 13 downloads in 13 seconds at a one-second interval, once a minute on every
      machine in production. Such a build now waits two intervals, then four, eight, up to an hour; a
      new entry in the manifest is tried at once, and a dropped link at the next check.
    - A master killed mid-update (a crash, a kill, a power cut) left the update unjudged: the next
      start ran it unwatched, and a build whose core crashes at start crash-looped for good, with no
      updater running to fix it. `update-pending.json` now records the sha256 of the cli.js it put in
      place, and a fresh master started on that bundle puts its first core on probation.

    With `DISKFULL=1` the install and the data folder share a 96 MB disk image, filled while the build
    downloads, between the canary and the swap (the test holds the spawn lock the updater waits on),
    just after the swap, and while a build that crashes is rolled back. More defects, all fixed:
    - Staging was not all or nothing: a write that failed left its temporary file (up to a whole
      bundle, on a disk already full) behind, package.json was rewritten in place, and a failure after
      cli.js was swapped left a mixed bundle with no pending note, which the retry then backed up over
      the old build's backup. Everything new is now written beside what it replaces first, and only
      renames touch what runs; backups are hard links, so a swap needs room for one copy, not two.
    - The spawn lock's owner record, cut short by a full disk, was never reclaimed: every update, start
      and stop after it waited 45 seconds and gave up, long after the space came back. The writer
      removes its own lock, and a record that names no one is debris after five seconds.
    - The master's re-execution marker, unwritable on a full disk, threw out of a promise and would
      end the master between cores. It keeps its code instead, and judges the new bundle itself.
    - A canary that could not be written was reported as the build failing; it is now retried at the
      next check without downloading again. A rollback that could not write the rejected list forgot
      the build (the rollback frees the room the list needs, so this takes a disk filled again at
      once, as by a log storm); its pending note now names the build until the list can be written.

    Left after round 40, and fixed since (round 40b), each with a test that fails without it:
    - A core that could not start for want of room on its disk (`listen ENOSPC` claiming its socket) was
      read as the new build failing: rolled back, the rollback freeing the room the build before needed,
      and a good build remembered as bad. A failure that names the disk (`ENOSPC`, `EDQUOT`, `EROFS`) is
      no verdict on the build now: the master keeps the update on trial and starts the core again,
      backing off, without counting it as a crash (`namesTheDisk`, harnessd/supervisor.ts). End to end,
      the build staged just before the disk filled is kept once there is room, nothing rejected.
    - A handoff whose teardown threw stayed on the old build, its servers half closed, the new bundle
      staged and never judged. The handoff is its own core module now (core/updateHandoff.ts, out of
      `runForeground`, 89 lines shorter): under harnessd every step is tried, one that fails is said
      and passed, one that hangs is given up on after 15 s, and the core exits 75 regardless. End to end,
      a build whose teardown throws still hands over, and the next build is kept.
    - Downloads had no deadline of their own: a link that stalled without dropping held the check on
      undici's five-minute body timeout, and a trickle for as long as it lasted. A transfer now gives up
      after a minute without a byte or a quarter of an hour in all (`ADAPTER_UPDATE_IDLE_MS`,
      `ADAPTER_UPDATE_DEADLINE_MS`; the manifest at most 30 s and a minute), and the next check tries
      again. End to end, a download that stalls halfway is given up on and the build lands.
    - A turn that ended while the disk was full, on a data folder that had never run a project, was lost:
      `OrchestratorService.roleOf`, asked at every turn's end, makes its state folder to read it, and the
      mkdir threw out of the transcript's line handler; once open, the orchestrator watches every frame
      sent, and the same mkdir threw out of every send after it. Neither depends on it now: a role that
      cannot be read is anyone's (core/turns/recaps.ts), and a frame goes out whatever the orchestrator
      makes of it (`BackendSocket.send`). End to end in `e2e/diskfull.e2e.ts`.

    Left, larger:
    - The manifest is not signed. Its sha256s are only as good as the TLS connection to the manifest
      host: one that served a matching manifest and bundle would be installed, its canary run first.
      Signing needs a release key and its public half pinned in the bundle.
    - A master that dies while a disk-starved update waits for room leaves its re-execution marker, and
      the next start rolls the update back as a re-execution that never came up.
    - Bundles in versioned directories behind one pointer (above) would make the swap a single rename.
    - After the release (the orchestrator is out of scope until then): `OrchestratorService` should read
      its state without making its folder, which only its first save needs.

### The core boundary, step by step

`runForeground` is 5,306 lines. About 4,600 of them move into modules under `cli/src/core/`. What
stays, about 700 lines, is the composition root: the guards and updaters that must run first, the
terminal backend, `BackendSocket` and its gate, the hook server and pid file, the boot sequence
(restore, then the first reconcile), restart-for-update and shutdown, and `openRequests`, `ready`
last. `startupOrder.spec.ts` already pins those in place.

Each module is a factory, `createX(deps)`, that returns closures, the pattern
`createStopAgentService` already uses.

| Module | What moves into it |
|---|---|
| `terminals/control` | Control leases, capture, submit, type, keys, pinning |
| `terminals/bootstrap` | The tmux backend, terminals, the host theme, pane titles |
| `agents/events` | Session sync and announcements |
| `transcripts/normalizers` | The 14 per-engine normalizer and reader maps, as one table |
| `transcripts/attach`, `ingest` | Attach, the attach tracker, watcher wiring, line ingest |
| `turns/funnel` | The one place session events fan out from |
| `turns/*` | Heartbeats, recaps, stop hooks, runtime profiles, reconcile timers |
| `input` | The input controller and the pane writer lock |
| `questions` | The question watcher, answers, open questions |
| `agents/*` | Forget, bind, discovery, launch; create, fork, retarget, restart, resume, stop, close, purge |
| `engines/hooks` | Hook handlers and hook installs |
| `api` | `CoreApi`, `CorePorts`, and binding `BackendSocket` |

Two typed interfaces replace the 53 callback assignments on `BackendSocket`:

- **`CoreApi`, services to core:** agents (list, resolve, create, fork), input (submit, cancel),
  questions (answer, open), recaps (recent turns, asks), runtime profiles (models, set), and events
  (agent, question, turn, stream, delivery). Each member is an existing request or event. There is
  no generic `call(name, args)`.
- **`CorePorts`, core to services, in process only:** the synchronous calls the core makes into
  features today: audience (which devices are watching), teams, devices, search, models, viewers
  and workspaces. Each port is a contract decision to make before its service leaves the process.

The order. Each step moves code verbatim and keeps the old names as aliases, so call sites and the
start-up lint stay as they are; each is checked by `tsc`, the unit suites and the e2e suite.

1. A spec that pins the start-up order: requests held from construction, every port bound before
   `openRequests`, then `ready`, then `[cli] ready`.
2. Terminal control.
3. Session events.
4. The normalizer table.
5. Input, with the pane writer lock.
6. Questions.
7. Heartbeats, activity and recaps.
8. The event funnel.
9. Attach, ingest and the stop hooks.
10. Agent discovery and binding.
11. The agent lifecycle.
12. Engine hooks.
13. Services in process, each behind `start(core, ports)`: search, viewers, models, workspaces and
    the teams; the devices guarded where the core calls them. Relay, sharing and the devices move
    with the next phase, into processes of their own.
14. Every slot `BackendSocket` calls into the core through is bound, and stays so:
    `socketBindings.spec.ts` reads the class's slots and fails on any that `cli.ts` leaves unbound
    (three are unbound on purpose, each with its reason). The bindings stay where start-up puts
    them: gathering them into one call would reorder a start-up `startupOrder.spec.ts` pins, for
    nothing a test cannot give.

What has to survive the move exactly:

- **The funnel's order.** Each event goes to the backend, then search, input, teams, the pane
  writer, devices, the heartbeat and the question watcher, in that order. Recaps come after the
  loop, and the devices stream comes last and never on replay. A bus that notified subscribers
  afterwards would reorder frames.
- **The input, pane writer and turns cycle.** Every pane write goes through the device input lock,
  which calls back into input, which re-enters the funnel. They move together.
- **Start-up windows.** Hooks arrive before the request gate opens and are not gated. Stopped-agent
  frames are published during restore, outside the gate, so their providers must be bound before
  restore. Relay callbacks are bound after `connect()` today, which is safe only because nothing
  awaits in between; they move before it.
- **Log lines that tests read:** `[cli] ready`, `transcript rewritten in place — attaching it
  again`, `[backend] machine busy`.

    - purged, after which search no longer finds it and its transcripts are gone.

    No defect was found.
  - Scale (`e2e/scale.e2e.ts`, `SCALE_AGENTS`). Many agents, half of each engine, are created at once,
    take a turn each, go through a restart and come back.
    - 24 agents: the core went from 219 MiB empty to 230 MiB after the restart, and all were back in 4.6 s.
    - 50 agents, the design's bar: the core went from 222 MiB to 268 MiB, and all were back in 8.3 s.
  - Part 22, found by the seventeenth round (`e2e/machine.e2e.ts`): what the machine does to the
    daemon. Two defects:
    - A dead tmux server went unnoticed. tmux says "no server" two ways. One of them, `error
      connecting to <socket> (No such file or directory)`, is what `kill-server`, a tmux crash and a
      reboot all leave, and it was read as "tmux unavailable". So the daemon never took an agent off,
      and the apps showed dead agents as active until a new server happened to start.
    - A restore replayed recent turns live. After a daemon restart, a restored agent whose transcript
      was under ten minutes old had its turns sent out again as live, with their notifications. The
      first-turn rule excused a resume but not a restore. An attach that takes a relaunch mark now
      never replays live.

    After a reboot, the daemon brings every agent back on its own, with its conversation.
  - Part 23, found by the eighteenth round (`e2e/diskfull.e2e.ts`, `DISKFULL=1`): the data folder on
    a 64 MB disk image of its own, filled while agents work. Two defects:
    - A rename the daemon answered while the disk was full was lost to a restart that came before the
      next rename. Names were written only on a rename; a failed names write is now tried again on
      every save.
    - Saving the resume record threw out of a binding after the agent was bound, so the windows never
      heard of it. The record is best effort there; a stop still saves first and refuses on failure.

    The core never restarted, and agents kept taking turns throughout.
  - The nineteenth round (`e2e/folders.e2e.ts`), for both engines:
    - folders named with spaces, quotes, `$HOME` and backticks, accents and emoji: each holds an
      agent that works, comes back after a restart and is closed;
    - a folder deleted under a running agent, or while the daemon is down: it costs that agent at
      most.

    No defect was found.
  - The twentieth round (`e2e/frozen.e2e.ts`): an engine stopped (SIGSTOP) rather than exited.
    - A message sent to it is taken once when it wakes, and the other agents go on meanwhile.
    - A cancel leaves it able to work.
    - A stop does not wait on it forever.

    No defect was found.
  - The thirty-fourth round (`e2e/relay.e2e.ts`): the relay link under stress, as a phone sees it. A
    phone is paired with a signed-in daemon and reaches it through the fake backend's blind relay
    (`e2e/harness/fakeBackend.ts`, `e2e/harness/relayPhone.ts`, the CLI's own relay client role).
    The relay drops mid-turn and comes back, the backend restarts, the relay is slow by seconds, it
    sends garbage or replays old sealed frames, and the daemon restarts while the phone is connected.
    Every message is in the phone's re-read history once, nothing announces a turn it has already
    read, and a message tried with no session is refused at once. Found and fixed:
    - A broadcast the relay replayed into a client's next session opened as news, because the replay
      record for the machine's group key was the session's. The CLI's relay client now carries it from
      one session to the next (`lib/e2ee/relayClient.ts`, `lib/remoteRelay.ts`).
    - A frame a client sealed for a session the daemon no longer had was dropped without a word: a
      message vanished, and a request waited out its timeout. That happens when the daemon restarted
      while the relay kept the client's socket, as the phone app does. The daemon now answers
      `e2e_session_unknown`, naming the frame (terminal bytes by their clear kind and counter), and the
      CLI's relay client opens a new session on it.

    Left, larger: no message is acknowledged end to end, so one lost inside the relay is found only by
    reading the conversation again; and the phone app has both of the above to learn.
  - Every request the apps send is answered: all 39 of the desktop's, all 21 of the phone's and all 20
    of hn's, checked against the daemon's sources.
    - The desktop's `lessons` is answered `UNSUPPORTED` on purpose, for a feature not yet built.
    - hn's `terminal_remain` is a feature of hn's own local shells.
    - hn's `terminal_info` had never been answered, and is now (part of the comparison above).

## Testing

The bar for the core is total: 100% statements, branches, functions and lines, enforced in its
vitest configuration, as the orchestrator, sharing and resume suites already do.

- **Engine conformance, for every agent we support.** Each engine has a suite that checks attach
  and history pages against the whole-history reads they replace at every cut point, its turn
  lifecycle, questions and model chips, on fixtures, plus an opt-in run against a machine's own
  transcripts (`ATTACH_REAL_TRANSCRIPTS=1` today for Claude Code and Codex), plus the real-CLI
  checks for installed engines (`test:tmux-real`).
- **End to end, out of process.** The harness boots the master, core and services under a throwaway
  home and a private tmux server, drives them with a client that speaks the desktop's protocol, and
  runs scripted engines that write transcripts and call hooks: create, stream, type, deliver,
  question, answer, turn end, recap, restart, resume, stop.
- **Failure.** Kill, hang and overload each service and the core under load: crash loops, a start-up
  that hangs after binding, a heap that grows to its limit. Panes, questions and input must stay
  within an agreed baseline, and nothing respawns in a loop. Corrupt each state file, fill the disk,
  stall a subscriber.
- **Budgets as tests.** The regression from October 3 is a permanent test: a transcript larger than
  the heap, attached, paged and rewritten in place, and 50 panes attaching at once, under a fixed
  memory and time budget. A soak run holds a desk of agents for hours and fails on memory growth.
- **The apps.** The desktop app against harnessd in an isolated profile, never against the
  person's own harnesses.

## Open decisions

- **Platform supervision by default.** Whether the launchd agent and systemd unit are installed on
  every install, which on macOS asks the user once (Login Items).
- **tmux server.** Agents on the user's default tmux server, or a dedicated one that `tmux
  kill-server` cannot reach; and under systemd, whether the core starts it in a scope of its own, so a
  stop job on the unit no longer reaches the panes (see Rollout, platform supervision).
- **Service defaults.** Which services start on a new install and which wait to be needed (a device
  paired, sharing used, a viewer installed), and which light ones share the host.
- **Safe mode.** Whether three crashes in five minutes is the right trigger, and what a degraded core
  keeps beyond the updater.
- **A healthy update.** Ready plus a number of crash-free minutes, or a first successful attach.
- **The relay protocol's stability promise,** once self-hosting is documented.
- **State directory.** Whether moving to `~/.harness/harnessd/` is worth its migration at all.

## Appendix: what other daemons do

Studied on October 4, 2026, from each project's own documentation and source. The decisions above
cite what they take from here.

### Erlang/OTP supervisors

- **A restart strategy for each group.** `one_for_one` restarts only the failed child; `one_for_all` and `rest_for_one` also restart its dependents ([OTP](https://www.erlang.org/doc/system/sup_princ.html)).
- **Intensity and period.** More than MaxR restarts in MaxT seconds and the supervisor stops its children and itself; its parent decides what happens next. Default: 1 restart in 5 s.
- **Limits multiply across levels:** "do not set the restart intensities to the same values on all levels".
- **`transient` children** are restarted only after an abnormal exit. Children stop in reverse start order, each with its own timeout.

### systemd

- **Exit codes are a contract** (`RestartForceExitStatus=`, `SuccessExitStatus=`). Exponential restart delay arrived in version 254, but it does not reset after a healthy run ([systemd.service](https://man7.org/linux/man-pages/man5/systemd.service.5.html), [#43813](https://github.com/systemd/systemd/issues/43813)).
- **Start limit.** By default a unit started more than 5 times in 10 s is no longer restarted automatically ([systemd.unit](https://man7.org/linux/man-pages/man5/systemd.unit.5.html), [defaults](https://man7.org/linux/man-pages/man5/systemd-system.conf.5.html)).
- **Readiness and liveness are separate signals.** `READY=1` means start-up is done. `WATCHDOG=1` is sent from the event loop every half `WatchdogSec`; a missed one means SIGABRT ([sd_notify](https://man7.org/linux/man-pages/man3/sd_notify.3.html), [watchdog](http://0pointer.de/blog/projects/watchdog.html)).
- **Sockets outlive the service.** "If a service dies its listening socket stays around, not losing a single message" ([socket activation](http://0pointer.de/blog/projects/socket-activation.html)). `FDSTORE=1` keeps other fds across restarts ([sd_listen_fds](https://man7.org/linux/man-pages/man3/sd_listen_fds.3.html)).
- **Memory limits.** `MemoryHigh=` slows a unit down and `MemoryMax=` triggers the OOM killer inside it ([resource-control](https://man7.org/linux/man-pages/man5/systemd.resource-control.5.html)). User units can use both ([user@.service](https://github.com/systemd/systemd/blob/main/units/user%40.service.in)). By default, stopping a unit kills everything in its cgroup ([systemd.kill](https://man7.org/linux/man-pages/man5/systemd.kill.5.html)).

### launchd

- **User agents** run while their user is logged in, and they must not daemonize: "If you do, launchd thinks your process has died" ([Apple](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)).
- **`KeepAlive`** can restart a job after a clean exit, a crash, or both. By default a job is spawned at most once every 10 s (`ThrottleInterval`) ([launchd.plist](https://keith.github.io/xcode-man-pages/launchd.plist.5.html), Apple's man page).
- **Sockets** are created by launchd, and the job collects them with `launch_activate_socket(3)`.
- **`ProcessType` Background** jobs get resource limits; Interactive jobs do not. By default launchd kills a dead job's process group.
- **`SMAppService`** (macOS 13+) registers an agent shipped inside the app bundle, "subject to user approval" ([SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), [agent](https://developer.apple.com/documentation/servicemanagement/smappservice/agent(plistname:))).

### nginx

- **The master does the privileged setup** (config, ports) and manages workers, which "do all of the work" ([NGINX](https://blog.nginx.org/blog/inside-nginx-how-we-designed-for-performance-scale)).
- **Signals control it.** TERM is a fast stop, QUIT a graceful one, HUP reloads, USR1 reopens logs and USR2 loads a new binary ([control](https://nginx.org/en/docs/control.html)). A graceful stop has a time limit ([worker_shutdown_timeout](https://nginx.org/en/docs/ngx_core_module.html#worker_shutdown_timeout)).
- **Reload validates first.** If the new config fails, nginx "rolls back changes and continues to work with old configuration".
- **An upgrade keeps the old master as the rollback.** It starts the new binary but keeps its own listening sockets open, so it can bring its workers back if the new one misbehaves.

### PostgreSQL postmaster

- **The supervisor keeps away from shared state.** It "as a rule does not touch" shared memory, so a backend crash can't take it down ([postmaster.c](https://github.com/postgres/postgres/blob/master/src/backend/postmaster/postmaster.c)).
- **One crash resets everything.** The postmaster stops the other children and reinitializes ([restart_after_crash](https://www.postgresql.org/docs/current/runtime-config-error-handling.html)).
- **Children watch a pipe** to notice when the postmaster dies. There are three stop modes: smart, fast and immediate ([shutdown](https://www.postgresql.org/docs/current/server-shutdown.html)).
- **The OOM killer must not pick the supervisor.** The postmaster gets `oom_score_adj` −1000 and its children 0 ([docs](https://www.postgresql.org/docs/current/kernel-resources.html)).

### Syncthing

- **A monitor process restarts the real one.** Exit code 3 means restart and 4 means upgrade ([docs](https://docs.syncthing.net/users/syncthing.html)).
- **Loop guard.** After 4 restarts within 60 s, the monitor gives up ([monitor.go](https://github.com/syncthing/syncthing/blob/main/cmd/syncthing/monitor.go)).
- **Upgrade.** When the child exits with "upgrade", the monitor `exec`s the new binary, which starts the new child. Panics go to a panic log; logs rotate by size and count.
- **Under systemd:** `--no-restart`, `RestartForceExitStatus=3 4`, and `StartLimitBurst=4` in 60 s ([unit](https://github.com/syncthing/syncthing/blob/main/etc/linux-systemd/user/syncthing.service)).

### Docker and containerd

- **Live-restore:** "containers remain running if the daemon becomes unavailable". It only works across patch releases, and a full 64K log FIFO blocks containers ([live-restore](https://docs.docker.com/engine/daemon/live-restore/)).
- **Shims are the containers' parents.** containerd reconnects to them at boot and cleans up any it can no longer reach ([runtime v2](https://github.com/containerd/containerd/blob/main/docs/runtime-v2.md)).
- **The unit files let workloads survive:** `KillMode=process` ("kill only the docker process, not all processes in the cgroup"), a negative `OOMScoreAdjust`, and socket activation ([docker.service](https://github.com/moby/moby/blob/master/contrib/init/systemd/docker.service), [containerd.service](https://github.com/containerd/containerd/blob/main/containerd.service)).
- **Version skew is planned for:** the API version is negotiated ([Engine API](https://docs.docker.com/reference/api/engine/)), and unknown shim extensions are ignored.
- **Logs:** the `local` driver caps them at 100 MB per container ([local](https://docs.docker.com/engine/logging/drivers/local/)); `json-file` does not ([json-file](https://docs.docker.com/engine/logging/drivers/json-file/)).

### Chrome

- **The network service runs in its own process**, which is "preferred for isolation and stability". After a crash it is restarted and clients reconnect ([network service](https://chromium.googlesource.com/chromium/src/+/main/services/network/README.md)).
- **It degrades instead of looping.** About 3 GPU-process crashes switch Chrome to a more stable mode, and one crash is forgiven every 5 minutes ([fallback](https://chromium.googlesource.com/chromium/src/+/main/content/browser/gpu/fallback.md), [gpu_process_host.cc](https://chromium.googlesource.com/chromium/src/+/main/content/browser/gpu/gpu_process_host.cc)).
- **The number of processes depends on available memory** ([process model](https://chromium.googlesource.com/chromium/src/+/main/docs/process_model_and_site_isolation.md)).

### VS Code

- **Extensions run together in a separate extension host process** (one per local, web or remote host), each loaded only when needed ([docs](https://vscode-docs.readthedocs.io/en/stable/extensions/our-approach/), [extension host](https://code.visualstudio.com/api/advanced-topics/extension-host)).
- **Crash budget:** automatic restarts until 3 crashes in 5 minutes, then a Restart button ([source](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/services/extensions/common/abstractExtensionService.ts)).
- **Terminals live in a pty host process** that survives window reloads ([1.54](https://code.visualstudio.com/updates/v1_54)): a 5 s heartbeat, a second timer against false alarms after sleep, and capped restarts (`MaxRestarts = 5`) ([terminal.ts](https://github.com/microsoft/vscode/blob/main/src/vs/platform/terminal/common/terminal.ts), [ptyHostService.ts](https://github.com/microsoft/vscode/blob/main/src/vs/platform/terminal/node/ptyHostService.ts)).
- **Agent sessions live in one Agent Host** and are "not tied to the lifetime of the window"; clients replay missed actions on reconnect ([agent host](https://code.visualstudio.com/docs/agents/concepts/agent-host), [blog](https://code.visualstudio.com/blogs/2026/08/26/agent-host-architecture)).

### tmux

- **One server owns all sessions.** Clients connect to it over a socket, and `-L` or `-S` runs a separate server ([tmux(1)](https://man.openbsd.org/tmux.1)).
- **The server daemonizes** (`daemon(3)`), leaving its launcher's process group ([proc.c](https://github.com/tmux/tmux/blob/master/proc.c)).
- **The protocol version is strict.** A client built for a different version gets "protocol version mismatch" ([client.c](https://github.com/tmux/tmux/blob/master/client.c)).

### PM2

- **Backoff that forgives:** delays grow to 15 s and reset after 30 s of uptime ([restart strategies](https://pm2.keymetrics.io/docs/usage/restart-strategies/)). After 16 unstable restarts the app is marked "errored" ([ecosystem](https://pm2.keymetrics.io/docs/usage/application-declaration/)). Memory is checked every 30 s.
- **The app says when it is ready.** `wait_ready` waits for `process.send('ready')`. Stopping sends SIGINT, then SIGKILL after 1.6 s ([signals](https://pm2.keymetrics.io/docs/usage/signals-clean-restart/)).
- **Zero-downtime reload** in cluster mode, where the Node cluster primary owns the port and accepts connections for the workers ([cluster](https://pm2.keymetrics.io/docs/usage/cluster-mode/), [Node](https://nodejs.org/api/cluster.html)).
- **Logs don't rotate by default** ([logs](https://pm2.keymetrics.io/docs/usage/log-management/)). `pm2 startup` leaves boot to systemd or launchd ([startup](https://pm2.keymetrics.io/docs/usage/startup/)).

### s6, runit, daemontools

- **One tiny supervisor per service**, waiting at least a second between restarts ([s6-supervise](https://skarnet.org/software/s6/s6-supervise.html), [runsv](http://smarden.org/runit/runsv.8.html), [supervise](https://cr.yp.to/daemontools/supervise.html)).
- **State is kept in files.** The supervisor writes `supervise/status`, which `svstat` reads.
- **Readiness is reported explicitly.** The daemon writes a newline to `notification-fd`, because started is not the same as ready ([notifywhenup](https://skarnet.org/software/s6/notifywhenup.html)).
- **The supervision tree owns the log pipe**, so restarting the service or its logger loses nothing ([s6-svscan](https://skarnet.org/software/s6/s6-svscan.html)). `s6-log` rotates by size and count ([s6-log](https://skarnet.org/software/s6/s6-log.html)).

### Tailscale (tailscaled)

- **Supervised by systemd:** `Type=notify`, `Restart=on-failure`, a private state directory ([unit](https://github.com/tailscale/tailscale/blob/main/cmd/tailscaled/tailscaled.service)).
- **State is written atomically:** write a temp file, sync it, rename it ([atomicfile](https://github.com/tailscale/tailscale/blob/main/atomicfile/atomicfile.go)).
- **The local API checks the connecting process's user** ([safesocket](https://github.com/tailscale/tailscale/blob/main/safesocket/safesocket.go)), and the CLI warns when its version differs from the daemon's ([cli.go](https://github.com/tailscale/tailscale/blob/main/cmd/tailscale/cli/cli.go)).
- **Saying ready too early is a bug.** `READY=1` once went out before the daemon could actually serve ([#11504](https://github.com/tailscale/tailscale/issues/11504)).

### Caddy, HAProxy, Kubernetes

- **Atomic reload.** "If the new config fails for any reason, the old config is rolled back into place without downtime" ([Caddy](https://caddyserver.com/docs/api)).
- **The master re-executes itself.** HAProxy's master re-execs on SIGUSR2, and with `-x` a new process takes over the old one's listening sockets so it doesn't miss new connections ([HAProxy](https://docs.haproxy.org/3.0/management.html)).
- **Three probes:** a failed liveness probe restarts the container, a failed readiness probe stops its traffic, and a startup probe holds both off until start-up finishes. Dependency checks belong in readiness ([probes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)).
- **CrashLoopBackOff:** 10 s doubling to 5 minutes, reset after 10 crash-free minutes; 30 s to stop ([pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)).
