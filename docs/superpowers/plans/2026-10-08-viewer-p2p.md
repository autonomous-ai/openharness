# Viewer Surface over P2P Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Carry viewer-surface frames and input over a second WebRTC data channel (`viewer-v1`) on the terminal's peer connection — direct, then TURN, then the existing WS long-poll — to cut interaction latency and backend relay load.

**Architecture:** The client's offer opens `viewer-v1` next to `terminal-v1`. The machine's viewers process pushes each JPEG frame as raw bytes (binary kind `viewerFrame`, split into ≤ 480 KiB parts, sealed like terminal binary) through core → gateway onto that channel, two frames in flight at most, acked by the client. Input and acks come up as sealed JSON `surface_*` frames on the same channel. The client hides all of it behind the existing `ViewerSurfaceRequest` contract, so `InteractiveViewerSession` and the widgets keep working, and anything missing (old machine, no channel, channel lost) falls back to the Phase 1 `viewer_surface` long-poll over WS.

**Tech Stack:** TypeScript/Node (vitest, `werift`) in `cli/`; Flutter/Dart in `mobile/` (`flutter_webrtc`) and the desktop web build `desktop/lib/web/` (browser `RTCPeerConnection`).

**Spec:** `docs/superpowers/specs/2026-10-08-viewer-p2p-design.md` (and Phase 1: `docs/superpowers/specs/2026-10-08-remote-browser-design.md`).

## Global Constraints

- TURN and rollout follow terminal exactly: ICE policy `all` (direct, then TURN), kill switch `TERMINAL_P2P_ROLLOUT_PERCENT`. No viewer-specific policy.
- One `RTCPeerConnection` per E2EE session; channels: `terminal-v1` (unchanged) and `viewer-v1` (ordered). Any other label is refused.
- A failure of `viewer-v1` must never demote or stop `terminal-v1`; a failure of the peer connection ends both.
- Capability: `p2pViewer: 1` in the sealed `e2e_welcome` `features`. Without it, never use `viewer-v1`.
- Binary kind `viewerFrame = 8`; part payload ≤ 480 KiB of JPEG; plain layout `streamId(16) seq(u64) part(u16) parts(u16) width(u16) height(u16) scale×100(u16) jpeg…`; `streamId` = the 32-hex `surfaceId` as 16 bytes. Sealed with the session's terminal binary key and counter (shared with terminal; replay window 4096).
- Flow control: at most 2 un-acked frames per surface; the gateway waits for the channel's `bufferedAmount` to fall below 1 MiB (5 s cap) before sending a frame's parts.
- Channel-open wait: the P2P policy's `openWaitMs` (backend `OPEN_WAIT_MS`, default 2500 ms; clients clamp ≤ 5000).
- The surface stays owner-only and keeps Phase 1's event whitelist and limits (`surfaceFrame`).
- `viewerFrame` never travels over the backend relay (the backend's kind list is unchanged); the WS fallback is Phase 1's JSON long-poll.
- Desktop and mobile Dart P2P files stay identical apart from imports; both `InteractiveViewerSession` copies stay logic-identical.
- Comments say why, in plain sentences; 100% coverage for `cli/src/core` and `cli/src/services` (`npm run test:core`); architecture rules (`cli/src/architecture.spec.ts`): the core may not import edge files (`gateway/`, `services/`, `lib/terminalP2p.ts`, `lib/interactiveViewer.ts`, …) — anything the core needs lives in `lib/gatewayWire.ts` / `lib/terminalBinary.ts` / `lib/viewerFrames.ts`.
- Repo rule: no `git commit` until the user asks — the "Commit" steps are staging points.

## Decisions taken while planning (deviations from the spec text)

- Control frame names are `surface_open`, `surface_input`, `surface_ack`, `surface_close` (up) and `surface_state`, `surface_error` (down) — the spec's `viewer_*` names collide with the HTTP viewer proxy's existing `viewer_ack`/`viewer_close` (`cli/src/lib/viewerFrames.ts`).
- `surface_state` / `surface_error` (small, not latency-critical) go down over the existing sealed relay target (`clients.viewerFrame`), not over `viewer-v1`; only frames (down) and `surface_input`/`surface_ack`/`surface_open`/`surface_close` (up) use the channel.
- The desktop native offerer (`cli/src/lib/remoteRelay.ts`) is out of this plan: desktop native shows harness viewers through the WKWebView proxy and only needs surfaces for the Phase 2 browser agent. The CLI initiator class gains `viewer-v1` support (used by the e2e harness and later by `remoteRelay`).

## Review Focus

1. **The viewer channel fails while the terminal channel is healthy** (e.g. the machine closes `viewer-v1`): the terminal must keep streaming over P2P and the viewer must fall back to WS within one poll. → Task 3 test "a viewer channel failure leaves the terminal channel up" + Task 9 test "a lost viewer channel falls back to WS".
2. **A frame bigger than one part** (dense Retina pane, ~1.5 MB JPEG): it must arrive whole, and a newer frame must replace a half-received older one. → Task 1 test "splits and reassembles a 3-part frame" + Task 8 assembler tests.
3. **The client stops acking** (app backgrounded, slow phone): the machine must stop producing frames at 2 in flight, not queue them. → Task 5 test "never more than two frames in flight".
4. **New client on an old machine / old client on a new machine:** no `p2pViewer` flag → WS long-poll exactly as Phase 1; an old client never opens `viewer-v1` → the machine never pushes. → Task 4 tests + Task 10 test "no flag, no channel use".
5. **Connection closes mid-push:** the surface is released, pending sends dropped, no timer left. → Task 5 test "closing the connection ends the push" + Task 6 test.

```ts
import { TerminalBinaryKind, type TerminalBinaryClear } from './terminalBinary.js'

/** One part's JPEG bytes: under the data channel's 512 KiB message limit once the plain header (34 bytes)
 *  and the seal (20 bytes + tag) are added. */
export const VIEWER_PART_BYTES = 480 * 1024
/** 16 parts ≈ 7.5 MB: far beyond the 4.2 Mpx cap at JPEG quality 75; anything bigger is a bug, not a frame. */
const MAX_PARTS = 16

/** A surface id the clients mint (16 random bytes as lowercase hex) in the UUID form a binary streamId takes.
 *  Any other id cannot ride the binary path and stays on the WS long-poll. */
export function surfaceStreamId(surfaceId: string): string | null {
  if (!/^[0-9a-f]{32}$/.test(surfaceId)) return null
  return `${surfaceId.slice(0, 8)}-${surfaceId.slice(8, 12)}-${surfaceId.slice(12, 16)}-${surfaceId.slice(16, 20)}-${surfaceId.slice(20)}`
}

export function splitViewerFrame(surfaceId: string, seq: number, jpeg: Uint8Array,
  meta: { width: number; height: number; scale: number }): TerminalBinaryClear[] | null {
  const streamId = surfaceStreamId(surfaceId)
  const parts = Math.ceil(jpeg.length / VIEWER_PART_BYTES)
  if (!streamId || parts === 0 || parts > MAX_PARTS) return null
  return Array.from({ length: parts }, (_, part) => ({
    kind: TerminalBinaryKind.viewerFrame, streamId, seq, compressed: false,
    bytes: jpeg.subarray(part * VIEWER_PART_BYTES, (part + 1) * VIEWER_PART_BYTES),
    viewer: { part, parts, width: meta.width, height: meta.height, scale: meta.scale },
  }))
}
```
