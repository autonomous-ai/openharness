## Backend contract (#4115)

Use existing authenticated command transport and first-load/change transport; no new poll or endpoint.

- `member.approvalMode { mode: "autoApprove" | "review" }`: the signed-in person's own preference. Absent stored preference means autoApprove. No target person id; agents cannot change it.
- `task.suggest { conversationId, agentId }`: the requesting person or that task's PM names an available, visible agent as a suggestion. This never starts work. Before the first assignment, a new suggestion on an already approved task returns it to proposal and needs the person’s fresh approval, so a lost/stopping choice cannot strand it. Person approval remains separate.
- `task.approve { conversationId }`: the requesting person approves their pending task. The PM is told to prepare/route it; only the existing assignment path starts work, with all repository, machine, account and session checks. The selected agent is enforced on its first assignment. Only the person's current membership can approve, not an agent quoting them.
- `task.reject { conversationId, reason }`: the requesting person rejects their pending task, with a nonempty reason. No assignment or agent launch occurs.
- Store approval metadata on the existing task/proposal card, separate from assignment status. Pending is `proposal`, rejected is `rejected`, approved joins the ordinary task lifecycle. No worker is assigned while pending or rejected. The same guard covers explicit assignment, starts and automatic dispatch. PM preparation of a task does not approve it.
- Apply Review to new PM tasks for that requester and to their Buddy proposal cards. Keep the exact-consent Buddy checks and legacy proposal delivery. Represent legacy Buddy proposals on a durable card too, and link them when the PM creates the resulting task, so the feed has one continuing entry rather than duplicate work.
- Add optional `personalTasks` to `/parts` and `/changes`, for person readers only. It uses that response's existing cursor and visibility epoch, including its 30-second safety overlap; merge duplicate versions idempotently. Shape: `{ approvalMode, reset, upserts, removed }`. `reset` is true on first load; apply removals and upserts on changes. Each row has `id`, `version`, `at` (epoch ms), `projectId`, `projectName`, `title`, `agent` (null or id/name/avatar), `status`, `suggested`, and optional `reason`. Order newest first by `at`, then id. Overlay agent/project roster changes using their existing part updates; do not request the feed on a timer.
- The feed contains readable, active tasks requested by the person and their proposals; no chats or review steps. Archived, deleted, merged or dormant records leave the active feed through removals. Existing project history reads retain old work. First load uses the existing active snapshot; changes summarize only changed task parts, never all task history.

## Design (docs/feature-design-rules.md)

Reviewed revision: initial spec; independent review pending. These answers apply to #4115; each sibling task validates its implementation against this shared spec and documents its area-specific details.

1. **Growth/lifecycle:** one optional preference per existing membership; it is removed with the membership and resets on rejoin. One bounded approval record per existing task/card, removed by existing project/Swarm deletion. A task goes proposal → approved/ordinary lifecycle or rejected; rejected work stays visible until archive, never runs. Leaving/rejoining invalidates pending approval through membership generation. Existing archive/dormancy/tombstone retention removes rows from active Tasks; history remains in existing group reads. No new collection, raw feed history or timer.
2. **Concurrency:** use existing part-version guards and operation receipts. Approval/mode writes touch the person's member part. Creation reads/touches the requester; Buddy creation also touches its owner. Assignment and start guard the task; dispatch excludes unapproved tasks. Approval atomically changes metadata and makes any permitted assignment. Suggestion selection guards its agent; changing modes cannot race task creation past the mode it read. Replays recheck current authority before returning old receipts.
3. **Read cost:** reuse active first-load parts and changed parts selected by the existing cursor index. Feed rows contain summaries, no task briefs, messages, login data or machine observations. At 1,000 active tasks, first load is O(active parts) as before, with only that person's rows added; a one-task change adds one summary, and an idle cursor adds no rows. Removals are explicit; a visibility epoch change forces a reset. Test payload count/bytes and no history query on changes.
4. **Scale:** at 10× today's active tasks, change output depends on changed rows, not total history. Record summary byte counts and timing on a synthetic 1,000-task snapshot and one-task delta. Existing cache/delta metrics and backend latency expose growth; do not introduce per-person collections or a task-history scan.
5. **Compatibility/readers:** add optional fields only; do not add assignment WorkStatus values. Existing Desktop/CLI/phone task, Board, decisions, dispatch, liveness and host readers keep their normal status vocabulary. New Desktop uses personalTasks when advertised; against an old backend it must not expose unsupported approval controls. Pending/rejected are card metadata and feed states; assignment/start/queue enforcement is server-side even for old clients. Existing group/member views preserve additive fields. Light loading must keep the approval guard fields; unchanged clients may show these tasks as unassigned/proposals but cannot start them.
6. **Migration/rollback:** backend first, Desktop after, then coordinated release at 09:00. No schema migration or production write. Absent mode is autoApprove; existing tasks are not retroactively gated. Previous backend releases do not enforce the new metadata: do not roll back the approval backend while Review tasks exist; first deploy a compatible fix forward or drain pending/rejected tasks with their person's explicit decision. Production restore/anomaly reads are unnecessary for this additive JSON change; verify persistence and reload through the isolated integration store, never production.
7. **Audience:** use existing membership and project/conversation read predicates for every feed row and removal. Feed is authenticated-person only, no `asAgent` copy. Agent/avatar references come only from the reader-visible roster. No content leaves Tasks through logs/observations. PM notices remain inside the readable task/project; the existing Buddy exact-consent path controls what leaves private chat. Sharing revocation moves the epoch and resets the feed. Existing private-chat/share rules stay intact.
8. **Identity:** preference and decision commands derive identity from the authenticated person, never machineOwnerId. Match pending owner id and membership generation. A PM can suggest but cannot impersonate approval. No credential, provider-login or subscription read; sibling tasks remove legacy account/relay paths. Missing identity is refused, never replaced with a machine owner's identity.
9. **Failure:** invalid/removed/busy agents are rejected with existing assignment reasons; a stale approval, wrong person, inaccessible project or rejected task fails visibly. PM preparation can continue while user approval waits, but no session runs. Offline agents remain subject to routing/start checks. Duplicate operations use existing receipts. Invalid/expired cursors use the existing reload response; removals and revocation cannot leave a stale active row.
10. **Platforms:** backend serves Desktop on macOS, Windows and Linux with the same contract. This task starts no native process and reads no real sign-in. The sibling Desktop tasks validate light/dark and window behavior. Phone/web UI is excluded and older clients remain compatible.
