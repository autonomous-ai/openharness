# The dial lists, follows, talks to and opens agents in Rex (2026-11-25)

[Rex](https://www.superlogical.com/rex/docs) is a terminal multiplexer with a macOS app. Its sessions hold windows (the
app's tabs), and its windows hold blocks (panes). This spec adds Rex as one more host app of the dial. It uses the
screens the dial has today, and it adds none: the APPS picker, the agent's face, the panes list, a tap, a rest and
words. The pattern is Orca's (`cli/src/cable/hosts/orca.ts`) and Zellij's (`cli/src/cable/hosts/zellij.ts`).

## What `main` does today (70e8c496d6, measured on a real dial on 2026-11-25)

The test used a real dial (fw 0.1.1-dev.6dcb285e7d), Rex 0.1.0 (2061) with server API revision 8, Claude Code 2.1.332
and Codex 0.166.0.

| Case | What happened |
|---|---|
| A dial plugged in | The devices process set up Claude Code's plugin, Codex's skill and the VS Code and Cursor extension. Nothing was clicked |
| A Claude Code turn in a Rex pane | The dial got `turn.started`, `turn.done` and `summary`, and beeped |
| Claude Code asks (AskUserQuestion) in a Rex pane | The dial showed the agent waiting |
| Words said at the dial to that Claude Code | They reached the session through the plugin's mod (`[device] voice · mod`), Vietnamese included. While its question was open they were held as its next prompt, as designed |
| A Claude Code started before the plugin was installed | It has no mod. A tap on its face said "See it in Rex": no route takes its words |
| The page a Rex agent is on | "Other". Its hint `TERM_PROGRAM=rex` is not in `PROGRAM_APPS`, and Rex sets no `__CFBundleIdentifier` (`hostDetect.ts` `detectApp`) |
| A tap on a Rex agent | Rex does not switch to its pane: there is no Rex adapter |
| Codex in a Rex pane | Its words have no route: it has no mod, and its session is not in Harness's Codex home |
| Following focus in Rex | None |

## Goal

With Rex on this computer and a dial attached:

1. A Rex agent is on the "Rex" page of APPS, and its face reads "Rex".
2. A tap, or a rest on its face, switches Rex to its window and block. A tap also brings Rex to the front.
3. The dial's words reach any Rex agent at its prompt, a Codex one and a Claude Code with no mod included. A Claude Code
   with a mod keeps its mod's route first (`observed.ts` `send`).
4. Clicking a block or a tab in Rex turns the dial to that agent, as Orca's focus does.
5. The ring is in Rex's order (window, then block), and a window the person renamed names its agent.

The person does nothing for any of it: no setting, no Rex config change and no `harness device` command.

## Design

Everything is in the devices process, as for every host (cli/AGENTS.md rule 7). The core never hears of Rex.

### 1. The hook names the session (`cli/hook/notify.mjs`)

- Add `REX_SESSION` to `HOST_HINTS`, right after `REX_BLOCK`, and to `WHOLE_HINTS`: a cut one would name another
  session.
- `REX_SERVER` is not sent. A hint holds at most 64 characters, and the socket's URL is 73 in a home of 10. Instead the
  hook decides (`onOwnRexServer`): it sends `REX_SESSION` only on macOS, and only when `REX_SERVER` is unset or is this
  home's own socket, `unix://` + `encodeURI(<HOME>/Library/Application Support/rex/server.sock)`. A session of a shared,
  remote or login server is left out before the cap counts it, as a named herdr session's pane id is.
- An older daemon ignores the new hint. An older hook sends only `REX_BLOCK`, so its agent has no pane (below) and
  keeps today's behavior.

### What Rex's docs say, and what this Rex does (read 2026-11-25)

| Docs (superlogical.com/rex/docs) | This Rex (API revision 8) | So |
|---|---|---|
| A Rex terminal sets `REX_BLOCK` and `REX_SERVER` (The CLI ▸ Command Targets) | It also sets `REX_SESSION` and `REX_BIN_DIR` | `REX_SESSION` is undocumented. The hook sends it while it exists |
| "Anywhere a command takes a session, you can also pass the full ID of a block" | `-s <block id>` exits 3: "is a block ID, not a session" (`RECORDED_REX.blockAsSession`) | The session id is needed. Using the block id once servers take it is a follow-up |
| Ids "never change and are never reused" | Seen | A block id of another server names nothing here |
| Rex puts the server's `rex` first on `PATH` in every terminal, and sets `REX_BIN_DIR` (The CLI ▸ PATH) | The daemon's `PATH` has no `rex`. The folder is `~/Library/Application Support/com.superlogical.rex/RexServer/Versions/Current/Rex Server.app/Contents/MacOS` | That folder is not in the docs: the finder takes only a `rex` in a `Rex Server.app` (section 3) |
| App actions (`rex do pane.split`) need the app running with Remote Control on (Shell Scripting ▸ Performing Actions). Remote Control is in Settings ▸ General ▸ Client Info | `client.perform session.select` worked with it on | Without it, a tap changes tab and block but not the session the app shows |
| `rex client ls --json` is the server's full reply, command line clients included | Seen: the app, its second connection with no `info`, and `rex` itself | Only `info.kind: app`, `platform: macos`, this uid |
| `session.select` takes `session_id` (required) and `window_id` | Seen in `rex client inspect` | `session_id` only: the block focus already chose the window |
| macOS app for all testers; Windows and iOS apps for enrolled testers (Installation) | — | macOS first (Platforms) |

### 2. Rex is an app (`cli/src/cable/hosts/hostDetect.ts`, `scannedApp.ts`)

- `PROGRAM_APPS`: `rex: 'rex'`. `APP_BUNDLES`: `rex: 'com.superlogical.rex'`. `open.ts` then brings Rex forward with
  that bundle id, and `frontApp.ts` knows Rex in front, because both read `BUNDLE_APPS`. `NAMES` already has
  `rex: 'Rex'`.
- `PTY_HOSTS`: `rex: 'rex'`, matched only when the maker's path ends in `Rex Server.app/Contents/MacOS/rex`. A bare
  basename `rex` is too common a name to trust.
- `types.ts` already says Rex "stays on its app's" page, and it is not a `Nest`. Rex is the app here, so its page is
  "Rex". A tmux inside a Rex pane still gets tmux's page, as now.

### 3. Finding `rex` (`cli/src/cable/hosts/rex.ts`, `rexFinder`)

- Use a `rex` on this process's `PATH` only when its path ends in `/Rex Server.app/Contents/MacOS/rex`. Otherwise use the
  fixed path above, under the daemon's own `HOME`. A bare `rex` elsewhere is another program, and is never run. The file
  must be a regular, executable file owned by this user. Otherwise the result is "absent", asked again once one is
  there (`binaryFinder`), as `zellijFinder` does.
- Every command runs with no shell, with the text as one argument and `RUN_TIMEOUT_MS` (10 s), through `OrcaDeps.run`.
- `rex` with no `-S` reaches this home's own server. A block of any other server has no `REX_SESSION` (section 1), so
  it has no pane. The daemon never reads another process's environment.

### 4. The Rex adapter (`HostAdapter`, `cli/src/cable/hosts/rex.ts`)

- **`paneOf(place)`:** on macOS, `REX_SESSION` matches `^session:<uuid>$` and `REX_BLOCK` matches `^block:<uuid>$`
  (lower-case, as Rex prints them).
  - The PTY maker must be Rex Server (section 2), and the place must have the agent's pid. Then the pane is the agent's
    own, `<session>/<block>/<pid>`: `type` checks the block's foreground against that pid.
  - Otherwise, for example a multiplexer inside the Rex pane, it is `held:`. A held pane takes a tap only and no words,
    as Orca's `HELD` and Zellij's.
- **`canFocus`:** `rex` was found.
- **`focus(pane)`, a tap:**
  1. `rex block focus -s <session> <block>`: the server's focus.
  2. `rex block inspect -s <session> <block> --json`: the block's `window_id`, its tab.
  3. `client.perform session.select {session_id, window_id}` to each of this user's `kind: app` clients
     (`rex client ls --json`). The app follows the server's focus within the tab it shows, but changes no tab for it
     (Diego on the dial, 2026-11-25): its own Go to Session, given the window ("A window in the session to show"), does.
  4. `open.ts` brings Rex forward.

  With Remote Control off, step 3 is refused. The block is still focused on the server, and Rex comes forward where it
  was. The log gets one fixed line (`[device] open · rex · session not shown`), counted.
- **`canShow` / `show(pane)`, a rest:** steps 1 to 3, only while Rex is the settled front app, so the pane the dial rests
  on is the one on screen, in its tab and session. No line when the app refuses.
- **Scrolling** (`canScroll`, `pageKeys`, `scroll`): a stroke on the agent's own block, or the block its layout placed it
  at (section 5), with Rex in front.
  - No `onScreen`, as VS Code's terminals: the devices ask a pane either whether it is on screen or whether it takes page
    keys (`devices.ts` routeOf), and Claude Code fullscreen needs the second. The dial rests the block on screen as it
    turns to it.
  - Rex's docs: Scroll Page Up and Down (`client.scroll.page_up/down`, Mac Actions) scroll a block's scrollback, and
    "full-screen programs … draw on a separate screen that has no scrollback" (Shell Scripting). Measured: on a
    shell's 300 lines both performed; on Claude Code drawn fullscreen the app answers `not_supported` ("isn't
    available here right now"), and its own PageUp and PageDown keys (`rex send-key … pageup`, Writing Keys) moved its
    view from line 65 to 38 and back.
  - So `pageKeys` is Claude Code at no question, `"tui": "fullscreen"` in its settings (claudeRenderer.ts, as VS Code's
    terminals read it), and the agent the block's foreground, within 1 s. Then a stroke sends it mouse-wheel events;
    else the app's Scroll Page Up or Down of that block.
  - Wheel, not page keys: a page key moved Claude Code half a screen (65 → 38), which read as jerky on the dial; an
    SGR wheel event (`ESC[<64;10;10M` up, `ESC[<65;10;10M` down, `rex send … --`) moved it about a line (65 → 64 → 63 and
    back). One wheel event a dial line, up to 10 in one `rex send`, 30 ms after each send, at most 20 waiting either
    way, so a fling stops with the finger.
  - App pages: 8 dial lines a page, a 100 ms gap after each, at most 4 pages waiting, a remainder forgotten after 1 s:
    Herdr's numbers (herdrApp.ts) and VS Code's (loop.ts).
- **`canType` / `type(pane, text, engine, atPrompt)`:** only an own pane. Words go only through the existing `send`
  checks: needs-you refuses, working refuses, and the mod and Codex queue come first (`observed.ts`).
  1. Read `rex block call -s <session> -b <block> process`. Its `foreground.pid` must be the agent's pid, the hook's
     `callerPid`. Otherwise the result is `failed`: the block holds a shell or another program now.
  2. `rex send -s <session> -b <block> <text>`. Control characters become spaces (`CONTROL`), and the text is at most
     `MAX_TEXT`.
  3. Wait the settle every typed host waits: `INJECT_PASTE_DELAY_BASE_MS` plus 1 ms per 60 characters, at most
     `INJECT_PASTE_DELAY_MAX_MS` (`lib/submitTiming.ts`, as `vscodeTerminals.ts`). This is the Codex Enter loss in the
     spike.
  4. Ask `atPrompt()` again and read `process` again, then `rex send-key -s <session> -b <block> enter`. If either check
     fails, nothing more is typed, and the result is `failed`.
- **`voiceRefusal`:** none. With no route, the dial's own "See it in Rex" stays.

### 5. Order, names and focus follow (`createRexReads` in rex.ts, `services/devices.ts`), as Orca's and tmux's

- **Order and names, read as Orca's (decided 2 of 2026-11-16):** with a dial attached, on macOS, each time an agent
  enters or leaves Rex's page, or one's Rex pane changes, one layout read runs, one at a time (a change during it asks
  for one more after it). Never polled.
  - The read: `rex ls --json`, then `rex api call -s <session> session.view` per session, then `process` and `title` per
    block, at most 16 sessions and 64 blocks. Its order is Rex's own: sessions as `session.list` orders them ("New
    sessions go at the end, and session.move changes the order"), windows as `session.view` does ("Rex.app shows them
    as tabs in this order"), blocks layer by layer, each "in layout order".
  - The ring goes in that order (`setRank('rex')`). An agent in no block read goes after the placed ones.
  - Each agent is named by its block's title, the one its program set and the app shows on the pane and the tab (Rex's
    Settings ▸ Terminal ▸ Titles), through the existing rule (`observed.ts` nameOf): a session the person named keeps
    that name, and a block with no title leaves the folder's. Tabs and panes renamed in Rex (Rename Tab, Rename Pane)
    are a follow-up: where Rex keeps those names was not measured.
  - An agent with no block of its own (found by the open scan, or heard from an older hook with no `REX_SESSION`) is
    placed at the block whose foreground process is its pid, when exactly one is: for its order, its name and the block a
    rest or a tap focuses, never its words (`observed.ts` shownOnly). The scan names its app Rex by its parent, the Rex
    Server app (`com.superlogical.rex.server`, frontApp.ts), so it is on Rex's page, not Other's.
- **Focus follow, as WezTerm's, kitty's and tmux's (focusPoll.ts):** while Rex is the settled front app with a dial
  attached and an agent's block on Rex's page, one poll reads `session.view` of each session holding such a block every
  500 ms. Each session is a place: the agent at the focused block of the window it shows.
  - The Rex app shows one session at a time, and this Rex tells no client which (API revision 8). A session whose focus
    changed since the last read is the one the person works in, so the poll turns the dial to a place that changed, one
    alone (paneAnswered).
  - The dial's own rest and tap are noted, and the read that sees them is their echo (paneTaps).
  - Not followed: the person picking another session in Rex's sidebar alone changes no focus. The dial turns at their
    next click on a block or tab there.

### 6. An answer outside Harness reads as prose on the dial (`lib/deviceRecap.ts` deriveAnswerCard)

Found on the dial with Rex, true of every app outside Harness: an observed agent's last answer (its transcript's last
turn) went to the dial raw, as the summary's headline, text and full text (`devices.ts` outsideTurn, `cableHost.ts`
recentSummaries), so the dial drew `**` and `##`. A Harness agent's turn is cut by `deriveTurnSummary`, its markdown gone.
Now the observed answer is cut the same way: the headline and the text under it with no markdown, the answer as the
full text, which the long view strips as it is sent (`deriveLongRecap`). An answer with no prose sends no summary.

## Design (docs/feature-design-rules.md)

Reviewed revision: ______  Reviewer: ______

1. **Growth:** nothing is stored on disk. In memory: the ring's members and its rank (replaced at each read, dropped at
   a detach), each pane's scroll remainder (one small record per Rex agent stroked), and the focus poll's last answer
   (one entry per session holding an agent, dropped with the poll). [x]
2. **Concurrency:** one layout read at a time, a change during it asking for one more after. One focus poll, one read at a
   time (focusPoll.ts). One run of wheel sends or app pages per pane, the strokes meanwhile adding to it. `type` re-reads `process`
   and `atPrompt` right before its Enter, and types into one block at a time (a second word meanwhile is `failed`). [x]
3. **Read cost:** a layout read is 1 + S + 2B `rex` runs (S sessions ≤ 16, B blocks ≤ 64), only when Rex's page changes.
   The focus poll is one `rex api call … session.view` per session holding an agent, every 500 ms, only while Rex is the
   settled front app with a dial attached; zero calls otherwise. [x]
4. **Scale:** at 10x sessions the layout read stops at 16 sessions and 64 blocks; the poll reads only the sessions that
   hold an agent. The metric that warns first is `rex` runs per minute while Rex is in front. [x]
5. **Compatibility:**
   - An older hook sends no `REX_SESSION`: its agent has no pane of its own, and is placed by its process as one the
     scan found.
   - An older daemon ignores the new hints.
   - Firmware is unchanged: `apps`, `caps` and `host` exist.
   - Every Rex command used was run on API revision 8, and each is in Rex's CLI reference with the flags used.
   - The docs are ahead of this Rex: they show a flag this Rex CLI lacks (`rex run --interactive`) and a block id as a
     session, which this server refuses. So only spike-verified commands are used.
   - `REX_SESSION` and the `Rex Server.app` folder are not in Rex's docs. If a later Rex drops either, its agents get
     no pane, as today, and nothing else breaks.
   - Readers of `PROGRAM_APPS`, `APP_BUNDLES` and `PTY_HOSTS` come from a search of the code: `detectApp`,
     `BUNDLE_APPS` (`open.ts`, `frontApp.ts`) and `ptyHostOf`. [x]
6. **Migration and rollback:** none: no stored field. A rollback to the previous CLI puts Rex agents back on "Other",
   with no other effect. [x]
7. **Audience:** local only. The commands go to the person's own Rex socket, through a binary owned by this user.
   Nothing leaves the computer, and no text is logged, only fixed reasons and counts. [x]
8. **Identity:** the devices process runs as the person, the same uid as their Rex server. No login is used. N/A
   beyond that. [x]
9. **Failure:**
   - `rex` absent or failing: the agent keeps today's caps, the dial says "See it in Rex", and the log has one fixed
     line.
   - A typed word refused by the checks: the dial says "<name> did not answer." (`observed.ts`).
   - Remote Control off: a tap focuses the block on the server, and Rex comes forward where it was, with one counted
     line; a rest says nothing; a stroke with no page keys pages nothing.
   - A layout read that fails: one line (`[device] rex order · failed`), the ring as it was, and the next change asks
     again.
   - A focus poll that fails three times in a row stops until the next settle (focusPoll.ts). [x]
10. **Platforms:**
    - macOS: the Rex app.
    - Linux: Rex runs servers there, and its Linux client is not in testing yet. Its panes keep `TERM_PROGRAM=rex` and
      get the "Rex" page, with no adapter and no layout read (follow-up).
    - Windows: a Rex app exists for enrolled testers. The hook sends no `REX_SESSION` there, so its panes get the
      "Rex" page with no adapter and no layout read (follow-up).
    - iOS: N/A. [x]
